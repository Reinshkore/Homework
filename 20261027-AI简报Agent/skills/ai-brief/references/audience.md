# 受众档位：结构与语言

三个档位不是「同一份报告的三种详略」，而是**三种不同的落点**。写之前先确认读者读完要拿到什么：

- 非专业：这件事跟我有什么关系
- 学习者：这件事挂在技术栈的哪一层
- 业内：我该改什么，哪里可能错

落点错了，写得再细也没用。

## 一、非专业

读者不写代码、不看发布会，但关心自己的生活和工作会不会被影响。他不是理解能力差，是**没有背景知识**，所以任何未解释的名词都会直接切断阅读。

### 单条三跳结构

**第一跳 · 发生了什么**

一句话。不出现英文缩写，不出现参数规模，不出现评测集名称。公司名和产品名可以留。

**第二跳 · 凭什么说它重要**

做一次对照：以前要怎样，现在变成怎样。对照必须是读者能凭常识判断的，不能是行业内部的对照。

反例：「上下文从 6.4 万提到 100 万」——读者不知道 100 万是什么概念。
正例：「以前它读完一份百页合同就忘了前面，现在能一次读完。」

**第三跳 · 会先影响到谁**

给具体场景或职业，不给「行业」「生态」这类词。

反例：「将深刻影响千行百业」。
正例：「先变的是需要整天翻合同、翻财报、翻病历的岗位。」

### 语言规则

- 术语必须当场换成日常说法。换不掉时加「，就是……」接一句解释，只解释这一次。
- 可以用：公司名、产品名、钱、时间、数量对比、生活场景。
- 禁用：参数规模、benchmark 名称、架构名词（MoE、量化、KV cache、多模态）、「赋能」「重塑」「范式」「奇点」。
- 禁用宏大叙事句：「AI 时代已经到来」「这标志着一次革命」。
- 数字要换算成可感知的量：不说「每百万 token 2 美元」，说「处理一本三百页的书，成本不到一分钱」——换算须注明是估算。

### 结论姿态

给判断，但必须标注这是判断，并说明依据。非专业读者没有能力自己复核，所以更要说清楚「我凭什么这么想」以及「我可能错在哪」。

## 二、学习者

读者有基础，缺的是结构。他的困难不是「看不懂名词」，是「新信息没地方放」。

### 单条五段结构

**1. 发生了什么**（事实层）

1–2 句。只写可溯源内容，不加因果词，不加评价。

反例：「OpenAI 重磅发布，彻底改写行业格局」——「重磅」「彻底改写」是评价，不是事实。

**2. 改动在哪一层**（定位层）

映射到 AI 技术栈固定五层，写明改的是哪层、有没有波及相邻层。

| 层 | 内容 |
|---|---|
| L1 算力与硬件 | 芯片、集群、互联、能耗 |
| L2 模型与训练 | 预训练、后训练、架构、数据 |
| L3 推理与部署 | 推理优化、量化、上下文管理、单位成本 |
| L4 工具与产品 | Agent 框架、API、应用产品 |
| L5 治理与生态 | 监管、标准、开源许可、行业联盟 |

这一步是学习者档的核心价值：单条新闻看不出结构，五层定位告诉他这件事该放进哪个抽屉。

**3. 为什么能做到**（原理层）

1–2 句，说清技术因果，必须带前置条件——「因为 X，所以在 Y 条件下可以 Z」。

反例：「得益于算力提升和算法优化，模型能力大幅增强」——零信息量。
正例：「长上下文靠稀疏注意力把复杂度从 O(n²) 压到近似线性，代价是超长序列的检索精度下降。」

**4. 还差什么**（边界层）

1 句。指出当前失效条件或未解决部分。没有边界的内容不该进简报——它要么是营销，要么是幻觉。

**5. 术语锚点**（按需）

格式：`术语：一句话定义（≤20 字）`。只在术语是理解本条的前提时写。

### 语言规则

- 术语可用，首次出现给中文译名 + 一句话定义
- 因果链要完整，允许出现「因为……所以……但前提是……」的长句
- 不用「据悉」「业内人士称」作唯一信源表述
- 数字给具体值，不给「大幅」「显著」

## 三、业内

读者在做这件事。他知道 MoE 是什么，知道 benchmark 会刷分，知道发布会说的和能用的差多远。**任何解释性的铺垫对他都是噪音。**

### 单条四段结构

**1. 增量**（省掉所有已知前提）

只写这次变了什么。不交代背景，不解释概念，不复述行业共识。

反例：「MoE 是一种混合专家架构，可以降低推理成本。NVIDIA 最近发布了……」
正例：「Bolt 74B-A9B 用 2-bit 把驻留压到 24GB，激活 9B——比同档开源模型的常见做法多压了一档。」

**2. 机制**（关键取舍，可以直接上术语与数字）

写清楚代价落在哪。任何「只讲收益不讲代价」的描述都是产品稿。

正例：「2-bit 量化省的是带宽和容量，代价是长链工具调用时的误差累积，所以它在单步任务上的跑分参考价值有限。」

**3. 与我相关**（对当前做法的具体影响）

落到三件事之一：架构选择、成本模型、评估口径。写不出具体的，就说明这条对他没用，应当降档或不写。

**4. 不确定处**（哪部分不可靠）

- 哪些数字是厂商口径、哪些有第三方复现
- 缺什么数据才能下结论
- 什么条件出现时，这条判断会被推翻

### 语言规则

- 术语直接用，不解释
- 每个数字标口径：`（厂商宣称）`／`（第三方实测）`／`（估算）`。不标口径的数字一律视为不可信
- 禁用：科普式铺垫、「值得关注」「拭目以待」「意义重大」、把「发布」说成「变化」
- 允许并鼓励：直接指出某个说法站不住，以及为什么

### 结论姿态

给假设，不给定论。格式：**我认为 X，因为 A、B；若出现 C，则 X 不成立。当前倾向：偏信 / 存疑。**

业内的价值不在「知道得多」，在「知道哪部分不可靠」。报告如果读完让人更确定而不是更清醒，就是写失败了。

## 四、三档共同的禁止项

不论哪一档，以下一律不许出现：

- 「你怎么看」式问题
- 把预测写成已发生
- 用二手转述当唯一信源而不标注
- 用「据悉」「有消息称」替代具体来源
- 在事实段做因果推断
- 为了凑条数纳入不合格事件

## 五、切档时的常见错误

| 错误 | 表现 | 修法 |
|---|---|---|
| 术语泄漏 | 非专业档出现 benchmark 名称 | 换成「在某个专业测试里排第一」并说明这个测试考什么 |
| 过度简化 | 非专业档把机制全删，只剩结论 | 保留「为什么能做到」的一跳因果，删的是名词不是逻辑 |
| 科普污染 | 业内档解释什么是 MoE | 整句删除，直接写增量 |
| 口径缺失 | 业内档写「提升 8 倍」不说谁测的 | 补 `（厂商宣称）`，或删掉这个数字 |
| 结论溢出 | 学习者档替读者下了判断 | 把判断移进主线块，正文只留结构与边界 |
