# 构建流程记录

用途：记录「我如何用 WorkBuddy 把这个项目做出来」。不是操作手册，是过程档案。
读者：我自己（写汇报、答问时查依据）；老师若问"你怎么做的"。
写法：每完成一个里程碑追加一节，不回头改已写的内容（改了就在新节里写"更正"）。
随仓库上传（原在 `docs/` 下不追踪，提交前已移出；`docs/` 其余工作文档仍不上传）。

每节固定四栏：

| 栏 | 记什么 |
|---|---|
| 我下了什么决定 | 决策点编号 + 选项 + 理由（一句话，不写长篇） |
| Agent 做了什么 | 产出的文件、改动的模块（不用列全，指到关键处） |
| 我怎么验证 | 跑了哪条命令、看到什么输出、接受还是打回 |
| 卡在哪 | 报错原文、几轮修好、有没有改计划 |

> 仓库内只保留两份记录文档（本文与 `分析-demo5拆解与重构设计-2026-10-24.md`）。文内提到的项目计划、改动记录等属于本地工作文档，未随仓库上传。

## M0 决策与连通性

**Agent 做了什么**

- `scripts/probe_search.py`：标准库实现，零依赖，可跑四种源（`deepseek` / `bocha` / `zhipu` / `tavily`），未填 key 自动跳过。
- `.env.example` + `.env`：按「主模型 / 检索」两段组织，四个检索 key 并列，可全填做横向对比。
- 探针不只报"通不通"，同时算两个决策指标：**日期完整率**、**一手候选率**（按 `industries/ai.md` 的域名白名单分级）。

**我怎么验证**

- 未填 key 时跑了一次，确认 `.env` 解析、HTTP 调用、错误分支、对比表都能走通（拿占位符 key 打到 `api.deepseek.com`，返回 401 并原样显示，说明链路是通的，只是 key 不对）。

**探针结果（2026-10-24 20:40，2 个查询 × 7 天窗口）**

```
provider     条数    延迟ms    日期率   一手   次选    窗口外    唯一题    重复率  状态
deepseek     20     476   1.00    1    1      1     18   0.10  ok
bocha        20     388   1.00    0    1      0     17   0.15  ok
zhipu        20    1266   1.00    0    0     14     20   0.00  ok
tavily       12    2705   1.00    0    1      0     12   0.00  ok
```

第一次跑出来的表里 Tavily 日期率显示 1.00，是假数——它返回 RFC1123（`Sat, 24 Oct 2026 ...`），被 `[:10]` 截成 `Sat, 24 Oc`，于是"有日期"。修了 `parse_date()` 并把「窗口外条数」「唯一标题数」加进度量后重跑，才是上面这张表。

**我下了什么决定**

- **D1 = DeepSeek 主用**，博查留作补检备选，智谱与 Tavily 淘汰。
- 依据不是"哪家搜索结果更好看"，而是四条可测的量：延迟、日期率、窗口外条数、一手候选数。

**四条被判死的理由**

| provider | 判死理由 |
|---|---|
| zhipu | **窗口外 14/20**。它只有 `oneMonth` 这种相对窗，代替不了 7 天，70% 结果落在窗外。延迟还是 DeepSeek 的 2.7 倍 |
| tavily | 7 天窗内只返回 12 条（第二个查询仅 2 条），延迟 2705ms 为四家最高；且付款渠道不通，超额即断 |
| bocha | 没判死，降为备选：延迟 388ms 略优、日期率 1.00、结果集与 DeepSeek 互补（Meta Muse Spark、月之暗面只在它这里出现）。问题是一手候选 0 |

**四条必须带进设计的事实**（比 D1 本身更重要）

1. **时间过滤是软的。** DeepSeek 20 条里有 1 条越出窗口。`after:/before:` 是搜索引擎的排序偏好，不是硬约束。→ `evidence_add` 必须自己再判一次日期，越界的标记 `boundary` 或拒收，不能信检索参数。
2. **重复率 10–15%，且是跨站转载。** 博查那组里同一篇"KV Cache 砍掉 99%"分别出现在网易、`m.163.com`、`c.m.163.com`、新浪——按 URL 去重只能拦下子域相同的两条，跨站拦不住。→ 证据表必须有 `title_norm` 指纹列，去重键 = `url_norm` + `title_norm`。
3. **一手率极低（1/20 = 5%），`site:` 能定向但会把无关页面捞进来。** 实测查 `MiniMax M3.1 Flash site:minimax.io`，返回的全是 `platform.minimax.io/docs/...` 的 API 文档页，不是模型发布页；查 `Kimi K3.1 Pro site:github.com` 返回的是 AutoGPT、opencode 里第三方接入的 PR。→「域名是官方的」不等于「这是该事件的发布载体」。一手认定要在域名规则之外再加一层**页面性质**判据（路径含 `/blog/`、`/news/`、`/releases/`、`/pricing`、`/models/` 才算发布页；`/docs/` 降级）。
4. **`authority` 不能当一手判据。** 新浪财经拿到 a=4（最高档），而 BAAI 智源那一条是 a=3。权威度衡量的是站点分量，不是"是否原始载体"。若拿 authority 直接填证据表的「一手」列，会系统性地把二手大媒体判成一手——这正好是技能 `quality.md` 四之一最反对的事。

**卡在哪**

- 智谱那条没有继续深究：`search_engine` 还有 `search_pro` / `search_pro_sogou` / `search_pro_quark` 三档，换档可能改善质量，但**区间能力缺失是接口层面的**，换档救不回来。不值得花时间。
- 一手率低这件事没有当场解决（用 `site:` 试了，结果如上）。它不阻塞 M1，但要在 M4 跑首期时决定：接受"本期无一手信源"照实标注，还是每期花 2–3 次 `site:` 检索换 1–2 条一手。

### M0 补测：英文检索与 fallback（20:52）

**起因**：中文查询的一手率只有 5%，而技能的主体清单一半是国外主体——中文报道对国外事件必然是二手编译。所以问题不是"哪个源更好"，是"检索维度里缺了英文"。

**同一批查询的英文版本，四源对比**

| 配置 | 条数 | 延迟 | 一手 | 窗口外 | 重复率 |
|---|---|---|---|---|---|
| DeepSeek 中文（基线） | 20 | 476ms | 1 | 1 | 0.10 |
| DeepSeek 英文（无运算符） | 20 | 463ms | 2 | 0 | 0.00 |
| **DeepSeek 英文 + `lang:en`** | 20 | 644ms | **3** | 0 | 0.05 |
| 博查 英文 | 20 | 399ms | 0 | 0 | 0.05 |
| 智谱 英文 | 11 | 3381ms | 0 | 8 | 0.00 |
| Tavily news + 日期过滤 | 19 | 3345ms | 0 | 0 | 0.00 |

**三个结论**

1. **英文检索必须加。** DeepSeek 加 `lang:en` 后一手从 1 提到 3（5% → 15%），命中 `huggingface.co`、`amazon.com`、`noahpinion` 这类真正的原始载体。代价是延迟 +40%（463→644ms），可以接受。
2. **博查不能用于英文。** 英文 query 打进去，返回的全是中文媒体（Arabian Business 一条，其余中文）。它把英文词当中文索引处理了。
3. **Tavily 的"英文官方源优势"不成立。** 换了三种配置都没体现：

   - `topic=news` + 严格日期过滤：只给英文媒体（Bloomberg / TechCrunch / the-decoder / interconnects），官方域名 0；
   - `topic=general` 不滤日期：给的是常青内容（Wikipedia、GitHub 清单、nvidia 营销博文、McKinsey、Reddit、YouTube），成文日期不受控，时间闸门直接失效；
   - 原因不在配置，在定位：Tavily 优化的是"可读的检索增强内容"，不是"原始发布载体"。官方 release 页往往不是新闻体裁，也没有可靠的 published_date。

   所以 Tavily 的真实价值是"英文二手报道质量"，而一手本来就该靠 `site:` 定向 + 页面性质判定去拿，与 provider 无关。**不引入 Tavily。**

**由此改了 M2 的两处设计**

- **fallback 要按语言分开**：中文查询失败降级到博查；**英文查询失败不降级**——博查的英文结果实测全是中文，降级等于用中文结果冒充英文维度，比报错更糟。
- **检索配额从 18 提到 24**：6 类 × 2 语言 = 12 次基线，留 12 次给"类型覆盖不足"的定向补检。

**实测总数**：本轮约 110 次调用，成本约 ¥0.55。

**Agent 做了什么**

新建了这些文件，demo5 只搬机制、不搬业务：

| 文件 | 作用 |
|---|---|
| `core/config.py` | 路径与环境变量的唯一入口。拆掉了 demo5 里 `history.py` 反向 import `agent.py` 的循环依赖 |

| `agent/builder.py` | 装配：模型 / MCP / 权限 / 检查点 / 技能发现 |
| `agent/events.py` | 事件流，**`answer` 只装正文，旁白单独走 `thought`** |
| `agent/prompts.py` | 系统提示词，只写行为约束，不写人格 |
| `agent/subagents.py` | 只有 `critic`，工具留空 |
| `tools/timebox.py` `tools/calc.py` | `get_current_time` `resolve_window` `calculator` |
| `app.py` | Streamlit：左侧对话、右侧执行轨迹 |
| `scripts/smoke_chat.py` | 无界面冒烟测试，M1 的验收命令 |
| `memory/AGENTS.md` | 长期记忆：路径、口径、禁止项 |
| `mcp_servers.json` | `brief-store` 先占位，`enabled: false`，M3 再打开 |

**权限表**（顺序敏感，第一条命中即生效）：

```python
allow  write  /outputs/**  /docs/ledger/**
deny   r/w    /.env  /.venv/**  /data/**  /runtime/**  /.git/**
deny   write  /docs/**
deny   write  /**
```

第一行必须在最前，否则会被后面的 `deny /docs/**` 抢先匹配——这条规则一旦写反，不会报错，只会表现为"账本写不进去"。

**我怎么验证**

1. `smoke_chat.py --info` → 3 工具 / 0 MCP / 0 技能 / 无警告。
2. 真实对话「今天几号？再算 (3.5-2)/3.5*100」→ 触发 `get_current_time` 与 `calculator`，返回 2026-10-24 与 42.86，`answer` 62 字，**没有混进任何过程说明**。
3. 权限双向验证：让它同时写 `/docs/evil.md` 与 `/outputs/briefs/ok.md`。前者被拒且磁盘上确实没有该文件，后者写入成功（2 字节）。这是一次把"权限隔离"从配置变成证据的测试。
4. Streamlit 起在 8511，HTTP 200，日志无 traceback，随后关掉并清理测试文件。

**卡在哪**

1. **依赖装了 10 分钟。** 清华镜像对 `deepagents` 的 wheel 直接返回 403，换阿里云镜像才通。`pip install -r <(printf ...)` 这种进程替换在 Windows 的 Git Bash 里传进去是 `/proc/...` 路径，pip 读不到——老老实实用 `requirements.txt`。
2. **`403 Workspace endpoint access denied`，排查花了不少时间。** `.env` 里的 `LLM_BASE_URL` 是从 demo5 的 `.env.example` 抄来的课程专用 workspace 端点。换成自己的 key 之后：`GET /models` 正常返回 180 个模型，`POST /chat/completions` 却 403。**这个组合极易误判成"key 失效"**——因为列模型能通，会先怀疑 key 权限。实际是端点绑定了某个工作区。
   改成标准端点 `https://dashscope.aliyuncs.com/compatible-mode/v1` 后立刻正常，`qwen3.7-plus` 可用。这条已写进 `.env.example` 的注释和计划的风险表。
3. deepagents 装到的是 0.7.32（demo5 是 0.7.24）。先核了 `create_deep_agent` 的签名，参数没变，才继续——没有核对就搬代码是这类项目的常见坑。

**原理点**

装配集中在一个函数，好处不是"代码短"，是**改能力只改一处**。这次改权限表、加工具、换模型，全部只动 `agent/` 与 `tools/`，`app.py` 一行没改，界面照样能用。反过来说，如果界面里散落着"某工具叫什么名字"这类知识，每加一个工具都得改界面。

## M2 检索层

**Agent 做了什么**

| 文件 | 作用 |
|---|---|
| `core/sources.py` | 信源规则的唯一实现：域名分级、`url_norm`、`title_key`、`is_publish_page`、`is_primary` |
| `tools/search.py` | `web_search` / `fetch_page`，三个 provider（deepseek / bocha / mock），按语言分流的降级，配额计数 |
| `tools/registry.py` | 登记 5 个进程内工具 |
| `fixtures/mock.json` | 离线快照占位（空，M6 填真实数据） |
| `tests/test_search.py` | 10 条离线测试，不联网 |
| `app.py` | 新会话时重置检索配额 |

**几个刻意的取舍**

1. **同步实现，不用 async。** 检索会阻塞事件循环 0.5–3 秒，但这是单用户串行场景，界面在另一个线程，感知不到。换 async 要赌框架对协程工具的支持，多一处会坏的地方。
2. **`fetch_page` 用 DeepSeek 的 Fetch 接口**，不自己写正文抽取。少一个 HTML 解析库，也少一类解析错误。
3. **英文不降级**是写死在代码里的，不是靠提示词约束模型。提示词会被忽略，`if lang == "en": return error` 不会。

**我怎么验证**

1. `python -m unittest discover -s tests` → 10 条全过，0.001 秒（不联网）。
2. 真实双语对话（让 Agent 各搜一次中英文）→ 2 次工具调用，返回 20 条，日期与域名都齐。
3. `fetch_page` 实测抓一篇 → 3276 字正文，标题与日期正常。
4. 手工验降级：把 `SEARCH_PROVIDER` 改成必然失败的 `mock`，
   - 中文 → `degraded=True, provider_used=bocha`，拿到 8 条；
   - 英文 → `degraded=False`，报错文案正确。
5. 配额：`limit=2` 时第 3 次调用被拦，`used` 停在 2。

**实测后收紧的三处**

| 项 | 改前 | 改后 | 原因 |
|---|---|---|---|
| snippet 长度 | 320 字 | 240 字 | 一条 10 hit 的返回 ≈ 4.5k 字。按一期 12 次检索算，光原始结果就是 2.6 万 token。240 字够判主体与事件类型，细节交给 `fetch_page` |
| `count` 上限 | 20 | 10 | 模型第一次就把 count 拉到 20，多出来的几乎全是同事件转载 |
| 排除域名 | 只在报告层判 | 工具层直接过滤 | arXiv、Papers with Code 混进结果，模型会误当事件用。技能本来就排除它们，在工具层拦更省事 |

**卡在哪**

1. **`fetch_page` 返回的 Markdown 带反斜杠转义**（`\# 标题`、`\-`），模型会照抄进正文。加了一条去转义。
2. **一手判定偏严。** `hub-assets-cache.baai.ac.cn/view/58947` 被判成 `primary` 但 `publish_page=False`——路径 `/view/` 不在发布页模式里。这是故意的：宁可少认一手，不可多认。M3 的 `evidence_update` 允许模型带理由覆盖，覆盖记录留在库里可查。
3. `docs.nvidia.com` 的 Release Notes 也出现在结果里，同样因 `/docs/` 被判非发布页——符合预期。

**原理点**

工具的返回值就是上下文预算。同一个检索，返回 20 条带 320 字摘要 = 6k 字，返回 10 条带 240 字 = 2.4k 字，差 2.5 倍。**模型不会因为信息多而判断更准，只会因为要读的东西多而漏掉后面的**。所以"返回什么"是设计决策，不是实现细节。

| 去重 | `url_norm` + `title_norm` 双键 | URL 去重拦不住「同一篇稿子发在网易和新浪」 |
| 窗口 | 入库时自判，窗口前 48 小时内标 `boundary` 放行 | 检索参数是软的，实测 5% 越界 |
| 一手 | `kind=primary` + `is_publish_page` + `fetched_chars>=200` 三条同时满足 | 权威度评分会把新浪财经判成一手 |
| 单信源簇数 | `evidence_query(view="sites")` 直接给每个信源几个簇 | 跨条目统计，模型数不过来 |

**`period_id` 的设计取舍**：`窗口起止|受众|篇幅` 拼成主键。同一窗口同档位重跑会落进同一期，覆盖旧候选。这是故意的——重跑产生两份互不相干的证据，比覆盖更难排查。

**我怎么验证**

1. `scripts/probe_store.py` → **13/13 通过**。10 条人造数据里：4 条被拒（窗口外、arXiv、缺日期、非法类型）、2 条被判重复（URL 带跟踪参数、跨站转载）、4 条入库，其中边界条目被放行并标记，官方 docs 页没被认成一手。
2. `smoke_chat.py --info` → MCP 加载出 3 个工具，无警告（总工具数 8）。
3. 端到端：让 Agent 检索一次 → 挑 3 条入库 → 用 stats 报告。**10 次工具调用**，3 条入库，数据库里落盘正确（`kind` 分别是 other/other/secondary，`is_primary` 全 0）。
4. 直接查 `runtime/store.db` 核对，不只看 Agent 的自述。

**卡在哪**

1. **我自己写错了一条断言。** probe 期望「10 条入 6 条」，实际 4 条——因为我心算 10−4−2 时把拒绝数算错了。probe 把这个错抓出来了。这正好说明验收脚本的价值：它不替模型背书，它替你算一遍。
2. `query_clusters` 第一版里 `evidence_ids` 填的是 `in_report` 的值，纯手误。加断言时发现的。
3. Agent 一次简单任务用了 **10 次工具调用**（检索 1 次 + 入库 + 多次 query 换视图）。它没有滥调，但也没有节制——M4 要在技能里写清"stats 只看一次"。

**原理点**

证据库的价值不是"存数据"，是**让规则有地方执行**。技能里「同一信源最多供 2 簇」这句话，写在提示词里是愿望，做成 `view="sites"` 的查询结果就是事实。同样，「一手率」在技能里是一个要模型自己数的指标，现在是 `stats.primary_rate` 一个字段。

顺带说个观察：这次 Agent 报出"一手率 0%，因为 3 条都来自媒体转载"——它没有辩解，也没有硬凑。说明 `kind` 与 `publish_page` 两个字段确实进了它的判断，返回结构起作用了。

## M4 Skill 适配 + 首期

**Agent 做了什么**

1. 把技能整份复制进 `skills/ai-brief/`（10 个文件、1540 行），按清单改了 8 处 + B3 双语。改完 `SKILL.md` 从 155 行变 213 行。
2. 端到端跑第一期：**11 分 07 秒，56 次工具调用**。

**工具调用序列（这是 M4 的真正验收对象）**

```
read_file → get_current_time → resolve_window → glob ×2 → write_todos
  → read_file ×5（SKILL.md + 4 个 references）→ write_todos
  → web_search ×11（中英混合）→ fetch_page ×3
  → evidence_add ×1
  → evidence_update ×17 → evidence_query(rows) → evidence_update ×2 → evidence_query(stats)
  → read_file ×2 → write_file（正文）→ edit_file → write_file（账本）
```

顺序是对的：**先检索、再入库、然后判定、最后写盘**。M4 想验的就是这个——如果它跳过 `evidence_add` 直接判定，后面的去重与统计就全是空的。

**产出**

- `outputs/briefs/ai-brief-学习者-标准-2026-10-24.md`（2930 字）
- `docs/ledger/.ai-brief-ledger.md`（2 条主线 + 3 条悬置事项 + 检索缺口）

账本写得相当扎实：悬置事项带「下期该看什么」，检索缺口如实写了「T2 首轮返回的全是平台文档页，不是事件」「T3 无独立合格事件」。

**四个缺陷（都是质检发现的，不是猜的）**

| # | 问题 | 证据 | 归谁管 |
|---|---|---|---|
| 1 | 篇幅超配额 46% | 2930 字 vs 标准档上限 2000 | `brief_lint`（M5） |
| 2 | 术语锚点只有 1/8 | 学习者档要求每条事件一个，实际只有第 3 条有 | `brief_lint`（M5） |
| 3 | 簇合并根本没做 | 库里 15 条 = 15 个单条簇（`max_cluster=15`），报告头写「事件簇 8 个」——它是拿入选条数当簇数。根因：两次 `evidence_query` 分别是 `rows` 和 `stats`，**从没调过 `clusters`** | 技能 + lint |
| 4 | 事实段与推断段自相矛盾 | 第 4 条写「正式进入可用状态（GA）」，同一条的「还差什么」又写「下月正式可用」 | `critic` 子代理 |

**当场修了两处**

- `SKILL.md` Step 3 加了一道硬门：合并完必须调 `evidence_query(view="clusters")` 核对，**若每个簇的 `source_count` 都是 1，说明一条都没合上，回本步重做**；报告头的簇数取自该视图，不取入选条数。
- `events.py` 的 `tool_result` 加了 `chars` 字段：原来界面显示「返回 406 字」是截断后的长度，不是真实返回量，会误导。

**没当场修、留给 M5 的**：篇幅、术语锚点、簇数一致性。这三条都能机械判定，正好是 `brief_lint` 的第一批规则。

**卡在哪**

模型不是不听话，是**规则写在文档里不等于会被执行**。它老老实实读了 SKILL.md 和 4 份 references，Step 0–7 全走到了，但「合并成簇」这一步它以为自己做完了——因为它在对话里描述过合并。写成 "调 view=clusters 核对" 这种**有返回值可看**的动作，比写 "注意合并" 有用得多。

**原理点**

技能文档写给的是"有判断力的执行者"，而模型会跳过没有外部反馈的步骤。所以凡是"模型说它做了"的步骤，都要想办法给它一个能看见的证据——簇数、字数、违规条数。这就是 M5 存在的理由：把"应该检查"变成"调一次工具看返回值"。

## M5 自检工具

**Agent 做了什么**

| 文件 | 作用 |
|---|---|
| `core/lint.py` | 11 条机械规则（L1–L11），纯函数，可单测 |
| `mcp/brief_store.py` | 新增 `brief_lint`（单独校验）与 `publish_brief`（自检 + 落盘 + 记账，一次调用） |
| `tests/test_lint.py` | 14 条测试，含 2 条「不能误报」的反例 |
| `scripts/snapshot.py` | 测试状态快照：save / clear / restore / list |
| `core/store.py` | 修 `_connect`（连接不关闭导致文件锁）；`add_evidence` 加 `reset` 参数 |

**11 条规则里，最重要的是这三条**

| 规则 | 查什么 | 为什么它比模型自查可靠 |
|---|---|---|
| L3 | 全文字数在配额内 | M4 超配额 46%，模型自己没意识到 |
| L5 | 学习者档每条事件有术语锚点 | M4 缺 7/8 |
| L6 | 头部「事件簇 N」= 库里**入选**的簇数 | M4 把入选条数当簇数；M5 第三次跑把「全部候选簇」当簇数 |

其余：L1 档位行、L2 主线数、L4 事件条数、L7 四要素、L8 事实段措辞、L9 链接可溯源、L10 思考题结构、L11 簇数配额。

**三次跑，两个发现**

| 次序 | 结果 | 发现 |
|---|---|---|
| 首期（无 lint） | 2930 字、术语 1/8、簇数对不上 | 三个缺陷，见 M4 |
| 第二次（加了 lint 但模型没调） | **没写文件、没跑自检、把 7800 字报告打在对话里** | 自检工具只有在被调用时才存在。模型跳步时它等于不存在 |
| 第三次（改成 `publish_brief` 一次调用） | 1940 字、术语 7/7、已落盘、已记账 | 收尾动作必须绑成「一个有返回值的工具」 |

**`publish_brief` 的由来**

第二次跑失败后，问题不是"lint 不灵"，是**三步文件操作模型会漏**。所以把「lint → 写文件 → 追加账本」压成一个工具：

- 不通过 → **不写任何文件**，返回 violations；
- 通过 → 写文件 + 记账，返回 `published=true`；
- 只有拿到 true 才算交付。

这不是提示词能解决的。提示词说"必须写文件"，模型会回一句"已写入"；工具返回 `published=false`，它只能去改。

**对比（同一窗口、同一档位，都在清空状态后跑）**

| 指标 | 首期 | 第三期 |
|---|---|---|
| 正文字数 | 2930（超 46%） | 1940（配额内） |
| 术语锚点 | 1/8 | 7/7 |
| 是否落盘 | 是 | 是（经 `publish_brief`） |
| lint | 不存在 | 调 4 次，最后一次通过 |
| 最终回复长度 | 523 字 | 241 字（摘要 + 路径） |

**遗留一个问题**

第三期在当时的规则下 pass，但我在跑完后才发现 L6 的语义错：它把「全部候选簇 11 个」写成了本期事件簇。收紧 L6（只比入选簇）并新增 L11（簇数配额）后，这份报告会报 2 条 error（11 ≠ 7，且 11 > 8）。

不重跑。理由：这两条规则是跑完之后才发现的，如实记录比补一份好看的报告有价值——**检查清单是迭代出来的，不是设计出来的**。

**卡在哪**

1. **L8 误报。** 第一版用 `(将|即将|意味着)` 匹配，把「DeepSeek 将框架开源」这类"将=把"的完成句判成预测。中文里「将」有两个意思，只能抓固定搭配（即将/将会/将于/将在/将推出…）。误报多了，这套检查会被当噪音跳过，等于不存在。
2. **`sqlite3.connect` 的 `with` 不关闭连接。** 测试跑 13 个错误，全是临时目录删不掉——`with conn:` 只提交事务，句柄还在。改成 `contextmanager` 显式 close。这个 bug 在生产里表现为文件锁，备份脚本会失败。
3. **两轮不够。** 第三期 `publish_brief` 调了 4 次（首次 + 3 轮修）才通过。技能写"最多两轮"偏紧，但放宽会让模型在 lint 上耗时间，暂时保留两轮、允许它自己多试。

**原理点**

自检的价值不在于"查出错误"，在于**给出一个模型无法自欺的返回值**。`published=false` 加三条 violations，模型只能改；"请检查字数"这类要求，模型会回答"已检查"。

同理，测试隔离不是洁癖：证据库按 period 累积、账本按日期追加，不清状态重跑，你测的是"上一轮 + 这一轮"，不是这一轮。

### 目录布局


迁移脚本把单档案时代的数据整体搬进 `default`：证据 12 条、会话 9 条、账本 1 份、简报 2 份，
搬完逐项核对过条数。**三样必须一起搬**（会话 / 检查点 / 证据库）：会话与检查点靠
`thread_id` 关联，分居两地会表现为"点开历史会话，模型说不知道之前聊过什么"。

### 三个设计决定

| 决定 | 理由 |
|---|---|
| 记忆分两层：`memory/AGENTS.md` 全局口径 + `memory/archives/<id>.md` 档案补充 | 全局那份装的是产品口径（日期不可信、authority 不等于一手）。每档案复制一份，改一条要改 N 份，必然有漏——交接文档里"两份技能副本改错那份"就是这么坏的 |
| 简报进 `outputs/briefs/<id>/`，账本进 `docs/ledger/<id>/` | 必须留在 Agent 的放行区里。放进 `runtime/` 它读不到自己的记忆，也写不了账本 |
| 写入权限按档案收窄，不再放行整个 `/outputs/**` | 档案互不可见是功能前提。放行全局等于让 A 档案的报告能覆盖 B 的 |

### 四个实测出来的问题

**1. 删档案会静默失败（本机必现）。** 第一版用
`shutil.rmtree(path, ignore_errors=True)`，结果界面显示删除成功、目录还在。
原因是当前档案的 `checkpoints.db` 正被 Agent 打开，Windows 上删不掉，而
`ignore_errors=True` 把这个失败吞了。现在：删除前先 `close()` 运行时（界面里点删除时做），
`archive.delete()` 内部重试并在真的删不掉时**抛错**，让用户看到原因，而不是留一个幽灵档案。

**2. MCP 子进程不是常驻的。** 这一条纠正了我自己的假设。用 PowerShell 数进程时发现
`brief_store` 一个都没有——`langchain-mcp-adapters` 的 stdio 客户端是**每次工具调用
起一次进程**。所以"每个档案占一个后台进程"这件事根本不存在，切档案要重建 Agent，
代价只是重连一次工具清单 + 一个检查点连接。原计划担心的"独占后台进程"不成立。

**3. 测试会污染真实目录。** 试跑时 `runtime/archives/` 里冒出四个幽灵档案，撞到 5 个上限，
后续所有 `create()` 全部失败，而报错信息却指向"档案数不对"。根因是本机运行环境的
删除保护把 `rmtree` 改成了"移入回收站"，失败时目录会延迟恢复。解决方式不是绕过它，
而是**让测试不碰真实目录**：`test_archive.py` 在 `setUpClass` 里把 `config.ARCHIVES_DIR`
等四个路径指到临时目录，13 条用例从 23 秒降到 3 秒，且不再留残留。
断言也改了：不再断言"总数等于 2"，而是断言"新增了哪一个"——上一次就是这条断言
在目录有残留时把人引向了错的方向。

**4. 空简报目录会堆积。** `create()` 会建 `outputs/briefs/<id>/`，档案删了简报留着是设计，
但没产出过的空目录留着就成了噪音。现在删除时如果没有 `.md` 就把空目录一起清掉。

### 顺带改的技能与提示词

档案 id 是运行时才知道的，技能文档里只能写 `<档案>` 占位，具体值由
`build_system_prompt()` 追加在系统提示词末尾（简报目录、账本、档位偏好三条）。
技能里同步改了四处路径表述，并加一句「**不要回检别的档案的账本**」——
混读会把两个读者的判断口径搅在一起，而这种错误在报告里看不出来。

```bash
./.venv/Scripts/python.exe -m unittest discover -s tests -v     # 43 条
```

## 修复：运行中切页面丢记录（2026-10-25，约 25 分钟）

**现象**：新档案里跑一期，运行中切到「证据」页，再切回来，对话页只剩提问——助手回复与执行轨迹都没了。重载也不恢复。而简报本身正常落盘了。

**根因**：流式循环写在页面函数里。

```
page_chat()                                   ← 页面函数
  history.save_message(user)                  ← 执行了
  for ev in iter_events(...): 渲染            ← 切页面 → Streamlit 中断整个脚本 → 循环被丢弃
  history.save_message(assistant, steps)      ← 永远不执行
```

而 Agent 跑在 `AgentRuntime` 自己的事件循环线程上，页面死不死都不影响它——所以简报照常写完。**运行成功、记录丢失**是这两个独立生命周期错位的结果。

**数据侧的证据**（不是推测）：`c8068f81/sessions.db` 里那条会话只有 `user` 一条、59 字；而 `checkpoints.db` 的 `writes` 表里 `channel='messages'` 有 82 条写入，最后一条是 1235 字的 AI 消息。消息一直在，只是没人把它写进会话库。

### 改法：把运行的生命周期从页面里挪出去

新增 `agent/runner.py`：

```
Run.start()  →  runtime.submit(consume())   ← 在 Agent 的事件循环上跑
                  逐事件累积到 run.steps / run.text / run.answer
                  结束时**自己**写会话记录（成功、报错、无输出都写一条）
                  finally: done.set()
```

页面只负责"看"：`_render_running(run)` 读 `run.steps` / `run.text` 渲染，跑完 `st.rerun()` 回到历史消息的渲染路径。切页面、关标签页都不再影响记录——**记录不能挂在渲染路径上**。

三个配套改动：

1. **报错也落一条**（`出错了：…`）。空白会让人以为记录又丢了，而报错本身是信息。
2. **运行中禁用会腰斩它的操作**：切档案会 close 掉运行时、连带停掉事件循环，所以 `runner.busy()` 为真时，切档案、换会话、删除、新建一律灰掉，输入框也禁用，侧栏给一行「⏳ 有任务在跑」。
3. **`scripts/recover_transcript.py`**：从检查点把丢失的记录搬回会话库，用于已经发生过的情况，也用于以后进程被杀的场景。

### 恢复脚本为什么从 `writes` 取

`checkpoints.channel_values` 里**没有** `messages`——deepagents 的 state 把它标成不随检查点落盘（只有 `todos` / `memory_contents` / `__pregel_tasks` 这些）。消息只以"每步写入"的形式留在 `writes` 表。所以脚本是两级取数：先试 `channel_values`（常规图适用），取不到就按 `rowid` 顺序拼 `writes` 里的 `messages` 写入。

写库前先读**临时副本**：`SqliteSaver` 初始化会建表，直接开只读连接会失败；改原库不该是恢复脚本的副作用。

实际恢复结果：那段会话补回**正文 1235 字 + 工具步骤 112 条**。

### 验证

```bash
./.venv/Scripts/python.exe -m unittest tests.test_runner -v      # 7 条，离线
./.venv/Scripts/python.exe scripts/recover_transcript.py --list --all
```

| 验收项 | 结果 |
|---|---|
| 无人消费也落库 | 启动后完全不读进度，等到 `done` → 会话库有完整 assistant 消息 |
| 真实运行 | 临时档案跑一轮（3.0 秒、1 次工具），两条消息都在，运行后删档案干净 |
| 报错路径 | 异常时写入「出错了：connection reset」，不是空白 |
| 只有 token 无 answer | 用累积 token 当正文 |
| `busy()` | 运行中为真，结束为假；按档案判断也正确 |
| 全套回归 | **50 条通过** |

**这轮暴露的是一条通用规律**：只要"记录"写在"渲染"之后，任何中断都会丢记录。之前 `publish_brief` 解决的是"模型以为做了"，这次解决的是"界面以为写了"——同样是没有返回值就没人知道它没发生。

## S5 模型选项与环境变量页（2026-10-25，约 35 分钟）

### 三个决定，都是"少给一点自由"

| 决定 | 理由 |
|---|---|
| 模型**写死三个**（`qwen3.7-plus` / `qwen3.8-max` / `deepseek-flash`），不接受任意模型名 | 能不能跑完一期取决于工具调用格式的稳定性，不是参数规模。名字写错时，报错会出现在第 40 次工具调用上——那时十分钟和几毛钱已经花掉。写死三个、每个都能实测，比"支持任意模型"诚实 |
| **接口地址写死**在 `core/settings.py`，不再读 `LLM_BASE_URL` | 同一家的 key 只对应一个网关。让用户配 base_url 只会多一个"填错了但看起来能连"的失败模式——M1 那次 403 `Workspace endpoint access denied` 就是这个坑，现在从根上消失了 |
| 密钥**永不回显**：输入框留空、placeholder 显示 `sk-…a1b2`、保存只提交改过的键 | 页面截图、录屏、共享屏幕都可能把密钥带出去。留空即不改，也让"我只想改配额"这种操作不会误清密钥 |

### 连通性探针：为什么"键在不在"不够

`model_ready()` 只查环境变量有没有值。但**填错的键长度、前缀全都像**——实测就是这个情况：

```
qwen3.7-plus     FAIL(401)  Incorrect API key provided
qwen3.8-max      FAIL(401)  Incorrect API key provided
deepseek-flash   OK
```

`.env` 里 `DASHSCOPE_API_KEY` 与 `DEEPSEEK_API_KEY` 是同一个值（35 位、哈希相同）。也就是说百炼那一项被填成了 DeepSeek 的 key，两个 Qwen 选项必然 401。这种错误只有真发一次请求才暴露，所以设置页做了「测试连通」按钮，走一次 `max_tokens=16` 的对话。

### `.env` 改写为什么不能整份重写

`update_env()` 逐行比对、只替换目标键，保留注释与顺序。`.env` 里的注释是唯一记录"这个键为什么存在"的地方（比如英文查询不降级的原因），整份重写会把这些说明冲掉。

`reload_env()` 必须 `override=True`：`load_dotenv` 默认不覆盖已有环境变量，不加这个参数就是"界面显示保存成功、进程里还是旧值"——最难查的一类问题。为此给 `config` 加了 `refresh()`，重读 `SEARCH_PROVIDER` / `SEARCH_QUOTA` 这些会在运行中变化的常量。

### 改配置即重建 Agent

模型与密钥都握在 `AgentRuntime` 里的 `ChatOpenAI` 实例上，改环境变量不会让它跟着变。所以保存后 `_drop_runtime()` 关掉运行时，下一轮 rerun 按新配置重建。有任务在跑时整页禁用——重建会关掉正在跑的运行时（与"运行中禁止切档案"同一条道理）。

### 验证

```bash
./.venv/Scripts/python.exe -m unittest tests.test_settings -v      # 13 条，离线
./.venv/Scripts/python.exe -c "from core import settings; print(settings.probe())"
```

| 验收项 | 结果 |
|---|---|
| 设置页渲染 | 5 个页面全部无异常（AppTest） |
| 密钥不回显 | 断言页面所有元素（含 placeholder）都不含完整密钥，且含 `…` 脱敏提示 |
| `.env` 改写 | 注释与其它键保留；重复保存同一值返回空改动；新键追加到末尾 |
| 生效 | `reload_env()` 后 `config.SEARCH_QUOTA` / `SEARCH_PROVIDER` 跟着变 |
| 模型清单 | 未知模型名被拒；`settings.json` 写坏时退回 `LLM_MODEL` 或默认值 |
| 探针 | deepseek-flash 通；两个 Qwen 401（`.env` 里百炼项是 DeepSeek 的 key） |
| 全套回归 | **65 条通过** |

### 一条没做完的

D4 要求"三个模型都能跑完整期"。现在 **`deepseek-flash` 有整期记录**（10-25 那期 82 条消息、112 步工具调用就是它跑的），两个 Qwen **卡在密钥上**：`.env` 里的百炼 key 是 DeepSeek 的，401。补齐真 key 后，流程是「设置页填 key → 测试连通 → 切换模型 → 跑一期」。

### 整期验证：三个模型，同一句提问，同一窗口

条件完全一致：`做一份最近一周的 AI 行业简报`、窗口 2026-10-18..10-25、学习者 × 标准、各自独立档案。

| 模型 | 用时 | 工具 | 证据 | 类型 | 簇（多信源） | 一手 | 正文 | 自检 | 交付 |
|---|---|---|---|---|---|---|---|---|---|
| `qwen3.7-plus` | 13:02 | 49 | 16 | 6/6 | 12（2） | 0 | 1952 字 | 通过 | **需补救 1 次** |
| `qwen3.8-max` | >38:00 中止 | 46 | 52 | 6/6 | 18（13） | 2（4%） | — | — | **未交付** |
| `deepseek-flash` | 4:32 | 59 | 38 | 6/6 | 7（6） | 1（3%） | 1997 字 | 通过 | 一次通过 |

三条结论，都不是"哪个模型更聪明"：

1. **qwen3.7-plus 第一遍不交付。** 45 次工具调用、3784 字报告全写在对话里，`publish_brief` 一次没调。加上补救后第二遍才落盘（1952 字，回到配额内）。**同一份技能，deepseek-flash 会调、它不调**——这是交付纪律的模型差异，不是能力差异。
2. **qwen3.8-max 跑不完。** 它把 52 条证据全判完、标了 32 条入选（配额是 6–8，超四倍），簇也合并得最狠（18 簇里 13 个多信源），然后卡在一次模型调用上：数据库与日志双双静止，38 分钟没有任何新事件。这是"过度采集把上下文撑大 → 单次调用超时/重试"的典型形态，已中止。
3. **deepseek-flash 最快也最守规矩**，4 分 32 秒、一次交付，簇合并最干净（7 簇里 6 个多信源）。但它的正文贴着 1997 字上限，几乎顶格——换更长的窗口容易越界。

### 由此补的两处结构

这两处都不是"改模型"，是补上模型差异的兜底：

**A. 交付补救（`agent/runner.py`）**

交付是可检出的：有没有 `publish_brief` 调用、返回里 `published` 是否为真。所以不必指望每个模型都守规矩——检出没交付且正文超过 400 字时，自动追加一轮"把刚才的正文交给 `publish_brief`"，**只补一次**。补救后仍没交付，退回原稿照实保存，不伪造成功。

判据用"有没有交付"，不用"回答有多长"：模型可能只回一句"已交付：路径"，那是对的；也可能回"无需交付"，那就退回原稿。用长度判断会把前者误判成后者——这一条是被测试打出来的。

**B. 运行墙钟上限（默认 25 分钟）**

qwen3.8-max 那次卡死，界面会永远停在"思考中"，用户分不清是慢还是死了。现在 `Run` 用 `asyncio.timeout` 包住整个流程，超时即中止、把原因写进会话记录（"检索与判定结果都还在证据库里，可以下期接着用"），界面同时显示已运行时长 `mm:ss`。

### 验证

| 项 | 结果 |
|---|---|
| 期刊记录模型 | `period.model` 列，老库自动 `ALTER TABLE` 补列；徽章显示"模型"；换模型重跑同期会更新为最新 |
| 交付补救 | 6 条测试：补救生效 / 已交付不吵 / 短回答不吵 / 拒绝时退回原稿 / 可关掉 / 补救轮落库 |
| 超时 | 1 条测试：卡死 30 秒的流在 0.4 秒超时后中止并落库 |
| 全套回归 | **73 条通过** |

## S6 执行过程折叠栏（2026-10-27，不计工时）

作业已提交，此后只记构建过程，不再追踪时间规划。

**现象**（使用者报的两条，外加一条未复现）

1. 运行中，人点开「执行过程」想看看在干什么，展开后**很快被自动收回**，反复点也看不住。
2. 执行过程很长，展开后想收起，得把滚轮拖回顶部才能点到那个三角。
3. **未复现，先记档**：交付阶段出现过一次「抛出思维过程、聊天框不再更新」，而简报正常落盘。那次会话与档案在清理测试数据时被删，无法回溯。下次复现时先看 `runtime/*.log` 与检查点 `writes` 的时间戳是否静止。

### 根因：`st.status.update()` 每次刷新都在清 expanded

不是观感问题，是 API 语义。`StatusContainer.update()` 的实现：

```python
if expanded is not None:
    msg.delta.add_block.expandable.expanded = expanded
else:
    msg.delta.add_block.expandable.ClearField("expanded")   # ← 隐性折叠
```

`_render_running` 的进度循环每 0.4 秒调一次 `status.update(label=...)`，`expanded` 传的是默认 None——
前端在同一个 delta 路径上收到一个"expanded 字段不存在"的 block，语义就是折叠。
**每 0.4 秒把用户刚点开的栏打回去一次**，所以表现为"快速回弹"。

第二条现象有独立成因：无状态 `st.expander` 的展开状态活在浏览器里，脚本一重跑就按
`expanded=` 初值重建。任何交互（换会话、点按钮）都会把已展开的全部收回。

### 改法：换成有状态的折叠栏，并且不让标题承载进度

```python
def trace_box(key, default_open=False):
    st.session_state.setdefault(key, default_open)
    return st.expander("执行过程", expanded=False, key=key, on_change="rerun")
```

三处不那么直观、但缺一条就退回旧行为的约束：

| 约束 | 为什么 |
|---|---|
| 不用 `st.status` | `update()` 会清 expanded，见上。进度改用栏外的一行 `st.empty()`，折叠后仍看得见 |
| 必须 `key` + `on_change="rerun"` | 只有注册成控件，展开状态才在重跑之间存活，Python 侧也才能改写它（`_new_session_state` 优先于控件状态） |

第三条是踩出来的：第一版写的是 `f"执行过程（{calls} 次工具调用）"`，测试里"重跑后仍展开"一条直接挂。
计数只能放进栏内当 caption。

**侧栏「⏬ 全部折叠执行过程」**：按 `_trace-` 前缀枚举 session_state 里的键，不维护清单。
位置有硬约束——必须留在 `nav.run()` 之前：侧栏先于页面渲染，改写当场对下面的页面生效，不需要再 `st.rerun()`；

按键的两处细节：历史消息用消息 id（`load_messages` 新增返回 `id`，消息只增不改，id 稳定），

新运行开始前再把旧的 live 键清掉。

## S7 运行被步数上限掐断，且原因被吞掉（2026-10-27，不计工时）

**现象**：测试1（`78fd0dda`）跑学习者×深度，9 分钟后自己停了。执行过程里最后一句是「只差 76 字，做一次精准修剪后交付」，然后什么都没有——没有简报、没有报错、没有说明。用户的原话是「agent 自行终止（此前反复说要压缩篇幅）」。

### 证据链

不看现象看数据，四步定位：

| 查什么 | 结果 |
|---|---|
| 会话记录里的步骤 | 64 次工具调用，`publish_brief` 被调用 **8 次**，全部 `published=false` |
| 8 次的自检差异 | 正文 5476 → 4576 → 4275 → 4328 → 4263 → 4076 → 4049 → **4016**（深度档上限 4000） |
| 检查点 `metadata.step` | 主图检查点最大 `step=160`，正好等于 `RECURSION_LIMIT` |
| 时间线 | 18:25 建档 → 18:34 落库，约 9 分钟，**不是** 25 分钟墙钟超时 |

结论：**LangGraph 抛 `GraphRecursionError`（160 步用尽）**，而这一次正文只差 16 字就过线。

### 三个缺陷，一个症状

**① 异常被正文吞掉（直接导致"没有说明"）**

```python
body = self.answer or self.text
if not body:
    body = f"出错了：{self.error}" if self.error else "（没有生成回答）"
```

这次的 `text` 是 64 次调用累积的过程旁白，非空——于是 `body` 拿到了旁白，"有正文就不写错误"这条分支把 `GraphRecursionError` 吃掉了。用户看到的是话说到一半停住。**异常不是装饰，是这一轮唯一的结论。**

改法：错误无条件追加到正文尾部（`---\n**运行异常中止：…**`），并把 `Recursion limit` 翻成人话（「步数用尽（上限 300 步，一次工具调用约吃 2 步）」+ 下一步怎么办）。

**② 步数上限对小（`RECURSION_LIMIT = 160`）**

160 是课堂 demo 的值。实测这一期：64 次工具调用 → 160 步，约 **2.5 步/次**（含模型节点、工具节点、规划中间件）。也就是说 160 步只够 64 次调用，而深度档正常就要 60–80 次。

改成 300（约 120 次调用）。声明清楚：它只防死循环，真正的兜底是 25 分钟墙钟。

**③ 交付没有止损，也没有留稿（"没有简报"的直接原因）**

`publish_brief` 的闸门只认"通过"，没通过就当没发生——正文只活在这轮上下文里，进程一停就没了。8 次尝试、每次都重写全文，没有任何机制说"够了"。

两处收紧：

- `PUBLISH_MAX_TRIES = 12`：同一次运行里连续 12 次不过就中止（`aclosing` 主动关掉事件流，让图停在检查点上），不再空转到步数上限。
- 中止时把**最后一版正文**写成 `outputs/briefs/<档案>/_未交付-<时间>.md`。下划线开头，往期简报页按前缀过滤，草稿不会混进"已交付"。

**④ 顺手改了 L3 的报错措辞**

原来只说「正文 4016 字，深度档配额 2500–4000 字，需压缩」，差额要模型自己减。它确实在减，但每次只肯削二三百字。改成直说「超上限 16 字——一次删够，不要每次只删几十字再提交」。

### 验证

| 验收项 | 结果 |
|---|---|
| 异常不被正文吞 | 先出旁白再抛异常 → 落库正文里**旁白和异常都在**，且含"步数用尽" |
| 止损 | 单轮喂 15 次失败 → 第 12 次中止，`publish_tries=12`，不再消耗 |
| 留稿 | 草稿目录恰好 1 个文件，内容是**最后一次**提交的那版 |
| 全套回归 | **80 条通过**（78 → 80） |

第一版这两条测试都写错了，两个错都值得记：一个忘了 `return gen()`（异步生成器没返回，`aclosing(None)` 直接炸）；另一个把 12 次失败铺成 12 轮事件流——而 `_work` 最多只跑两轮（正轮 + 一次补救），根本走不到 12 次。

### 那期产物救回来了

会话记录的 `steps` 里存着 `publish_brief` 的完整参数，最后一版正文（4016 字）和账本条目（1717 字）都还在。已存成草稿：

```
outputs/briefs/78fd0dda/_未交付-2026-10-27-学习者深度.md
outputs/briefs/78fd0dda/_未交付-2026-10-27-账本条目.md
```

自检只剩一条 L3（超 16 字），其余（3 条主线、10 条事件、6/6 类型覆盖、簇数一致）全过。**没有替它删那 16 字**——删哪 16 字是编辑判断，不该由工具代做。

### 没修的：两处结构性浪费

这次 64 次调用里，`evidence_update` 占 18 次（44 条候选按"同一组字段"分组写回，每组 2–3 条）、`publish_brief` 占 8 次（每次重写全文）。两块加起来约 50 步，是步数消耗的主体。

- `evidence_update(ids, fields)` 的签名决定了它天然要分组调用。改成按条带字段的批量接口（`items: [{ids, fields}]`）能省 15 次左右。
- `publish_brief(markdown=全文)` 决定了每次重试都要重出 4000 字。让它在失败时返回一个可改的草稿路径、下次只提交路径，能省的是 token 而不只是步数。

两条都要改 MCP 工具契约和技能里的调用约定，不是调参。**先记着，等下一次真的再撞墙再动。**

## S8 思考题退路引用越界（2026-10-27，不计工时）

**现象**：使用者发现某一期只有 4 条思考题，第 3 条的退路却写「不知道跟自己有什么关系 → 见第 5 条」。

**先查是不是偶发**：把 6 份简报的思考节逐份核了一遍。

| 简报 | 档位 | 条数 | 退路引用 | 结果 |
|---|---|---|---|---|
| `c8068f81` 业内深度 | 业内 | 5 | 第 4 / 第 5 条 | 正确 |
| `17419d11` 学习者标准 | 学习者 | 4 | 标签 + 不要求作答 | 正确 |
| `9bee390c` 学习者标准 | 学习者 | 4 | 见下第 4 条（数算大算小） | 标签与原因错配 |
| `_baseline` 学习者标准 | 学习者 | 4 | 第 4 条 + **第 5 条** | 越界 |
| `default` 学习者深度 | 学习者 | 4 | 第 4 条 + **第 5 条** | 越界 |

五份学习者/业内简报里，**只有天然等于 5 条的业内那份是对的**。这不是偶发，是规范的必然结果。

### 三层原因

**① 模板把业内档的序号写死了。** `assets/report-skeleton.md` 第七节只有一份模板：

```
3. **反证型**　<问题>
> …不知道数算大算小 → 见下第 4 条；不知道跟自己有什么关系 → 见下第 5 条…
4. **学习者档**　…
5. **非专业档**　…
```

4 和 5 是「学习者档」「非专业档」，这份布局**只在业内档成立**（3 主 + 学习者 1 + 非专业 1 = 5）。
学习者档没有「学习者档」那道题，只有 4 条，照抄就写出不存在的第 5 条。

**② `inquiry.md` 6.3 少一种情况。** 退路表默认「主档位高于退路指向的那一档」：

> 不知道行业里这个数算大算小 → 学习者档

当**主档位本身就是学习者**时，这条退路指向读者自己，没有对应题可给。规范没写这种情况，
模型每次都在自己打补丁——17419d11 写成「缺的是定位坐标，本期不要求作答」（对），
`9bee390c` 写成「见下第 4 条」（把非专业档当成了坐标档，错）。

**③ 自检里没有这条。** L10 只查三种题型是否齐、反证型是否唯一；`quality.md` 第 15 条同理。
「见第 N 条」的 N 存不存在，是一个完全有客观答案的问题，却被漏在规则之外。

### 改法

| 位置 | 改动 |
|---|---|
| `report-skeleton.md` 第七节 | 模板按档位拆成两份（学习者 4 条 / 业内 5 条），退路**用标签引用**，并加一张「主档位 → 三句退路」的对照表 |
| `inquiry.md` 6.3 | 补「主档位 = 退路档位时怎么办」：学习者档这条退路写「本期不要求作答」；非专业档不写这条退路 |
| `quality.md` 第 15 条 | 加「退路引用用标签、且指向的条目确实存在」 |
| `SKILL.md` Step 6 | 同上，一句话；版本升 `0.7.1-app` |
| `core/lint.py` | 新增 **L12**：查「见第 N 条」与「见「XX档」那条」两种引用，指向不存在即 error |

L12 的存在理由是这次最值得记的一条：**规范写得再清楚，模型也可能照抄错模板；能不能自动发现，
取决于这个错误有没有客观答案。** 这一条比「提示词再强调一遍」可靠得多。

### 验证

```

```

对截图那一期跑新规则，L12 命中。另加 3 条测试：数字越界、标签指向不存在的档、以及**引用存在时不报**
（误报多了这套检查会被当噪音跳过）。**全套 83 条通过**（80 → 83）。

### 没动的

两份已交付的简报带着这个错（`_baseline` 是基线件、`default` 深度是这次看到的那期）。不重跑：
重跑要花一期额度，换来的只是两行措辞。记录在案即可。

技能版本 `0.7.0-app → 0.7.1-app`。这条属 **B 类（应回合主版本）**——上游 v0.6.1 同样有这个问题，
本项目只是第一次把它暴露出来。改动清单 A10/B4 记在 `docs/ai-brief改动记录.md`。

## S9 虚拟环境该不该进仓库（2026-10-27，不计工时）

**问题**：agent 启动依赖 `.venv`，而 `.venv` 不追踪——要不要把它传上去？

**结论：不传。** 三条理由，都不是"习惯"：

1. **换台机器跑不了。** `.venv/pyvenv.cfg` 里写死本机路径：
   `home = C:\Users\...\python\versions\3.13.12`、`command = ... -m venv C:\Users\...\20261027\.venv`。
   换个目录、换台机器，这份环境就是废的。
2. **体积。** 468 MB / 25 257 个文件。整个 `.git` 才 253 MB——传一次，仓库体积翻三倍，
   而且每次改依赖都新增一整份历史的二进制，删不掉。
3. **它不是源码，是生成物。** 传 venv 等于传编译产物；仓库该存的是生成它的配方。

**但问题背后的需求成立**：别人拿到仓库得能跑起来。查下来，这一半确实是缺的——

- `requirements.txt` 用的是 `>=`：`streamlit>=1.40.0`、`deepagents>=0.7.24`。
  而这个项目已经踩过版本敏感的坑（`create_deep_agent` 的参数在 0.7.x 内变过；
  `width="stretch"`、`expander(on_change="rerun")` 都是较新的 API）。半年后
  `pip install -r` 装出来的东西可能起不来，且报错会落在很难定位的地方。
- 没有一条命令能把环境建好。README 写的是四行手工命令，还要记得 `copy .env.example`。

### 补的三样

| 文件 | 作用 |
|---|---|
| `requirements.txt` | 8 个**直接依赖，全部 `==` 锁死**，附一行说明为什么锁 |
| `requirements.lock.txt` | 完整依赖树 96 个包的 `pip freeze` 快照，用于精确复现 |
| `scripts/bootstrap.py` | 一条命令：建 venv → 按 lock 装 → 复制 `.env`；另有 `--check`（只体检）、`--loose`（按 requirements.txt）、`--index`（换镜像） |

README 的安装一节整段重写，并把「为什么不传 .venv」「为什么锁版本」两条写进引用块——
理由不写出来，下一个人还会问同样的问题。

### 顺带发现的一个隐患

`mcp_servers.json` 里写的是 `"command": "python"`（裸命令，走 PATH）。它靠 `builder.py`
在执行时换成 `sys.executable` 才安全——**所以必须用 `.venv` 的解释器启动 streamlit**，
否则 MCP 子进程会用系统 Python，缺 `mcp` 包，表现为"工具清单是空的"。
这条以前只在代码注释里，现在写进了 README 的启动命令和 FAQ。

### 验证

```bash
python scripts/bootstrap.py --check
Python  3.13.14  (符合)  期望 3.12/3.13
虚拟环境  存在  .venv
依赖  96 个全部对上（requirements.lock.txt）
密钥  .env 存在，已填 2/2
```

| 验收项 | 结果 |
|---|---|
| 本机（环境完整） | 退出码 0，96 个包全部对上 |
| 空目录（无 venv） | 退出码 1，明确指向"运行本脚本生成" |
| 声明与快照一致 | 新增测试：`requirements.txt` 的每个 pin 必须在 lock 里同版本 |
| 不许留范围依赖 | 新增测试：出现 `>=` 或空版本即失败 |
| 全套回归 | **86 条通过**（83 → 86） |

第三条测试值得说一下：**两份 requirements 漂移，本地永远发现不了**，因为本地早就有 venv 了。
这种"只有别人克隆时才炸"的错，只能靠断言守。

S3 是唯一明显超出身位的一段：45 分钟里有一半花在排查"为什么删不掉"和"为什么进程数是 0"，
这两件事都不在计划里，但都得查清才能确定实现是对的。

## 答辩备用：三句话能讲清的增量

1. **检索**：demo5 没有任何联网能力（`fetch` 依赖未安装的 `uvx`，子代理拿到的是课程数据库工具）。本项目补了检索与抓正文，并按技能的「事件类型」而不是关键词组织检索。
2. **证据外置**：技能要求「同源只算一票、单信源最多 2 簇」。这是跨条目统计，模型在 40 条候选里数不过来。所以做了 SQLite 证据库，判定与统计走工具，不走模型记忆。
3. **自检可执行**：`quality.md` 的 24 条自检有 18 条有客观答案，做成了 `brief_lint`。其中最有价值的一条是「正文里每个链接必须能在证据库里查到」——把"禁止编造 URL"从道德要求变成不可能。
