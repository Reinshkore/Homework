## 解读 示例3.4.py 相对 qwen2.py 的新增能力（只解读，未改任何代码）

用户本次要求：不修改代码，只想理解示例3.4 与 qwen2.py 的差异，准备手打代码。

### 示例3.4.py 真正新增的 4 项
1. **CustomStreamer 自定义流式器**（queue + Thread 生产者/消费者）
   - 实现 transformers 的 streamer 协议：`put(value)` / `end()`
   - 逐 token 解码后写入 `queue.Queue`，主线程 `while True: queue.get(timeout=0.1)` 读取
2. **`enable_thinking=False`** —— Qwen3 特有的 chat template 参数，渲染出空 think 块，抑制思考链
3. **侧边栏可调参数** —— `st.slider` 控制 max_tokens(100-2048) 与 temperature(0.1-2.0)
4. **性能指标埋点** —— `first_token_time` / `get_first_token_latency()`

### 实测得出的关键事实（重要，值得记住）
- `generate(streamer=...)` 的**第一次 `put` 收到的不是新 token，而是整段 prompt**
  （实测 shape `(1, 18)` = prompt 全部 18 个 token；之后才是 `(1,)` 单 token）
  → 自定义 streamer 若不做 skip_prompt，会把用户提问回显出来。
- `TextIteratorStreamer(skip_prompt=True)` 输出与一次性 decode **完全一致**（实测 ==）。
- 示例3.4 的自定义 streamer + `<think>` 清理逻辑，产出也与一次性 decode **完全一致**（实测 ==），
  它能挡住 prompt 回显纯属"碰巧"——因为 `enable_thinking=False` 渲染出的 prompt 末尾正好是
  `<think>\n\n</think>\n\n`，`split('</think>')[-1]` 把前半段吃掉了。
- `get_first_token_latency()` 实测返回 ~2.8ms，因为 `first_token_time` 是在 prompt 那次 put 时记录的
  ——测的是 prompt 入队时刻，不是首个生成 token。且该函数定义了从未被调用（死代码）。
- `platform` 已 import 但从未使用（死导入）。
- think 清理的两个分支代码完全相同（`if '<think>'` / `elif '</think>'` 都执行 `split('</think>')[-1]`），冗余。
- 前缀清理列表 `['User:', 'Assistant:']` 是无效的：实际渲染文本里是 `user\n` / `assistant\n`，
  冒号形式根本不会出现，这段代码永不命中。
- **线程异常 → 死循环**：若 `generate_response_stream` 抛异常，`end()` 不会被调用，
  queue 永远拿不到 `None`，主线程 `while True` 会一直 `continue` 空转，界面卡死。

### 示例3.4.py 没有修的问题（qwen2.py 已修）
- 多轮历史仍只用单条消息 `messages=[{"role":"user","content":prompt}]` → 多轮仍然失效
- 路径仍是 `../models/Qwen3-0.6B`（与用户实际路径不符）
- 无离线环境变量、无 `model.eval()`、无 dtype 指定、无超长输入截断保护
- 助手消息仍在生成完成后才写入 session_state（丢输入风险仍在）

### 一句话总结
示例3.4 加的是「控制与观测」能力（可调参数、思考链开关、自定义流式、指标埋点），
qwen2.py 加的是「对话正确性」能力（多轮历史、真流式、截断保护、丢输入修复）。
两条路线互补，不是替代关系。

### 讲解时必须打通的三个「为什么」（这是用户之前听不懂的根因）
1. **为什么不能用普通 list 传数据** → append/pop 不是原子操作，会数据错乱；
   Queue 内部自带锁 + FIFO 保证顺序。
2. **为什么必须用 Queue 把数据传回主线程** → Streamlit 的界面操作**只能在主脚本线程执行**，
   在子线程里直接调 placeholder.markdown() 不生效。这条约束才是 Thread+Queue 的根本动机。
3. **为什么 put 第一次收到的是整个 prompt** → 不是新 token。实测形状 (1,18) vs (1,)。
   示例代码能挡住 prompt 回显**纯属巧合**（enable_thinking=False 的模板末尾恰好是
   `<think>\n\n</think>\n\n`，被 split('</think>') 顺手切掉）。

### 其他实测结论
- 3.3 的「假流式」对中文完全失效：`str.split()` 按空白切，中文没有空格 → 只有一个元素。
- 3.4 的 `import platform`、`get_first_token_latency()` 是死代码；两个 think 清理分支完全重复。
- 3.5 的 `is_first_chunk` + `rfind("Assistant:")` 也是无效代码：实际渲染是小写 `assistant\n`，
  带冒号的大写形式永不出现。真正挡住 prompt 的仍是 `</think>` 清理。

### 记忆
三个版本的演进：3.3 同步假流式 → 3.4 真流式(Thread+Queue) → 3.5 真流式+多轮记忆。
3.5 的 history 构建：`messages[:-1]`（排除当前问题）+ `memory_rounds*2`（一轮=2条消息）+ min 防越界。
