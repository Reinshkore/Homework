## 第 0 章　先看清全局：三个文件是什么关系

这不是三个并列的例子，而是**同一个程序的三个进化版本**。

| 版本 | 新增能力 | 仍未解决 |
|---|---|---|
| 3.3 | 能加载本地模型、能对话、界面能显示历史 | 要等回答全部生成完才显示；界面卡住；没有多轮记忆 |
| 3.4 | **真流式**：边生成边显示 | 没有多轮记忆 |
| 3.5 | **多轮记忆**：模型能记住之前的对话 | 无（功能已完整） |

一句话概括这条演进线：

- **3.3 的问题**：`model.generate()` 是"阻塞"的，程序卡在那里等几十秒，界面一动不动。
- **3.4 的答案**：把生成放到**另一个线程**里跑，主线程同时"边收边显示"。
- **3.5 的答案**：把之前的对话也拼进去，一起喂给模型。

所以真正的新知识集中在 **3.4**。3.5 用的技术手段（线程、队列）和 3.4 完全一样，只是多拼了一段历史文本。

## 第 1 章　Python 语言层：先把语法读懂

这一章只讲三个文件里**实际出现过**的语法，不贪多。

### 1.1 模块与导入

```python
import streamlit as st
from threading import Thread
from queue import Queue, Empty
```

- `import X` = 把 X 这个"工具箱"拿进来用，用的时候写 `X.东西`。
- `import X as Y` = 拿进来，但改名叫 Y。所以 `streamlit.title` 可以简写成 `st.title`。
- `from X import A, B` = 只从工具箱里拿某几件工具，用的时候直接写 `A`。

三个文件里 `import` 的东西分别负责：

| 模块 | 负责什么 |
|---|---|
| `streamlit` | 网页界面（输入框、气泡、按钮、滑块） |
| `transformers` | 加载大模型和分词器 |
| `threading` | 线程（让两件事同时进行） |
| `queue` | 队列（两个线程之间的传送带） |
| `time` | 计时 |

### 1.2 函数：定义、参数、默认值、返回值

```python
def generate_response_stream(prompt, queue, max_tokens, temperature, history=None):
    ...
    return 某个值
```

- `def` = 定义函数。括号里是**参数**（调用时要给的输入）。
- `return` = 把结果交出去。没有 `return` 就返回 `None`。

**默认值**：`history=None` 表示"调用方可以不传这个参数，不传就当作 None"。
这样 3.4 的调用方式（只传 4 个参数）和 3.5 的调用方式（传 5 个）都能用同一个函数定义。

**返回值可以不止一个**：

```python
return tokenizer, model
tokenizer, model = load_model()
```

第一行返回的其实是一个**元组**（打包），第二行用两个变量同时接住（解包）。

### 1.3 装饰器：`@st.cache_resource` 到底做了什么

```python
@st.cache_resource
def load_model():
    ...
```

看到 `@` 开头的这一行，就要理解为：**"这个函数被外面包了一层壳"**。

```python
# 加装饰器等价于（简化理解）
load_model = st.cache_resource(load_model)
```

也就是说，Streamlit 把你的函数换成了一个"带缓存的版本"。以后你每次调用 `load_model()`，实际调用的是那个壳：壳先检查"参数变了吗？没变就直接把上次的返回值还给你"。

**为什么非要用它？** 因为 Streamlit 有个特性（见 4.1）：每次用户点一下、拖一下，整个脚本都会从头重跑一遍。不缓存的话，每次交互都要重新加载 1.5GB 的模型权重。

详见 4.3。

### 1.4 类与对象

`CustomStreamer` 用到了类。类和对象的关系是：**类 = 图纸，对象 = 按图纸造出来的东西**。

```python
class CustomStreamer:
    def __init__(self, queue):
        self.queue = queue

    def put(self, value):
        self.queue.put(cleaned_text)
```

- `class X:` 定义一张图纸。
- `__init__` 是**构造函数**，在"造对象"时自动执行一次，用来做初始化。
- `self` 代表"这个对象自己"。`self.queue = queue` 的意思是"把我身上一个叫 queue 的位置，指向传进来的那个队列"。
- 类里面定义的函数叫**方法**。第一个参数永远是 `self`。
- **实例属性**（`self.queue`、`self.full_response`）挂在这个对象上，对象活着它就活着，所有方法都能读到。

为什么需要 `self`？因为 `put()` 会在生成过程中被反复调用，它需要记得"我之前累积了什么"，这个记忆就存在 `self.full_response` 里。

**关键理解**：`streamer = CustomStreamer(queue)` 这一句造出了一个对象。之后 `model.generate(streamer=streamer)` 把它交给模型。模型每生成一个 token，就调用这个对象身上的 `put()` 方法。所以 `queue` 这个传送带，是通过对象"带着走"进入生成过程的。

### 1.5 `with` 语句

```python
with st.chat_message("assistant"):
    placeholder = st.empty()
    ...
```

`with X:` 的意思是"在 X 这个范围内做事"。在 Streamlit 里，它的用途是：**这个块里创建的所有控件，都放进 X 这个容器里**。

所以 `with st.chat_message("user"):` 之后的 `st.markdown(...)`，内容会显示在"用户气泡"里，而不是页面其他地方。

要特别注意：**`with` 不产生新作用域**。在 `with` 块里定义的变量，出了块照样能用（3.4、3.5 最后的 `cleaned_response` 就是这种情况）。

### 1.6 切片

切片是三个文件里出现频率很高、但容易看晕的语法。

```python
generated_ids[0]                     # 取第 0 个元素
model_inputs.input_ids[0]            # 取第 0 行
output_ids = ... [len(input_ids[0]):]  # 从第 N 个到结尾
history_messages[:-1]                # 从头到"倒数第一个之前"（即丢掉最后一条）
history_messages[-keep_count:]       # 从"倒数第 keep_count 个"到结尾
text.split('</think>')[-1]           # 切分后取最后一段
```

记忆规则：

- `[i]` 取第 i 个，**从 0 开始数**。
- `[a:b]` 取从 a 到 b 前一个（**不含 b**）。
- `[:b]` 从头到 b 前一个。
- `[a:]` 从 a 到结尾。
- **负数表示"从后往前数"**：`-1` 是最后一个，`-2` 是倒数第二个。

### 1.7 海象运算符 `:=`

```python
if prompt := st.chat_input("请输入您的问题..."):
```

等价于：

```python
prompt = st.chat_input("请输入您的问题...")
if prompt:
```

`:=` 同时做两件事：**赋值**，并且**把这个值当作条件**。好处是少写一行。

为什么这里能用它当条件？因为 `st.chat_input()` 在用户没提交时返回 `None`。
在 Python 里，`None`、空字符串 `""`、空列表 `[]`、数字 `0` 都算"假"，其它值算"真"。
所以这个 `if` 的真正含义是：**"只有当用户确实提交了内容时，才执行下面的代码"**。

### 1.8 真值判断

```python
if history:
    ...
else:
    ...
```

同样的道理：`history` 如果是 `None` 或 `[]`（空列表），都算"假"，走 `else`。
所以这一句的真实含义是"**有历史记录就带上，没有就只发当前问题**"。

### 1.9 f-string 与字符串运算

```python
print('*' * 40)
```

`'*' * 40` = 把星号重复 40 次，得到一条分隔线。
（三个文件里没有用到 f-string，但你会看到 `f"..."` 这种写法出现在其它示例中，它的作用是"把变量的值塞进字符串里"。）

## 第 2 章　并发与线程（重点章节）

> 这是你说"弄不懂"的地方。我把它拆得最细。

### 2.1 先破除一个误解

到目前为止你写的所有代码，都是**一行一行、按顺序执行的**。第 3 行没执行完，第 4 行绝对不会开始。

这叫**同步**（或**串行**）。它有个致命问题：**如果某一行要花 30 秒，后面所有行都得干等着。**

在 3.3 里，那一行就是 `model.generate(...)`。它执行期间：

- 模型在算，算得很慢（CPU 上几十秒）
- 用户看到的界面**完全冻住**
- 更关键的是：即使模型中间算出了字，也没有任何人去把它显示出来 —— 因为程序还卡在那一行里，根本没走到显示的那句代码。

### 2.2 "阻塞"是什么意思

**阻塞 = 程序卡在某个操作上，无法继续往下走。**

常见的阻塞操作：等网络响应、读写大文件、等待计算完成。
`model.generate()` 就是典型的阻塞操作。

与之相对，"非阻塞"就是"发起之后不等结果，立刻往下走"。

### 2.3 进程与线程

这是理解一切的基石。

- **进程**：一个正在运行的程序。比如你那两个终端里跑的 Python，各自是一个进程。
- **线程**：进程内部的**执行流**。一个进程里可以有多个线程。

用厨房打比方：

- 进程 = 一个厨房，有自己的场地和食材储备（内存空间）。
- 线程 = 厨房里的**厨师**。同一个厨房里可以有多个厨师，**共用同一批食材和灶台**。

这里最关键的一点是：**同一个进程里的多个线程共享内存。**

- 好处：互相传数据极其方便（直接把对象给过去就行）。
- 坏处：可能"撞车"——两个厨师同时伸手去改同一批食材，可能弄乱（这叫**线程安全问题**，见 2.7）。

**为什么这里要用线程，而不是多开一个进程？**
因为 `model` 和 `tokenizer` 这两个对象加起来有 1.5GB。进程之间内存是隔离的，跨进程传这么大的对象代价极高。线程共享内存，直接拿来就能用。

### 2.4 主线程与子线程：`start()` 和 `join()`

Python 程序启动时，会自动创建一个线程来跑你的代码，这个线程叫**主线程**。

```python
thread = Thread(
    target=generate_response_stream,              # 要执行哪个函数
    args=(prompt, queue, max_tokens, temperature) # 传给它的参数
)
thread.start()
```

- `Thread(...)` 只是**造出一个线程对象**（写好"待办事项"），还不会真正开始。
- `thread.start()` 才是**真正启动**它。

**`start()` 之后发生了什么？这是全篇最重要的一句话：**

> 子线程开始跑 `generate_response_stream`，
> 而主线程**不等它**，立刻执行 `start()` 的下一行。

于是两件事同时在推进：

- 子线程：吭哧吭哧地让模型生成文字
- 主线程：立刻进入下面的 `while` 循环，专门负责刷新界面

这就是整个 3.4 的核心思想。

**两个必须记住的坑：**

**坑一：`target=` 后面不能加括号。**

```python
target=generate_response_stream     # 正确：把"函数本身"交给线程
target=generate_response_stream()   # 错误：这是"立刻调用它"，然后把返回值交给线程
```

加了括号，函数会**在你当前线程里立刻执行完**，那个线程就等于白建了。这是新手最常见的错误。

**坑二：`args` 必须是元组，一个参数时别忘了逗号。**

```python
args=(prompt, queue, max_tokens, temperature)   # 四个参数，OK
args=(prompt,)                                  # 只有一个参数，那个逗号不能省
args=(prompt)                                   # 错了！这只是加了括号的 prompt 本身
```

**`join()` 是另一件事：**

```python
thread.join()
```

它的意思是"**我站在这里等，直到那个线程彻底结束再往下走**"。

对比记忆：

| 写法 | 含义 |
|---|---|
| `thread.start()` | 开始跑，我不管你，我先走 |
| `thread.join()` | 我在这里等你跑完 |

3.5 在最后加了 `thread.join()`，目的是等子线程真的收完尾，再去保存历史记录。

### 2.5 一个自然的疑问：Python 不是有 GIL 吗？

如果你查过资料，会看到"Python 有 GIL（全局解释器锁），同一时刻只有一个线程能执行 Python 代码"。
那多线程岂不是没用？

对这个具体场景来说，**依然有用**，原因有两个：

1. **这里的重活不在 Python 层。** 真正耗时的矩阵运算发生在 PyTorch 底层的 C++ 代码里，运算时不需要一直持有 GIL。
2. **主线程的 `queue.get(timeout=0.1)` 是一个"阻塞等待"操作。** 这类操作会主动让出执行权，所以主线程能规律地醒来去取数据、刷新界面。

所以结论是：**即使有 GIL，"一个线程算 + 一个线程刷新界面"这个组合仍然是有效的。** 这类任务通常被称为 I/O 密集型或"等待型"，用线程是合适的。

### 2.6 队列 Queue：为什么要用中间容器

先看一个"更直接"的想法：两个线程共享内存，那子线程生成好的文字，直接放进一个普通 list，主线程从 list 里读不就行了吗？

**不行，因为不安全。** 普通的 `list.append()` / `list.pop()` 看起来是一步，实际内部有好几条指令。两个线程同时操作时可能交错执行，导致数据错乱（比如同一条被读了两次、或者列表内部状态被写坏）。这类问题非常难调试，因为它不总是发生。

`queue.Queue` 就是为解决这个问题造的：

- **内部自带锁（lock）**，保证"放"和"取"永远是完整的、不会半途被打断。
- **先进先出（FIFO）**：先放进去的先取出来。这点对文字流极其重要——**顺序不能乱**。

常用方法：

| 方法 | 作用 |
|---|---|
| `q.put(x)` | 放一个元素进去 |
| `q.get()` | 取一个出来。队列空时会**一直等** |
| `q.get(timeout=0.1)` | 最多等 0.1 秒。还是空的就抛 `Empty` 异常 |
| `q.empty()` | 判断是否为空（**不可靠，不要用它做并发控制**） |

为什么代码里用 `get(timeout=0.1)` 而不是直接 `get()`？
因为直接 `get()` 是**死等**：一旦子线程那边出了意外（崩溃了、卡住了），主线程会永远等下去，界面彻底失去响应。加个超时，主线程至少能周期性醒来，有机会做别的判断。

### 2.7 生产者—消费者模式

这是计算机里非常经典的一种设计，三个示例用的就是它。

**分工：**

- **生产者**：只负责造数据，放进缓冲区。这里是子线程里的 `generate_response_stream`。
- **缓冲区**：临时存放数据。这里是 `Queue`。
- **消费者**：只负责从缓冲区取数据来处理。这里是主线程里那个 `while` 循环。

画成图：

```
子线程（生产者）          缓冲区            主线程（消费者）
generate_response_stream   Queue            while True
        │                    │                    │
        │  queue.put(文字) ──►│                    │
        │                    │──► queue.get()     │
        │                    │        文字        │
        │                    │                    ├─► 拼接到 full_response
        │                    │                    └─► placeholder.markdown()
        │  queue.put(None) ──►│                    │
        │                    │──► queue.get() 返回 None
        │                    │                    └─► break 退出循环
```

**为什么非要这么绕？直接把文字显示出来不行吗？**

不行。这是**本章的第二个关键点**：

> **Streamlit 的界面操作，只能在主脚本线程里执行。**

如果你在子线程的 `put()` 里直接写 `placeholder.markdown(...)`，它不会正常生效（Streamlit 会因为找不到"脚本运行上下文"而报错或静默失效）。

所以你**必须**把数据"送回主线程"再刷新界面。而"送回来"这件事，就需要一个双方都能访问的容器——**这就是 Queue 存在的根本原因**。

**这种设计的好处：**
- **解耦**：生产者不需要知道界面长什么样；消费者不需要知道模型怎么算。
- **削峰填谷**：两边速度不一致也没关系。模型吐一个字要 0.3 秒，界面刷新一次要 0.01 秒，队列自动缓冲，谁也不卡谁。

### 2.8 哨兵值：怎么告诉消费者"我说完了"

现在有个新问题：消费者在 `while True` 里不断取数据，它怎么知道**什么时候该结束**？

**不能用"队列空了"来判断**，因为队列空有两种可能：

1. 生产完了（真的结束了）
2. 暂时没数据（模型还在算下一个 token）

这两种情况从"队列空"这个现象上完全分不出来。如果拿它当结束信号，消费者会在第一个 token 还没算出来时就误判结束。

**解法：约定一个特殊的值来表示"结束"。**

```python
def end(self):
    self.queue.put(None)     # 生产者：放一个 None，意思是"我说完了"
```

```python
chunk = queue.get(timeout=0.1)
if chunk is None:            # 消费者：看到 None 就结束
    break
```

这个特殊的值就叫**哨兵值**（sentinel）。

- `end()` 是 transformers 在生成正常结束时自动调用的（见第 5 章）。
- 判断时用 `is None` 而不是 `== None`：因为 `None` 在 Python 里是唯一的单例对象，`is` 判的是"是不是同一个对象"，更符合习惯也更安全。

### 2.9 回调函数

最后一个概念，也是 `CustomStreamer` 这个类存在的理由。

**回调 = 你把一个函数交给别人，让他在合适的时机回头调用你。**

```python
streamer = CustomStreamer(queue)          # 造一个对象，身上有 put() 方法
generated_ids = model.generate(
    ...,
    streamer=streamer,                    # 把它交给模型
)
```

之后发生的事情是：

- **`put()` 不是你调用的，是 `model.generate` 在生成过程中调用的。**
- 模型每算出一个 token，就回头调用一次 `streamer.put(那个token)`。

打个比方：你在家等快递，你不必站在门口一直盯着（那叫"轮询"）。你只要把电话号码留给快递员（交一个回调），他到了自然会打给你。

这种"控制权交给别人、别人到时机叫你"的模式，也叫**控制反转**。

**关键契约**：transformers 对 streamer 只有两个要求：

| 方法 | 什么时候被调用 |
|---|---|
| `put(value)` | 每生成一步调用一次，`value` 是新 token 的张量 |
| `end()` | 生成结束时调用一次 |

所以 `CustomStreamer` 里那两个方法**必须叫这个名字**，这是约定，不能改。

### 2.10 把整条链路连起来（★ 建议反复读这段 ★）

现在把第 2 章所有概念串成一条时间线。这就是 3.4 / 3.5 的运行全过程：

| 步骤 | 发生在线程 | 做了什么 |
|---|---|---|
| 1 | 主线程 | 用户按下回车，`st.chat_input()` 返回文字 |
| 2 | 主线程 | `queue = Queue()` 造出传送带 |
| 3 | 主线程 | `Thread(...)` 造线程，`args` 里**把 queue 也传进去** |
| 4 | 主线程 | `thread.start()` —— 子线程启动，主线程**立刻继续往下** |
| 5 | 子线程 | 开始跑 `generate_response_stream`，调 `model.generate(streamer=...)` |
| 6 | 子线程 | 模型每算出一个 token → **回调** `streamer.put()` |
| 7 | 子线程 | `put()` 里：解码成文字 → 清洗 → `queue.put(文字)` **放进传送带** |
| 8 | 主线程 | 同时，`while` 循环里 `queue.get(timeout=0.1)` **取出文字** |
| 9 | 主线程 | 拼接到 `full_response`，然后 `placeholder.markdown(...)` **刷新界面** |
| 10 | — | 步骤 6~9 反复循环，直到模型生成完毕 |
| 11 | 子线程 | 生成结束，transformers 自动调 `end()` → `queue.put(None)` |
| 12 | 主线程 | 读到 `None` → `break` 退出循环 → 显示最终结果 |
| 13 | 主线程 | （3.5）`thread.join()` 等子线程收尾 → 保存到历史 |

**请特别注意第 7 步和第 8 步是"同时"发生的**：子线程在往里放，主线程在往外取。这不是"先全部算完再显示"，而是**一边算一边显示**。这就是"真流式"的含义。

## 第 3 章　大模型推理层

### 3.1 token 是什么

**模型不认识"字"，只认识"编号"。**

token 是文本切分的最小单位。分词器会把一句话切成若干个 token，每个 token 对应词表里的一个编号。

- 中文：大致上 **1 个汉字 ≈ 1 个 token**（常用词可能合并）。
- 英文：一个单词可能被拆成几块（比如 `understanding` 可能切成 `understand` + `ing`）。

Qwen3-0.6B 的词表大小是 **151936**（来自 `config.json` 的 `vocab_size`），意思是它的词表里一共有 15 万多个 token。

### 3.2 分词器 tokenizer：编码与解码

分词器负责"文字 ↔ 编号"的双向转换：

| 方向 | 方法 | 作用 |
|---|---|---|
| 文字 → 编号 | `tokenizer(...)` | 叫**编码**。这一步还顺手转成了模型能吃的张量 |
| 编号 → 文字 | `tokenizer.decode(...)` | 叫**解码** |

```python
text = tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=True)
model_inputs = tokenizer([text], return_tensors="pt")
...
response = tokenizer.decode(output_ids, skip_special_tokens=True)
```

一行行看：

- `tokenize=False`：`apply_chat_template` 默认会顺手编码，传 False 就**只拼字符串、先不编码**。
- `[text]` 外面套方括号：**加一维**，表示"这一批里有 1 条"。模型总是按"批"处理，哪怕只有一条。
- `return_tensors="pt"`：返回 PyTorch 张量（`pt` = PyTorch），而不是 Python 列表。模型只接受张量。
- `skip_special_tokens=True`：丢掉 `<|im_start|>`、`<|im_end|>` 这类**控制标记**。不丢的话它们会混在你的回答里显示出来。

### 3.3 自回归生成：模型每次只做一件事

**模型的全部工作就是：根据已有的所有 token，预测下一个 token 是什么。**

然后把这个新 token 接到末尾，再预测下一个。如此循环，直到吐出"结束标记"。

这就叫**自回归**（autoregressive）。

**从这里可以推出一个非常重要的结论：**

> **生成本来就是"一个 token 一个 token"出来的。**

所以"流式输出"**不是一种额外技术**，它只是**把这个本来就存在的中间过程暴露出来**给用户看。模型本来就一个一个吐，只是 3.3 那样写代码把中间结果全丢掉了、只留最后的总结果。

### 3.4 chat template：把对话"套模板"

大模型本体只认识"一段纯文本"，它并不知道什么叫"用户说的"和"模型说的"。所谓对话格式，其实是**每个模型自己约定的一套标记**。

`apply_chat_template` 就是把你的消息列表按模型规定的模板拼成一整段字符串。

Qwen3 的模板拼出来大概是这样：

```
<|im_start|>user
请概括一下Qwen3的优点。<|im_end|>
<|im_start|>assistant
```

其中 `<|im_start|>` / `<|im_end|>` 是划分"说话人边界"的特殊标记。

两个常用参数：

- **`add_generation_prompt=True`**：在末尾追加"轮到 assistant 说话了"的提示。
  不加的话，模型不知道自己是该"接着说"还是"已经说完了"，很可能不输出任何东西。

- **`enable_thinking=False`**（Qwen3 特有）：关闭"思考模式"。
  Qwen3 默认会先输出一段思考过程（包在 `<think>...</think>` 里）再给答案。传 `False` 之后，模板会直接给一个**空的 think 块**，模型就不真的思考了，直接作答。

  实测渲染结果末尾是：
  ```
  <|im_start|>assistant\n<think>\n\n</think>\n\n
  ```
  这个"空 think 块"后面还会用到（见 5.2）。

### 3.5 张量、input_ids、attention_mask、device

- **张量（tensor）**：多维数组，PyTorch 的基本数据结构。你可以先把它理解成"能放到显卡上算的高级列表"。
- **`input_ids`**：token 编号组成的张量，形状是 `(批大小, 序列长度)`。比如 `(1, 18)` 表示"1 条，18 个 token"。
- **`attention_mask`**：标记哪些位置是"真实内容"、哪些是"填充占位"。单条输入时通常全是 1，不用管。
- **`device`**：数据在 CPU 还是 GPU 上。`model.device` 就是模型所在的位置。**模型和数据必须在同一个设备上**，否则报错。`.to(model.device)` 就是在做这件事。

### 3.6 `model.generate` 内部在做什么

它是一个循环，反复做这几件事：

1. 把当前序列喂给模型，算出"下一个 token 的概率分布"
2. 根据采样参数挑出一个 token
3. 把这个 token 接到序列末尾
4. 判断是否该停（吐出结束标记了？或者到数量上限了？）
5. 没停就回到第 1 步

**两个必须知道的细节：**

**细节一：返回的是"输入 + 输出"的完整序列。**

所以你要自己切掉输入部分，否则会把用户问的问题也解码出来重复显示一遍：

```python
output_ids = generated_ids[0][len(model_inputs.input_ids[0]):].tolist()
#                            ↑ 取第 0 条      ↑ 从"输入长度"之后开始切
```

**细节二：传 `streamer=` 会改变它的行为。**

传了 streamer 之后，它不再"闷头算完再返回"，而是**每一步都把新 token 通过回调交给你**。这就是流式生效的关键开关。

### 3.7 `max_new_tokens` 与上下文长度

这两个概念必须分清：

| 概念 | 含义 | Qwen3-0.6B 的值 |
|---|---|---|
| **上下文长度** | 输入 + 输出 的**总**上限 | 40960 |
| **`max_new_tokens`** | **只限制输出**部分的长度上限 | 由你指定 |

关系是：**输入长度 + max_new_tokens 不能超过 40960。**

两个常见误解：

- **误解一**："设得越大越快。" 错。它只是**上限**，不是目标。模型正常说完会自己吐结束标记停下来，根本用不到上限。
- **误解二**："设得大没坏处。" 有。一旦模型进入复读、停不下来的状态，上限就是唯一的刹车。设成 65536（超过 40960）等于**把刹车拆了**，会白跑到长度上限才停。

所以 3.4 / 3.5 用滑块限制在 `100~2048` 以内，是安全的。

**这也正是 3.5 要限制"记忆轮数"的原因**：历史越长，输入越长，越接近 40960 的上限。

### 3.8 采样参数：模型怎么"挑"下一个 token

模型算出的是一个**概率分布**（每个候选 token 各有一个概率）。怎么从里面挑一个？

| 方式 | 做法 | 特点 |
|---|---|---|
| **贪心解码** | 永远选概率最大的那个 | 稳定、可复现，但死板，容易重复绕圈 |
| **随机采样** | 按概率分布抽签 | 有多样性，但每次结果不同 |

常用调节旋钮：

- **temperature（温度）**：把概率分布"压平"或"变陡"。温度低 → 分布更陡 → 更倾向选最可能的 → 更确定；温度高 → 分布更平 → 更多冷门词有机会 → 更随机、更有创意，但也更容易胡说。
- **top_k**：只在概率最高的 k 个候选里挑。
- **top_p**：从累积概率达到 p 的最小候选集合里挑。

**一个重要提醒**：Qwen3-0.6B 的 `generation_config.json` 里自带一组推荐值：

```
temperature = 0.6,  top_k = 20,  top_p = 0.95
```

而 3.4 / 3.5 的滑块默认值是 **1.0**。一旦你在 `generate()` 里传了 `temperature`，就会**覆盖**模型自带的那一套参数。也就是说，**默认跑的不是模型作者推荐的参数**。

另外：

```python
do_sample=True if temperature > 0 else False
```

意思是"温度大于 0 才启用随机采样，否则用贪心"。但注意滑块最小值是 `0.1`，所以这个条件**永远成立**，`else` 分支永远走不到——这是段冗余代码。

### 3.9 停止条件

`model.generate` 在两种情况下会停下来：

1. 模型自己吐出了**结束标记**（EOS，end of sequence）。Qwen3-0.6B 的 `eos_token_id` 是 `[151645, 151643]`。
2. 生成数量达到了 `max_new_tokens`。

正常情况下是第 1 种。第 2 种是"兜底刹车"。

**停止时会发生什么？** transformers 会调用 `streamer.end()` —— 这就接上了 2.8 讲的哨兵值。

### 3.10 流式 vs 非流式：一个必须澄清的点

| | 非流式（3.3） | 流式（3.4 / 3.5） |
|---|---|---|
| 用户看到第一个字 | 等全部生成完（几十秒） | 立刻（几百毫秒～几秒） |
| **生成总耗时** | **一样的** | **一样的** |

**重点：流式并不加快生成速度。**

它改善的是**感知延迟**——用户不用盯着一个静止的屏幕几十秒，而是马上看到文字一个个冒出来，心理上觉得快得多。

这是所有 AI 聊天产品的通用做法，原因就在这里。

## 第 4 章　Streamlit 层

### 4.1 最重要的特性：脚本会从头重跑

**这是理解全部 Streamlit 代码的钥匙。**

Streamlit 的运行模型是：**用户在网页上每做一次操作（打字、点按钮、拖滑块），它就把整个 `.py` 文件从头到尾重新执行一遍。**

由此推出三个后果，三个文件里的很多"奇怪写法"都是为了应对它们：

| 后果 | 应对方式 | 出现位置 |
|---|---|---|
| 普通变量每次都被重新创建，值会丢 | 用 `st.session_state` 存 | 所有 `session_state` 相关代码 |
| 顶层代码会被反复执行 | 用 `@st.cache_resource` 缓存昂贵操作 | `load_model()` |
| 界面元素的"当前值"需要自己记住 | 把控件返回值写回 `session_state` | 3.5 的复选框 |

所以看到 `if "messages" not in st.session_state:` 时，要理解成："**因为我可能会被重跑很多次，所以第一次运行时先建好这个容器**"。

`st.rerun()` 则是**主动**要求立刻重跑（比如清空对话后想让界面马上更新）。

### 4.2 `st.session_state`

它是一个"**跨重跑存活的字典**"。你可以往上面挂任何东西。

两种标准用法：

**用法一：首次初始化**

```python
if "messages" not in st.session_state:
    st.session_state.messages = []
```

为什么必须判断？因为脚本会重跑。不加判断的话，第二次重跑会把历史清空。

**用法二：受控组件（保持控件状态）**

```python
st.session_state.memory_enabled = st.checkbox("启用长期记忆", value=st.session_state.memory_enabled)
```

这一行做了两件事：

- `value=st.session_state.memory_enabled`：**读**出上次的状态，让复选框保持勾选/不勾选。
- `st.session_state.memory_enabled = ...`：把这次的新状态**写**回去。

如果只写 `memory_enabled = st.checkbox(...)`，那么用户勾选之后，下次重跑又会回到默认值，开关就"按不住"了。

### 4.3 `@st.cache_resource`

装饰器，作用是**缓存函数的返回值**（原理见 1.3）。

- 为什么必须用：`load_model()` 要读 1.5GB 文件，不缓存的话每次交互都要重来。
- `_resource` 后缀的含义：缓存的是**资源类对象**（模型、数据库连接）。它不做序列化拷贝，多个用户会话共享同一个对象——对模型来说这正是我们想要的。

### 4.4 聊天界面三件套

| 组件 | 作用 |
|---|---|
| `st.chat_input("提示文字")` | 页面底部的输入框。**用户没提交时返回 `None`**，提交了返回输入的文字 |
| `st.chat_message("user"/"assistant")` | 创建一个聊天气泡容器，用 `with` 往里放内容 |
| `st.markdown(内容)` | 渲染内容（支持 **加粗**、列表、代码块等） |

标准套路：

```python
if prompt := st.chat_input("请输入您的问题..."):   # 只在用户刚提交时成立
    st.session_state.messages.append({"role": "user", "content": prompt})
    with st.chat_message("user"):
        st.markdown(prompt)
    ...
```

**一个容易困惑的点**：为什么上面已经用 `for` 循环画过全部历史了，这里还要再画一次用户气泡？

因为**执行顺序**：那个 `for` 循环在这次重跑中，是在 `append` **之前**执行的，所以历史列表里还没有刚提交的这条。因此需要在这里补画一次。

侧边栏及其它控件：

| 组件 | 作用 |
|---|---|
| `with st.sidebar:` | 这个块里的控件都放进左侧面板 |
| `st.slider(标签, 最小, 最大, 默认, 步长)` | 拖动条，返回当前数值 |
| `st.checkbox(标签, value=...)` | 勾选框，返回 True/False |
| `st.button(标签)` | 按钮，**只在那一次重跑时**返回 True |
| `st.divider()` | 一条水平分隔线 |
| `st.header()` / `st.title()` / `st.write()` | 各级标题与普通文字 |

`st.slider` 还有两个关键字参数在 3.5 里用到了：

- `disabled=not st.session_state.memory_enabled`：当记忆没启用时，把滑块**禁用**（变灰、拖不动）。这是界面联动。
- `help="..."`：鼠标悬停时显示的说明文字。

### 4.5 `st.empty()` 与打字机效果

```python
placeholder = st.empty()                        # 先占一个空位
...
placeholder.markdown(full_response + "▌")       # 反复往同一个位置覆盖写入
...
placeholder.markdown(full_response)             # 最后写一次干净的结果
```

`st.empty()` 创建一个**占位符**，它的特点是**可以被反复覆盖**。

这正是打字机效果的实现方式：**同一个位置，不断被更长的文本覆盖**。末尾那个 `▌` 是假装的光标。

最后那句再去掉光标、写入最终结果。

### 4.6 为什么这里**必须**用线程

把前面两块知识合起来看，答案就清楚了。同时存在两个约束：

1. `model.generate()` 很慢且阻塞 —— 如果放主线程，界面会冻住。
2. **Streamlit 的界面操作只能在主脚本线程里执行** —— 所以生成又不能放在子线程里直接刷新界面。

两条约束挤在一起，唯一的出路就是：

> **生成放到子线程跑，生成好的文字通过队列送回主线程，由主线程负责刷新界面。**

这就是 `Thread` + `Queue` 这个组合存在的**根本原因**。它不是"为了炫技"，而是被这两个约束逼出来的。

## 第 5 章　transformers 的 Streamer 协议

### 5.1 契约：只需要两个方法

只要你传给 `model.generate` 的对象实现了下面两个方法，它就能工作：

| 方法 | 何时被调用 | 参数含义 |
|---|---|---|
| `put(value)` | 每生成一步调用一次 | `value` 是新 token 的张量 |
| `end()` | 生成结束时调用一次 | 无 |

`CustomStreamer` 就是按这个契约写的。

**注意这里有个容易混淆的地方**：transformers 自带的 `TextIteratorStreamer` 可以被 `for` 循环直接遍历（那三个文件没用它，但你在别处会见到）。而**自定义的 streamer 不会自动变成可遍历的**——所以 3.4 / 3.5 需要**自己配一个 Queue**，由主线程从队列里取。

这是两种不同的收数据方式：

| 方式 | 怎么收数据 |
|---|---|
| `TextIteratorStreamer` | 主线程里 `for chunk in streamer:` |
| 自定义 Streamer + Queue | 主线程里 `while True: queue.get(timeout=...)` |

### 5.2 ★ 第一次 `put` 收到的是整个 prompt ★

**这是最好用但也最容易踩的一点，一定要记住。**

我实测验证过：`put()` 会被反复调用，但**第一次调用非常特殊**。

| 调用次序 | 收到什么 | 张量形状 |
|---|---|---|
| 第 **1** 次 | **整个 prompt**（用户问题 + 模板标记） | `(1, 18)` ← 多元素 |
| 第 2 次起 | **一个新 token** | `(1,)` ← 单元素 |

实测数据：生成 15 个新 token 时，`put` 一共被调用了 **16** 次（1 次 prompt + 15 次 token）。

**这带来一个陷阱**：如果你把第一次收到的东西原样显示出去，**用户就会看到自己的问题被回显一遍**。

**那为什么示例代码看起来没这个问题？** 因为它"碰巧"挡住了，而不是有意设计：

回顾 3.4 的 `put()`：

```python
if '<think>' in text:
    text = text.split('</think>')[-1]
elif '</think>' in text:
    text = text.split('</think>')[-1]
```

而 `enable_thinking=False` 渲染出的 prompt 末尾正好是：

```
<|im_start|>assistant\n<think>\n\n</think>\n\n
```

于是第一次 `put` 收到的整段 prompt 里**含有 `</think>`**，被 `split('</think>')[-1]` 切掉前半段后，只剩下末尾的空白 —— prompt 就被顺手丢掉了。

**所以这份"能用"完全依赖模板渲染结果的巧合。** 一旦把 `enable_thinking` 打开（prompt 末尾就没有那个空 think 块了），prompt 就会被原样回显给用户。

**更稳妥的做法**是在 `put()` 里主动跳过第一次调用（比如加个 `is_first` 标记直接 return），而不是依赖这种巧合。

### 5.3 逐 token 解码的一个理论风险

`put()` 里每次都单独解码一个 token：

```python
text = tokenizer.decode(tokens[0], skip_special_tokens=True)
```

理论上，如果一个多字节字符（比如中文）刚好被切在两个 token 上，单独解码前一半会产生乱码或占位符。

**实测结论**：这份 tokenizer 在中文上逐 token 解码**没有出现乱码**，输出与"一次性整体解码"的结果完全一致。

所以这里不必过度担心，但要知道这是逐 token 解码方式固有的风险点——这也是官方 `TextIteratorStreamer` 内部要做缓冲处理的原因之一。

## 第 6 章　三份代码逐项对照

### 6.1 能力对照表

| | 3.3 | 3.4 | 3.5 |
|---|---|---|---|
| 流式方式 | 假流式（生成完再逐词显示） | **真流式**（线程 + 队列） | 真流式 |

### 6.2 三个版本各自的关键那一行

**3.3 的症结：**

```python
assistant_response = generate_response(prompt)   # ← 这一行要等几十秒，界面全程冻住
```

**3.4 的解法：**

```python
thread.start()                                   # ← 生成交给子线程，主线程立刻往下走
...
chunk = queue.get(timeout=0.1)                   # ← 主线程边取边刷新
```

**3.5 的解法：**

```python
messages = history + [{"role": "user", "content": prompt}]   # ← 把历史真的拼进去
```

### 6.3 3.5 里最值得细读的一段

```python
history = None
if st.session_state.memory_enabled and len(st.session_state.messages) > 1:
    history_messages = st.session_state.messages[:-1]
    keep_count = min(st.session_state.memory_rounds * 2, len(history_messages))
    history = history_messages[-keep_count:]
```

逐行拆：

1. `history = None`
   默认不用记忆。传 `None` 给子线程时，子线程走 `else` 分支，只发当前问题。

2. `if memory_enabled and len(messages) > 1:`
   两个条件同时满足才构建历史：
   - 用户打开了记忆开关；
   - 消息数大于 1。**为什么？** 因为刚把当前问题 `append` 进去，列表里至少有 1 条。如果正好只有 1 条，说明这是第一轮，压根没有历史可记。

3. `history_messages = st.session_state.messages[:-1]`
   **丢掉最后一条**。丢掉的正是**当前这个问题**——因为它马上要在子线程里被显式拼上去。不排除的话会重复两次。

4. `keep_count = min(st.session_state.memory_rounds * 2, len(history_messages))`
   - **为什么乘 2？** 一轮对话 = 1 条 user + 1 条 assistant = 2 条消息。记住 3 轮就是要保留 6 条。
   - **为什么套 `min`？** 取两者中较小的。万一历史还不够 6 条（比如刚聊了 2 轮），就按实际条数来，否则下面切片会取到空列表。

5. `history = history_messages[-keep_count:]`
   取**最后 keep_count 条**。更早的丢掉。

**为什么不能把所有历史都传进去？** 因为上下文长度有上限（40960），而且输入越长越慢。所以必须做"最近若干轮"的截断（见 3.7）。

### 8.2 三个动手练习（由易到难）

**练习一：确认线程真的在工作**

在 `generate_response_stream` 的开头和结尾各加一句打印：

```python
print("【子线程】开始")
...
print("【子线程】结束")
```

再把 `print(full_response.strip())` 那行删掉。
运行后观察终端输出的顺序——你会看到"开始"在界面开始出字之前就打出来了，直观感受到两条执行流在同时推进。

**练习二：故意制造子线程异常，观察后果**

在 `generate_response_stream` 开头插入一行：

```python
raise RuntimeError("故意报错")
```

然后提问。你会发现：**界面永远停在"正在输入"，不报错也不结束。**

原因是：子线程抛异常后，`end()` 永远不会被调用，队列永远收不到 `None`，
主线程的 `while True` 就无限空转下去了。这是生产者—消费者模式的经典漏洞：
**缺少异常路径的收尾**。

（用 `Ctrl+C` 停止 streamlit 再重启即可恢复。）

**练习三：把记忆机制改得更清楚**

在 3.5 里临时把 `keep_count` 那行改成：

```python
keep_count = len(history_messages)     # 全部历史都带上
```

再问它记不记得之前说过的内容，对比打开/关闭记忆开关的效果差异。
注意：这样改之后，输入会随对话轮数不断变长，可以顺便观察界面出字速度的变化。

### 8.3 最后一个提醒

这三份代码是**教学示例**，为了把知识点讲清楚，保留了一些冗余和不够严谨的地方（本文档和代码注释里都标注了）。

它们适合用来理解原理，但如果要拿去做真正的项目，下面这些问题是需要处理的：

1. 模型路径是教程作者机器上的相对路径，需要改成你自己的绝对路径。
2. 助手回复在生成**完成后**才写入历史——生成期间若发生重跑，用户输入会丢失。
3. 子线程异常时界面会永久卡死（见练习二）。
4. 输入很长时没有截断保护，可能超过 40960 的上下文上限。
5. 首 token 延迟的计算方式不对（它记的是 prompt 到达的时刻）。
6. 一些死代码：`import platform`、`get_first_token_latency()`、无效的前缀清理循环。
