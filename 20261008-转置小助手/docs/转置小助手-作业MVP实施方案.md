## 1. 最小产品定义

**一句话**：把一封客户入离职邮件（正文 + 附件）一键转置成公司标准报岗表，自动标出需要人工确认的字段。

### 1.1 四个必须有的能力

少任何一个，就演示不出这个项目的核心价值。

| # | 能力 | 内容 |
|---|---|---|
| 1 | 解析 | 吃下邮件正文 / Excel / PDF / Word 四类输入 |
| 2 | 抽取 | 从非结构化文本抽出 7 类关键字段：姓名、证件号、岗位、地区、基数、入离职类型、生效日期 |
| 3 | 映射 | 按**客户模板**把抽出的字段映射到公司标准报岗表列 |
| 4 | 校验 + 标色 + 导出 | 规则校验、低置信标色、人工修正、导出标准 Excel |

### 1.2 明确不做

把"不做清单"写进方案本身就是加分项，它证明范围是受控的。

- 不接真实邮箱，不接 RPA
- 不做通用抽取平台（合同 / 发票 / 证明）
- 不做用户体系、不做数据库、不做云端部署
- 不做 20+ 客户模板（**3 家足够证明"可配置"**）
- 不做多语言

## 2. 产品形态

一个本地运行的 Web 小程序。左原文、右结果的双栏对照是整份 demo 最有说服力的画面：点击右侧某个标色单元格，左侧对应原文段落高亮，用户立刻能判断对不对。

```
┌─────────────────────────────────────────────────────┐
│  [客户模板 ▾]   [邮件样本 ▾]              [转置]     │
├──────────────────────┬──────────────────────────────┤
│ 原始邮件 + 附件文本   │  标准报岗表（可编辑）          │
│ （左栏，只读）        │  （右栏，标色 + 可改）         │
│                      │                              │
│ 高亮：抽取来源        │  黄 = 低置信   红 = 校验失败   │
├──────────────────────┴──────────────────────────────┤
│  复核清单：3 项待确认              [导出标准报岗表]   │
└─────────────────────────────────────────────────────┘
```

## 3. 技术方案

### 3.1 选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | Python 3.13 | 文档解析生态最全 |
| 后端 | FastAPI + uvicorn | 轻量，两个文件起服务 |
| 前端 | 单页原生 HTML + 少量 JS | 单元格级标色与双栏对照需要精确控制，上框架反而累赘 |
| 抽取 | LLM（OpenAI 兼容接口） | 作业要求"用 AI" |
| 附件解析 | openpyxl / python-docx / pdfplumber | 各管一种格式 |
| 校验 | 纯 Python 函数 + pytest | 确定性、可解释 |
| 导出 | openpyxl | 直接产出 xlsx |

零外部服务、零数据库、零登录。所有配置是 JSON 文件。

### 3.2 LLM 接入的关键设计：可插拔 + 回放

演示最怕的情况是"到台上连不上网或 key 失效"。抽取层因此做成三层：

| 层 | 触发条件 | 行为 |
|---|---|---|
| live | 有 key 且网络可用 | 调用 LLM |
| cache | 命中缓存 | 直接读 `cache/<邮件id>.json`（预先跑一次生成） |
| offline | 无 key 或调用失败 | 走内置规则抽取，界面显式标注"离线模式：规则兜底，置信度按低处理" |

演示时默认走 cache——效果与 live 一致，但百分之百稳。

### 3.3 客户模板配置（核心资产）

一个客户模板 = 一个 JSON。**换客户只改这个文件，不动任何代码。**

```json
{
  "customer_id": "CUST_A",
  "customer_name": "示例客户A",
  "aliases": {
    "name":      ["员工姓名", "姓名", "Name"],
    "id_no":     ["身份证号", "证件号码", "ID No."],
    "position":  ["岗位", "职位"],
    "region":    ["工作地", "地区"],
    "base":      ["社保基数", "缴纳基数"],
    "move_type": ["入离职类型", "类型"],
    "effective": ["生效日期", "入职日期", "离职日期"]
  },
  "derived_rules": {
    "社保起缴月": "取生效日期所在月"
  },
  "notes": "该客户日期格式为 YYYY/MM/DD"
}
```

配置引擎的作用：把"这家客户把证件号叫'证件号码'"这类差异，从代码里赶出去。

### 3.4 置信度评分：用确定性规则算，不用 LLM 自报

让模型自报 confidence 不可靠——模型标定差，且无法解释错在哪。改用三条确定性规则加权：

| 维度 | 权重 | 判定依据 |
|---|---|---|
| 格式匹配 | 0.5 | 值符合该字段的格式约束（证件号校验位、日期可解析、基数在合理区间） |
| 别名命中 | 0.3 | 来源标签命中该客户模板的 aliases |
| 多源一致 | 0.2 | 同一字段在多处出现时取值一致 |

判定：≥0.8 绿；0.5—0.8 黄（进复核清单）；<0.5 红（强制人工）。三个维度全部可单测。

### 3.5 校验规则库（纯函数 + 单测）

| 规则 | 类型 | 说明 |
|---|---|---|
| 证件号校验位 | 格式 | 18 位 GB 11643，ISO 7064 MOD 11-2 |
| 日期可解析 | 格式 | 支持 `YYYY-MM-DD` / `YYYY/MM/DD` / `YYYY年M月D日` |
| 枚举合法 | 取值 | 入离职类型 ∈ {入职, 离职, 入职+离职} |
| 基数区间 | 取值 | 社保基数落在 [当地下限, 上限] |
| 必填非空 | 完整性 | 7 类核心字段 |
| 日期顺序 | 一致性 | 离职日期 ≥ 入职日期；生效日期落在合理窗口 |
| 跨源一致 | 一致性 | 正文与附件对同一字段取值冲突则报冲突 |

每条规则是一个纯函数 `(record) -> list[Issue]`，`Issue = {字段, 规则名, 说明, 严重度}`。配 pytest。

## 4. 合成数据设计

3 家客户模板，格式**刻意做差异**，用来证明"可配置"：

| 模板 | 邮件正文风格 | 附件格式 | 差异点 |
|---|---|---|---|
| 客户 A | 表格式罗列 | `.xlsx` | 日期 `YYYY/MM/DD`；字段名用全称 |
| 客户 B | 自然语言叙述 | `.docx` | 日期 `YYYY年M月D日`；字段名用简称 |
| 客户 C | 表格 + 备注段 | `.pdf`（文本型） | 含"社保基数另见附件"的跨文件引用 |

每个模板 2 封邮件：**1 封正常、1 封故意埋问题**（证件号错 1 位、日期倒挂、某字段缺失），用于演示标色与复核流程。

再加 1 个扫描件（图片型 PDF）样本，用于演示 OCR 兜底路径——这条只求跑通识别，不追求准确率，界面标注为"降级处理"。

> 所有姓名、证件号均为编造。证件号使用**校验位正确的虚构号码**，避免与真实身份碰撞。

## 5. 实施步骤

按"先能跑，再加分"排序，每步给出完成判据。

### S1 地基（无外部依赖）
- 建目录结构、写字段字典（标准报岗表列定义）、写 3 份客户模板 JSON
- 造 7 份合成样本（3 模板 × 2 封 + 1 扫描件）
- **判据**：样本齐全；字段字典与模板 JSON 通过 schema 校验

### S2 解析 + 抽取
- 附件解析器：xlsx / docx / pdf → 统一文本块
- LLM 抽取 + 三层降级（live / cache / offline）
- **判据**：7 份样本都能吐出含 7 字段的结构化 JSON

### S3 映射 + 校验（工作量重心）
- 模板映射引擎（按 aliases 归一）
- 置信度评分
- 校验规则库 + 单测
- **判据**：`pytest` 全绿；问题邮件产出预期标色项——错证件号 / 日期倒挂 / 缺字段各命中一次

### S4 界面 + 导出
- 单页：选模板 → 转置 → 双栏对照 → 标色 → 可编辑 → 复核清单 → 导出 xlsx
- **判据**：浏览器里完整走通一遍，导出的 xlsx 可直接打开且内容正确

### S5 演示材料
- 3 分钟录屏 + 一页架构图
- **判据**：不看代码也能看懂"配置化"与"双重校验"这两个核心主张

**工作量分布**：S3 最重（映射 + 校验是整个方案的价值所在），S4 次之，S2 最轻。

## 6. 现在能做什么

| 项 | 依赖外部输入 | 说明 |
|---|---|---|
| S1 地基 | 否 | 立刻可做 |
| S3 校验规则库 | 否 | 纯函数，立刻可做 |
| S2 解析器 | 否 | 立刻可做 |
| S2 LLM 抽取 | **是** | 需要 API key；可先做 offline 版 + 缓存层，key 到位后补 live |
| S4 界面 | 否 | 立刻可做 |
| S5 演示材料 | 否 | 最后做 |

**结论：除 LLM live 调用外，全部可在没有任何外部输入的情况下完成。** LLM 那一步用"缓存 + 离线兜底"绕开，不构成阻塞。

## 7. 与"做得好才开放真实对接"的关系

如果目标是择优进入真实对接，那么这份 demo 需要证明的**不是"抽取准"**，而是两件事：

1. **换客户只改配置**——对应评价文档的"模板资产化"，也是 ★★★ 升 ★★★☆ 功能清单第 1 项
2. **出错能被发现、并能被人工兜住**——对应"校验体系化"，功能清单第 2 项

这两点恰好是评价文档点名的两个当务之急。demo 里把这两件事演示清楚，比把抽取准确率从 92% 提到 96% 有价值得多。
