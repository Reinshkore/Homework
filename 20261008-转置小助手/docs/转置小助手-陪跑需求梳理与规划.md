### 1.1 三个由事实直接推出的判断

**判断一：项目方缺的是工程产能，不是业务理解。**

6 人构成中，业务/运营 4 人（其中 2 人为挂职）、产品 1 人、技术 1 人。技术执行力量为 1 人且来自外服云、属兼职。而项目申报书里的方案写得相当完整——痛点、架构、场景、成效四条俱全。也就是说对方**不缺方案，缺的是一个人把方案变成能跑的东西**。

需要留意"挂职"二字：运营项目经理与业务项目经理均为挂职身份，意味着其在本项目上的时间投入存在不确定性。

**判断二：L4（低代码 Agent）被打"—"，说明平台方认为它不是 Agent 形态。**

能力阶梯里 L2（文档智能抽取）是唯一的核心关键项，L4 反而标为不需要。评审组对该项目形态的认定是"**抽取—校验—输出闭环**"（★★★ 的定义原文），而不是对话式智能体。这一点与"做一个智能体应用"的想法存在张力，第三章会展开。

**判断三：陪跑意向为 0，意味着这不是一次"响应申报"的陪跑。**

同批 41 份问卷中 25 份（60.98%）表示需要陪跑，但本项目无人报名。因此不存在默认的数据通道、口径确认渠道与授权关系。陪跑必须**按"零依赖项目方"的前提来设计**，否则第一步就会卡住。

## 二、实际需求梳理

把申报书里的"思路举措"与评价文档里的"短板"合并成一条完整链路，逐层标注真实难点。

### 2.1 需求链路

```
邮件（正文 + 附件）
   ↓  L-A 输入层      附件格式：Excel / PDF / Word；异常：扫描件、加密件、多语言
   ↓  L-B 抽取层      "规则优先、模型补充"，抽 7 类关键字段
   ↓  L-C 映射层      客户模板 → 公司标准报岗表  ← 要害
   ↓  L-D 校验层      规则校验 + AI 复核 → 差异标色 → 复核清单 → 人工修正
   ↓  L-E 输出层      标准报岗文件 → 批量导入 / RPA
   ↓  L-F 约束层      本地化部署、敏感数据不出域、全程留痕可追溯
```

**L-A 输入层。** 申报书只写了"Excel / PDF / Word"，评价文档点名了三类未定义异常：

| 异常类型 | 可否自动化 | 处置结论 |
|---|---|---|
| 扫描件（图片型 PDF） | 可以 | 走 OCR 路径，需单独技术栈，准确率低于文本型 |
| 加密附件 | **基本不可行** | 密码来源不在系统内，只能走人工兜底 |
| 多语言附件 | 可以 | 字段名走字典映射，值本身不动 |

**L-B 抽取层。** 字段清单（申报书原文）：姓名、证件号、岗位、地区、基数、入离职类型、生效日期；评价文档另点出"社保缴纳口径"。

判断：**这一层不是难点。** 对固定字段的结构化抽取，当前大模型已经足够稳。真正的困难在下一层。把主要精力投在这里是典型的资源错配。

**L-C 映射层——项目成败的分水岭。** 承两件事：

1. *多客户模板差异*。每个客户的字段名、列序、表头合并方式都不同。需要一套"客户级数据映射规则"，且要求业务人员能自助配置、能版本管理、不依赖开发写代码。"模板一次创建、后续自动匹配"是申报书原话。
2. *业务口径的逻辑判断*。社保缴纳口径、入离职类型、生效日期这几类字段，**不是"从文本里找到"，而是"由多条信息推导"**。例如某客户只写"离职日期"，标准表要的是"社保停缴月份"，中间需要套当地社保规则与缴纳口径。

评价文档的核心结论与此一致：当务之急是"把'能跑通'变成'换客户也能跑通'，核心是**模板资产化与校验体系化**"。

**L-D 校验层——决定业务敢不敢用。** 评价文档列为短板：字段级校验体系不完整、缺差异自动标色与人工复核界面。没有这一层，抽错一个证件号就是一次风险事件。双重校验（规则 + AI 复核）、可信度评分、低置信强制人工复核，是升到 ★★★☆ 的必要项。

**L-E 输出层。** 生成标准格式报岗文件 → 对接批量导入 / RPA。RPA 对接依赖项目方环境，陪跑阶段只能做到"输出合规文件 + 预留接口"。

**L-F 约束层。** 姓名 + 证件号 + 社保基数属个人敏感信息。申报书明确要求"本地化部署确保敏感数据不出域"，并有"统一留痕与可追溯"的合规诉求。这直接决定陪跑的工作方式（见 3.1）。

### 2.2 需求优先级（按投入产出排序）

| 序 | 需求 | 性质 | 判断 |
|---|---|---|---|
| 1 | 字段映射配置机制 + 模板资产库 | 资产 | **最高价值。** 唯一能沉淀下来、能复用的东西 |
| 2 | 双重校验 + 差异标色 + 复核清单 | 能力 | 决定业务敢不敢真用 |
| 3 | 异常附件兜底策略（OCR / 加密 / 多语言） | 兜底 | 边角但必须定义，否则演示时会翻 |
| 4 | 抽取准确率提升 | 优化 | 已够用，投入产出最低 |
| 5 | RPA 对接 | 集成 | 最后做，依赖对方环境 |

### 2.3 与"智能体应用"的关系

申报书的预期成效里没有"智能体"三个字；平台评级也把 L4（低代码 Agent）标为不需要。如果照字面做一个对话式 Agent，形态会偏。

**合理的 Agent 化定位是：把大模型放在"决策与调度"位置，而不是"聊天入口"。** 具体是四件事：

- 异常附件如何兜底（扫描件走 OCR、加密件判人工）
- 字段冲突如何裁决（同一字段在两处出现且不一致时）
- 低置信字段如何升级人工
- 邮件该匹配哪家客户的模板

抽取、映射、校验这三步，用确定性代码 + 规则库实现，不交给模型临场推断。这样既符合平台对 L2●● 的真实定位，Agent 也确实用在了刀刃上——它处理的是"规则覆盖不到的情况"，而不是"把简单的事再做一遍"。

## 三、陪跑方式

### 3.1 三个现实约束

1. **无授权通道。** 陪跑意向 0 报名 → 项目方没有向我们发出请求 → 默认拿不到任何真实数据、口径确认或署名许可。
2. **数据是个人敏感信息。** 不可能获取真实入离职邮件。所有验证只能在合成数据上做；如需真实数据，只能由项目方在其本地环境执行。
3. **知识产权未定。** 推荐表勾选"无知识产权"。我们产出的代码、模板、规则库的归属、能否署名、能否开源，**必须先书面约定**，否则做到一半会卡在交付环节。

### 3.2 陪跑定位（建议）

> **做"参考实现 + 方法资产"，不做"接管生产系统"。**

拆开说：

- 用**全合成数据**把"抽取 → 映射 → 校验 → 输出"整条闭环完整跑通，产出可演示的 MVP；
- 同时把项目方缺的东西做成**可迁移的资产**：客户模板配置格式、字段映射规则库结构、三套提示词模板（抽取 / 校验 / 格式化）、双重校验规则清单、异常附件兜底决策表；
- 项目方拿这套资产，在自己本地环境接真实邮件即可。

**理由：** 项目方技术产能只有 1 名兼职人员，最缺的不是又一份方案（他们的方案已经足够完整），而是一个**已经跑起来、能照着改**的东西。合成数据路线同时绕开了授权与合规两道障碍，可以立刻开工，不依赖对方任何响应。

### 3.3 陪跑路线

阶段划分与评价文档给出的 M1 / M2 / M3 对齐。

#### P0 对齐与范围锁定（约 1 周）

- 与项目方确认三件事：能否提供 1—2 封脱敏样本、交付物署名规则、是否允许以开源形式产出
- 锁定首期场景：**只做入离职报岗表**，不铺开到体检名单 / 礼券 / 账单
- 确认字段字典：标准报岗表的字段清单、类型、口径说明（社保口径、入离职类型枚举、生效日期规则）
- 产出：需求确认单 + 字段字典 + 范围说明
- **明确不做**：RPA、多语言、通用抽取平台

> 若项目方零响应，P0 降级为"按行业通识假设口径并显式标注假设"，不阻塞后续阶段。

#### P1 闭环样板间（2—3 周 · 对应 M1）

| # | 动作 | 产出 |
|---|---|---|
| 1 | 构造 5 个客户模板的合成样本，覆盖 Excel / PDF / Word / 扫描件 | 合成样本集 |
| 2 | 建"客户模板 → 标准表"字段映射配置机制（配置即数据，不改代码） | 映射配置格式 + 5 家客户规则 |
| 3 | 沉淀三套提示词模板：抽取 / 校验 / 格式化 | 提示词模板 + 说明文档 |
| 4 | 定义异常兜底策略表 | 决策表（扫描件→OCR、加密→人工、缺字段→标红、多语言→字典） |
| 5 | 跑通完整闭环 | 输入样本 → 输出标准报岗表 + 差异标色清单 |

**验收**：5 个模板各跑一遍，输出文件经人工核对无误；换一家新客户模板，只改配置不改代码即可跑通。

#### P2 校验闭环与人机复核（3—4 周 · 对应 M2）

| # | 动作 | 产出 |
|---|---|---|
| 1 | 规则校验层（确定性纯函数）：证件号校验位、日期合法性、枚举合法性、跨字段一致性（如离职日期 ≤ 生效日期） | 校验规则库 + 单测 |
| 2 | AI 复核层：逐字段可信度评分 | 评分机制 |
| 3 | 低置信字段强制进复核队列；差异自动标色 | 复核清单 |
| 4 | 最小复核界面：清单 + 一键修正 + 回写映射规则 | 复核台原型 |
| 5 | 合成集端到端测试，统计字段级准确率与耗时 | 准确率基线报告 |

**验收**：准确率基线可复现；每条校验规则有对应单测。

#### P3 规模化（可选 · 2—3 月 · 对应 M3）

- RPA 触发链路（需项目方环境配合）
- 模板自动匹配：新邮件进来自动识别所属客户模板
- 模板库覆盖 20+ 客户
- 准确率监控看板

> 评级体系明确写着"演示材料权重不低于方案文本"。因此每个阶段都必须产出**可跑、可录屏**的东西，不能只交文档。

### 3.4 分工与边界

| 事项 | 项目方 | 陪跑方 |
|---|---|---|
| 业务口径定义（社保 / 入离职类型规则） | 主责 | 协助整理为可执行规则 |
| 客户模板样本 | 提供（脱敏） | 无则用合成样本替代 |
| 抽取 / 映射 / 校验实现 | 评审 | **主责** |
| 模板库与提示词资产 | 接手维护 | **主责产出** |
| RPA 对接与生产部署 | 主责 | 接口设计协助 |
| 真实数据端到端测试 | 主责（本地） | 提供测试脚本与方法 |

### 3.5 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 项目方零响应（0 报名） | 拿不到脱敏样本与口径确认 | 默认全合成路线；口径按行业通识假设并显式标注，待对方确认后更新 |
| 敏感数据合规 | 不能接触真实数据 | 全程合成数据；如需真实数据，只在对方本地执行 |
| IP 归属未定 | 产出可能无法署名或使用 | P0 阶段先书面约定 |
| 范围蔓延（体检名单 / 礼券 / 账单） | 精力分散，首期做不实 | 首期只做入离职报岗表，扩展场景进 backlog |
| 技术产能倒挂（对方仅 1 名兼职技术） | 交付后无人接手 | 交付物以"可照着改"为唯一标准：配置即数据、规则表驱动、附说明文档 |
| "Agent 形态"与平台评级冲突 | 做出来的东西不是评审要的 | Agent 只做调度与异常决策；抽取 / 映射 / 校验用确定性代码 |

## 四、结论与下一步

**"能不能按这个想法做一个智能体应用"——能做，但要换形态做。**

- 不要做对话式 Agent。平台评级（L4 为"—"）与真实业务需求（配置化 + 规则化 + 复核闭环）都不指向这个形态。
- 要做的是：**抽取—映射—校验—输出闭环 + 一个负责异常决策的 Agent**。这个形态既符合 ★★★ 的评审口径，也真的能解决对方"换客户就重调"的核心短板。
- 最大的价值不在写出抽取代码，而在**模板资产化与校验体系化**——这也是评价文档反复强调的两件事。

**本轮交付到此为止：需求梳理 + 陪跑规划。**

**下一步第一步（不依赖项目方任何输入，可立即开工）：** 构造 5 个客户模板的合成样本（Excel / PDF / Word / 扫描件各一），并搭出"抽取 → 映射 → 校验 → 输出"的最小闭环，即 P1 的前两项。

**需要外部确认的事项（非本方可自决）：**

1. 与项目方是否存在实际接触渠道 —— 决定 P0 能否真实执行，还是降级为假设口径
2. 交付边界（只做规划 / 做到 P1 可演示 / 做到 P2）—— 取决于课程与竞赛的考核节点
3. 知识产权与署名规则
