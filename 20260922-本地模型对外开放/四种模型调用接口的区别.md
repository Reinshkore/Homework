# 四种模型调用接口的区别

> 讲解范围：Ollama API / OpenAI Chat Completions / OpenAI Responses / Anthropic Messages
> 环境对照：ollama 0.34.2 / Windows / `qwen3:0.6b`

---

## 0. 先纠正一个前提

这四者**不是"调用方式"的不同，而是四套独立的 API 契约**。每套有自己的：

- 端点路径
- 请求数据模型
- 响应数据模型
- 状态管理约定

它们做的事情相同（把消息发给模型、取回回答），但**数据怎么组织、历史由谁保管、能力边界在哪**，四家各不相同。

---

## 1. 演进脉络：两条平行支线

理解演进关系，才能理解为什么会有四套。

### 1.1 支线一（OpenAI 内部）：Chat Completions → Responses

**Chat Completions** 是 2023 年的产物，数据模型是**消息数组**（`messages`），设计目标是**一次请求、一次响应**。

用它做智能体（agent）时暴露出的问题：

| 问题 | 具体表现 |
|---|---|
| 多轮对话要全量重发 | 客户端必须每次发送完整历史，长对话昂贵 |
| 工具调用只支持一轮一次 | 无法把「模型说话 → 调工具 → 拿结果 → 再说话」串进单次请求 |
| Prompt 缓存命中率低 | 官方内部测试称 Responses 缓存利用率提升 40%–80% |
| 推理过程被丢弃 | 思考型模型的推理 token 在轮次之间不保留 |

**Responses** 是为解决上述问题设计的，核心改动是**把「消息」换成「条目（Items）」**——这是数据模型层面的重构，不是加几个参数。

### 1.2 支线二（跨厂商）：Anthropic Messages

**Anthropic Messages 不是 OpenAI 的演化分支**，而是并行发展的另一条路。

它和 Responses 属于**同时代、面向同类问题（智能体）的竞争设计**。两者都把 computer use、web search、MCP 作为一等公民。

关键差异：

- Anthropic 暴露**完整的思维链原文**，OpenAI 只给**摘要**
- Anthropic 的 prompt caching 是**开发者可显式控制**的特性，OpenAI 的缓存是**隐式**的
- Anthropic 把 system prompt 放在**独立的 `system` 字段**，不混进消息数组

### 1.3 Ollama 的定位

Ollama **不发明 API**，而是在自己的服务上**实现别人的契约**：

| 契约 | 归属 | Ollama 的角色 |
|---|---|---|
| `/api/chat` | Ollama 自有 | 原生实现 |
| `/v1/chat/completions` | OpenAI | 兼容层适配器 |
| `/v1/responses` | OpenAI | 兼容层适配器（仅无状态） |
| `/v1/messages` | Anthropic | 兼容层适配器（子集） |

**重要**：所有适配器都是**部分实现**。ollama 只翻译它认识的部分，其余字段**静默忽略**，不报错。这是后面所有坑的根源。

## 2. 四个最关键的区别

### 2.1 区别一：消息 vs 条目（最根本的数据模型差异）

| 接口 | 输入模型 |
|---|---|
| Ollama 原生 | `messages`: `[{role, content}, ...]` |
| Chat Completions | `messages`: `[{role, content}, ...]` |
| Responses | `input`: **条目流（Items）**，`message` 只是其中一种类型 |
| Anthropic Messages | `messages`，但 **`system` 是独立顶层字段** |

**为什么从「消息」改成「条目」**：

Chat Completions 把多种关注点**粘**在一条 message 里——文本、工具调用、工具结果都挤在同一对象的字段中。当一轮对话里同时出现「模型说了句话 → 调了工具 → 又说了句话」，这个结构会变得难以表达。

条目模型把每种动作拆成独立类型：

- `message` —— 一条文本消息
- `function_call` —— 模型发起的工具调用
- `function_call_output` —— 工具返回结果
- `reasoning` —— 推理内容

**好处**：混合序列（文本 + 工具调用 + 检索 + 代码执行）能作为**单一输出流**清晰地表达。

**代价**：结构更复杂，且 `n` 参数被移除（不再支持并行生成多个候选）。

**Anthropic 的差异值得一提**：`system` 提到顶层是**显式的设计选择**——它强调 system 与对话消息性质不同，不应混在一起。而 Chat Completions 把 system 作为普通 role 塞进数组。

### 2.2 区别二：状态归属（最容易踩坑）

| 接口 | 状态 |
|---|---|
| Ollama 原生 | 无状态 |
| Chat Completions | 无状态，客户端拥有历史 |
| Responses | **有状态可选**（`store: true` + `previous_response_id`） |
| Anthropic Messages | 无状态，客户端管理 |

**行话陷阱**：各家 SDK 都有「库替你保留历史」的外观，底层实现分两类：

**第一类——库替你存，但每次全量重发**

OpenAI SDK 里，Chat Completions 的多轮对话是通过**库帮你维护 `messages` 列表**实现的。但每次请求仍然把**完整历史重发一遍**。服务端不存任何东西。

**第二类——服务端真的存了会话**

Responses 的 `previous_response_id` 是**服务端保持了会话状态**。下一次请求只需带新一轮内容，历史由服务端关联。

**对本地部署的直接后果**：

ollama 只实现了 Responses 的**无状态版本**。官方文档明确说明：

```
Only the non-stateful flavor is supported
(i.e., there is no previous_response_id or conversation support)
```

**这意味着**：如果在本地用 `/v1/responses` 却照云端文档写 `previous_response_id` 来续接对话——

- 它**不会生效**
- 它**不会报错**
- 每次请求都是全新对话，模型完全不记得上一轮

**工程建议**：无论用哪套接口，都**自己持有会话状态**。把 ollama 当作「模型执行服务」，而不是「应用层的对话数据库」。

客户端持有状态的好处：

- 可限制上下文增长（裁剪、摘要）
- 可对旧轮次做脱敏或改写
- 请求可确定性重放，便于复现问题
- 可审计、可切换模型或供应商

### 2.3 区别三：系统提示词的位置

| 接口 | 写法 |
|---|---|
| Ollama 原生 | `messages` 数组里的一条 `{"role": "system", "content": ...}` |
| Chat Completions | 同上 |
| Responses | **`instructions` 顶层字段**（也接受 message 形式） |
| Anthropic Messages | **`system` 顶层字段**（string 或 array） |

迁移代码时这是必改项。

### 2.4 区别四：内建工具（本质性差异，适配层无法弥补）

| 接口 | 内建服务端工具 |
|---|---|
| Ollama 原生 | 无 |
| Chat Completions | 无（只有客户端侧函数调用） |
| Responses | web search、file search、code interpreter、computer use、MCP |
| Anthropic Messages | web search、computer use、MCP |

**为什么无法靠适配弥补**：这些工具**运行在服务提供商的服务器上**。

- 你的笔记本无法替 OpenAI 执行 code interpreter
- ollama 无法提供 web search（它只能跑本地模型）

**对本地部署的意义**：Responses 的核心卖点「agentic by default」，**只有连云端才用得上**。在 ollama 上，它退化成「另一种形状的 chat 接口」。

## 3. 逐接口详解

### 3.1 Ollama 原生 API

**端点**：`/api/chat`、`/api/generate`、`/api/tags`、`/api/embed`、`/api/ps`

**特点**：能力最全，不被适配层过滤。

```python
import json, urllib.request

payload = {
    "model": "qwen3:0.6b",
    "messages": [
        {"role": "system", "content": "你是一个简洁的技术助手"},
        {"role": "user", "content": "解释一下什么是递归"}
    ],
    "think": False,        # 原生接口专有：布尔值可彻底关闭思维链
    "stream": False,
    "format": {            # 结构化输出：传 JSON Schema
        "type": "object",
        "properties": {"answer": {"type": "string"}},
        "required": ["answer"]
    }
}
req = urllib.request.Request(
    "http://127.0.0.1:11434/api/chat",
    data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"}
)
with urllib.request.urlopen(req, timeout=300) as r:
    result = json.loads(r.read().decode("utf-8"))
print(result["message"]["content"])
```

**响应结构**：

```json
{
  "model": "qwen3:0.6b",
  "created_at": "2026-10-10T01:20:00Z",
  "message": {"role": "assistant", "content": "递归是..."},
  "done": true,
  "done_reason": "stop",
  "prompt_eval_count": 48,
  "eval_count": 12
}
```

**独有优势**：

| 能力 | 说明 |
|---|---|
| `think` 布尔值 | 可**彻底关闭**思维链（兼容接口做不到） |
| `format` JSON Schema | 解码层约束输出结构 |
| `/api/ps` | 查看当前加载的模型与剩余驻留时间 |
| 原生流式 | NDJSON 格式（逐行 JSON） |

### 3.2 OpenAI Chat Completions

**端点**：`/v1/chat/completions`

**地位**：**事实标准**。被 Anthropic 兼容端点、Azure、以及绝大多数开源推理服务器实现。跨厂商可移植性最好。

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:11434/v1", api_key="ollama")

resp = client.chat.completions.create(
    model="qwen3:0.6b",       # 注意：必须是 ollama 的模型 tag，不是 OpenAI 的模型名
    messages=[
        {"role": "system", "content": "你是一个简洁的技术助手"},
        {"role": "user", "content": "解释一下什么是递归"},
    ],
    stream=False,
)
print(resp.choices[0].message.content)
```

**响应结构**：

```json
{
  "id": "chatcmpl-123",
  "object": "chat.completion",
  "choices": [{
    "index": 0,
    "message": {"role": "assistant", "content": "递归是..."},
    "finish_reason": "stop"
  }],
  "usage": {"prompt_tokens": 48, "completion_tokens": 12, "total_tokens": 60}
}
```

**ollama 在 Chat Completions 上的限制**（已确认不支持）：

| 字段 | 状态 |
|---|---|
| `logprobs` | 不支持 |
| `tool_choice` | 不支持 |
| `n`（并行生成） | 不支持 |
| `logit_bias` | 不支持 |
| 图片 URL | 不支持（须传 base64） |
| **上下文长度** | **无法设置**（OpenAI 参数里没这个概念） |

**`reasoning_effort` 的行为**：ollama 会把 `low` / `medium` / `high` 映射到内部 Think 参数（源码 `openai/openai.go:106-125`）。**但只能调级别，无法彻底关闭思维链。** 要彻底关闭只能走原生接口的 `think: false`。

### 3.3 OpenAI Responses

**端点**：`/v1/responses`（ollama 需 v0.13.3+）

```python
resp = client.responses.create(
    model="qwen3:0.6b",
    instructions="你是一个简洁的技术助手",      # system 提示词的位置不同
    input="解释一下什么是递归",                  # input 而非 messages
)
print(resp.output_text)
```

**ollama 支持的程度**：

| 特性 | 支持 |
|---|---|
| Streaming | ✅ |
| Tools（函数调用） | ✅ |
| Reasoning summaries | ✅（思考型模型） |
| Stateful 请求 | ❌ |

**支持的请求字段**：

| 字段 | 支持 |
|---|---|
| `model` | ✅ |
| `input` | ✅ |
| `instructions` | ✅ |
| `tools` | ✅ |
| `stream` | ✅ |
| `temperature` | ✅ |
| `top_p` | ✅ |
| `max_output_tokens` | ✅ |
| `previous_response_id` | ❌ |
| `conversation` | ❌ |
| `truncation` | ❌ |

**判断**：在 ollama 上，Responses 相比 Chat Completions **几乎没有额外增益**——它的核心优势（服务端状态、内建工具）在本地都不可用。除非你已有针对 Responses 写的代码，否则没有理由在本地选它。

### 3.4 Anthropic Messages

**端点**：`/v1/messages`（ollama 需 v0.14.0+）

```python
import anthropic

client = anthropic.Anthropic(
    base_url="http://127.0.0.1:11434",
    api_key="ollama",          # SDK 要求必填，ollama 忽略此值
)

message = client.messages.create(
    model="qwen3:0.6b",
    max_tokens=1024,           # 必填参数，与其他接口不同
    system="你是一个简洁的技术助手",   # system 独立顶层字段
    messages=[{"role": "user", "content": "解释一下什么是递归"}],
)
print(message.content[0].text)   # 注意：content 是块数组，不是字符串
```

**响应结构（与其他三套差异最大）**：

```json
{
  "id": "msg_123",
  "type": "message",
  "role": "assistant",
  "model": "qwen3:0.6b",
  "content": [
    {"type": "text", "text": "递归是..."}
  ],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 12, "output_tokens": 150}
}
```

**三个显著的结构差异**：

| 差异 | 说明 |
|---|---|
| `max_tokens` 必填 | 其他接口是可选 |
| `system` 顶层字段 | 不混进 messages 数组 |
| `content` 是**块数组** | 须取 `content[0].text`，不是 `content` 直接就是字符串 |

**ollama 支持的特性**：多轮对话、system prompts、流式、视觉（图片）、工具调用、扩展思考。

**已确认不支持或部分支持**：

| 项 | 状态 |
|---|---|
| 强制 `tool_choice` | ❌ 不支持 |
| prompt caching | ❌ 不支持 |
| Batches API | ❌ 不支持 |
| PDF 输入 | ❌ 不支持 |
| 图片 URL | ❌ 不支持 |
| `budget_tokens` | ⚠️ 被接受但**不生效** |
| token 计数 | ⚠️ 仅为近似值 |

**注意 `budget_tokens` 这一项**：这是典型的「被接受但静默忽略」——请求成功、不报错、但限制未生效。与 `previous_response_id` 是同类问题。

**流式事件类型**（Anthropic 格式，SSE）：

| 事件 | 含义 |
|---|---|
| `message_start` | 响应开始，含初始元数据 |
| `content_block_start` | 内容块开始（text / thinking / tool_use） |
| `content_block_delta` | 增量内容 |
| `content_block_stop` | 内容块结束 |
| `message_delta` | 消息级更新（stop_reason、usage） |
| `message_stop` | 消息结束 |
| `ping` | 保活 |
| `error` | 错误 |

**用途**：让 Claude Code 这类按 Anthropic 协议设计的工具接本地模型。

## 4. 横向对照总表

### 4.1 基础对照

| 维度 | Ollama 原生 | Chat Completions | Responses | Anthropic Messages |
|---|---|---|---|---|
| 端点 | `/api/chat` | `/v1/chat/completions` | `/v1/responses` | `/v1/messages` |
| 输入模型 | `messages` | `messages` | `input` 条目流 | `messages` |
| 系统提示词 | messages 内 | messages 内 | `instructions` | `system` 顶层 |
| 状态 | 无状态 | 无状态 | 可选有状态 | 无状态 |
| 输出结构 | `message.content` | `choices[0].message.content` | `output_text` | `content[0].text` |
| 必填参数 | model | model | model, input | model, max_tokens |
| 流式格式 | NDJSON | SSE | 类型化事件 | SSE |
| 内建工具 | 无 | 无 | 有（6 种） | 有（3 种） |
| API Key | 不需要 | SDK 要求（忽略） | SDK 要求（忽略） | SDK 要求（忽略） |

### 4.2 ollama 上的实际支持度

| 契约 | 端点 | 需 ollama 版本 | 支持程度 |
|---|---|---|---|
| 原生 | `/api/chat` | 任意 | 完整 |
| Chat Completions | `/v1/chat/completions` | 较早 | 较完整，若干字段不支持 |
| Responses | `/v1/responses` | **v0.13.3+** | 仅无状态 |
| Anthropic Messages | `/v1/messages` | **v0.14.0+** | 子集 |

### 4.3 特性支持矩阵

| 特性 | Ollama 原生 | Chat Completions | Responses | Anthropic Messages |
|---|---|---|---|---|
| 多轮对话 | ✅（客户端管理） | ✅（客户端管理） | ✅（云端服务端管理） | ✅（客户端管理） |
| 流式 | ✅ | ✅ | ✅ | ✅ |
| 工具调用 | ✅ | ✅ | ✅ | ✅ |
| 结构化输出 | ✅ `format` | ✅ `response_format` | ✅ `text.format` | （basetool 形式） |
| 视觉 | ✅ | ✅（仅 base64） | ✅ | ✅（仅 base64） |
| 关闭思维链 | ✅ `think: false` | ❌ 仅调级别 | ❌ | ⚠️ 仅 `budget_tokens`（不生效） |
| 设置上下文长度 | ✅ `num_ctx` / Modelfile | ❌ | ❌ | ❌ |
| 服务端会话 | ❌ | ❌ | ❌（本地不支持） | ❌ |
| 内建联网检索 | ❌ | ❌ | ❌（本地不支持） | ❌（本地不支持） |

## 5. 该选哪套

### 5.1 决策依据

| 你的处境 | 选择 | 理由 |
|---|---|---|
| 学习模型能力；要用 `think` 布尔值；要用 `format` | **Ollama 原生** | 能力最全，不被适配层过滤 |
| 已有 OpenAI 代码；想跨厂商可移植 | **Chat Completions** | 事实标准，被最广泛实现 |
| 要让 Claude Code 等工具接本地模型 | **Anthropic Messages** | 这类工具按此协议设计 |
| 连云端 OpenAI，需要内建工具 + 会话保持 | Responses | 本地部署下这些优势用不到 |
| 纯本地 + 追求最少坑 | **Ollama 原生** | 少一层适配，少一层静默忽略 |

### 5.2 两条纪律（无论选哪套都要遵守）

**纪律一：只用你验证过支持的字段。**

不要照搬云端文档的请求对象。适配层的危险不在于「报错」，而在于「**接受但忽略**」——请求成功返回 200，但你要的功能根本没生效。

用之前先测：确认该字段**真的产生了效果**，而不只是没报错。

**纪律二：把上下文大小当部署配置，不当请求参数。**

三套兼容接口都无法设置上下文长度。只能通过：

- Modelfile 里的 `PARAMETER num_ctx`
- 或环境变量 `OLLAMA_CONTEXT_LENGTH`

这一点对本地部署尤其重要——当前默认仅 4096 token（模型本身支持 40960），而它**无法通过任何兼容接口的请求参数修改**。

### 5.3 迁移改动清单

从 Chat Completions 迁到其他接口时，必改项：

| 迁到 | 必改 |
|---|---|
| Ollama 原生 | 端点 `/v1/chat/completions` → `/api/chat`；响应取 `message.content` 而非 `choices[0]...`；流式从 SSE 改 NDJSON |
| Responses | `messages` → `input`；system 移到 `instructions`；响应取 `output_text`；**注意 `previous_response_id` 本地无效** |
| Anthropic Messages | 端点改 `/v1/messages`；`max_tokens` 变必填；system 提到顶层；响应取 `content[0].text` |

## 6. 关键概念速查

| 概念 | 说明 |
|---|---|
| **消息（Message）** | `{role, content}`，Chat Completions 的基本单位 |
| **条目（Item）** | Responses 的基本单位，是多种类型的联合（message / function_call / reasoning…） |
| **无状态** | 服务端不保存历史，客户端每次全量重发 |
| **有状态** | 服务端保存会话，客户端只传 ID 续接（`previous_response_id`） |
| **NDJSON** | 每行一个 JSON 对象，ollama 原生接口的流式格式 |
| **SSE** | Server-Sent Events，`data:` 前缀 + `[DONE]`，Chat Completions / Anthropic 使用 |
| **兼容层适配器** | 把外部契约翻译成内部格式的中间件，只翻译认识的部分 |
| **静默忽略** | 字段被接受但不生效，不报错——适配层最危险的失败模式 |
| **内建工具** | 运行在服务商服务器上的工具，本地部署无法提供 |
