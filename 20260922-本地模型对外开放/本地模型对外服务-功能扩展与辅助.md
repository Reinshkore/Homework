# 本地模型对外服务的功能扩展与辅助

> 讲解场景：已完成 ollama 本地部署 + 局域网对外服务的基础链路，探讨后续可扩展方向
> 环境对照：ollama 0.34.2 / Windows / `qwen3:0.6b` / 局域网 `10.201.17.177`

---

## 0. 先建立判断框架：为什么有些扩展有用，有些是白费力气

**核心原理：本地模型服务存在一个「不可能三角」，任何扩展方案都必须在三者之间取舍。**

| 要素 | 含义 |
|---|---|
| **算力** | 你能提供多少推理能力（模型参数量 × 硬件吞吐） |
| **访问** | 服务能被多少人/多少并发访问 |
| **私有** | 数据与模型的控制权是否留在本地 |

三者最多同时满足两个：

- 保**算力 + 私有** → 只能服务极少数人（当前你的处境）
- 保**访问 + 私有** → 算力必然被稀释（多人共享同一张小卡）
- 保**算力 + 访问** → 必须牺牲私有（上云，或数据出本地）

**这个三角之所以成立的底层原因是自回归解码的性质**：大模型是逐 token 生成的，是一个串行过程。

- 生成 1 个 token 通常只涉及一次矩阵乘向量运算（matrix-vector，属于**访存瓶颈**）
- 而训练/预填充阶段可以并行（矩阵乘矩阵，**算力瓶颈**）

GPU 的显存带宽有限，所以在解码阶段，算力严重过剩而带宽成为瓶颈。**批处理（batching）正是把这个瓶颈利用起来的手段**——把多个请求合成一个批次，一次访存服务多个请求，从而摊薄单位成本。

这也解释了两个常见现象：

1. **为什么并发很小时 GPU 利用率很低** —— 带宽瓶颈，算力在空转
2. **为什么 ollama 默认 `OLLAMA_NUM_PARALLEL=1`** —— 一次只处理一个请求，其余排队

## 1. 场景修正（重要）

上一轮文档里假设的「手机连同一 WiFi 访问 `10.201.17.177`」有一个隐含前提：**笔记本与手机处在同一网段内**。

这带来两个必须正视的约束：

| 约束 | 说明 |
|---|---|
| **网络移动性** | 笔记本一旦换网络、离开局域网，手机就连不上 |
| **硬件天花板** | 笔记本属于「小内存 + 无独显」量级：i5-1340P，39.7 GiB 内存，**无可用独显**（Intel Iris Xe 集显被跳过），CPU 推理约 41–46 tokens/s（0.6B 模型） |

**由此推出第一位的扩展方向是「让服务不依赖同一局域网」**，即内网穿透 —— 这不是锦上添花，而是当前形态的必要补全。

**由此也推出一个必须接受的边界**：`10.201.17.177` 属于 `10.0.0.0/8` 私有网段，处于 NAT 之后，且你没有出口设备管理权。**端口映射这条路不通**，公网访问只能靠出站长连接（内网穿透）或云服务器。

## 2. 功能扩展地图

按「加能力」还是「加支撑」分两大类。下面按依赖关系组织，**不要跳在第 1、2 节之前做后面的**。

### 2.1 能力扩展（服务能做什么）

| 方向 | 加的是什么能力 | 适配你当前条件的成本 | 优先级 |
|---|---|---|---|
| **流式输出** | 首 token 延迟从数秒降到亚秒级 | 极低（改一个参数） | ★★★ |
| **结构化输出** | 让模型返回可被程序解析的 JSON | 极低（`format` 参数） | ★★★ |
| 视觉多模态 | 识图能力（截图、表格、公式） | 需换模型（≈2–6 GB） | ★★ |
| 工具调用 / Function Calling | 让模型能查天气、算数、查数据库 | 低，但小模型成功率低 | ★★ |
| 嵌入 Embeddings | 本地检索、去重、聚类 | 低（小模型 ≈300 MB） | ★★ |
| 重排 Rerank | 提升检索质量 | 中 | ★ |
| 语音（ASR + TTS） | 语音输入输出 | 中，需额外模型 | ★ |
| 图像生成 | 文生图 | 高，算力要求大 | — |

### 2.2 支撑扩展（服务怎么活得更稳、更安全）

| 方向 | 解决什么问题 | 优先级 |
|---|---|---|
| **网络穿透** | 跨网络访问 | ★★★ |
| **反向代理 + 鉴权** | 裸端口无保护 | ★★★ |
| **可观测性** | 不知道服务状态与用量 | ★★ |
| **持久化与会话管理** | 重启即丢上下文 | ★★ |
| 模型生命周期管理 | 加载卸载、换模型 | ★ |
| 前端界面 | 给非技术用户用 | ★★ |
| 缓存与降级 | 省算力、抗故障 | ★ |
| 多模型路由与量化 | 按任务分配资源 | ★ |

## 3. 能力扩展详解

### 3.1 流式输出（Streaming）—— 优先级最高

**原理**：非流式模式下，服务端要等**最后一个 token 生成完**才一次性返回完整响应。用户面对的是一段静止的等待。

流式模式下，每生成一个 token 就立刻通过 HTTP chunked 传输推给客户端。**总耗时几乎不变，但感知延迟从"数秒全等待"变成"亚秒即见字"**。

这在本地部署上尤为关键——因为你的硬件是 CPU 推理，长回答可能需要十几秒到几十秒，不流式的话体验很差。

**实现**（两套接口写法不同）：

原生接口：

```python
import json, urllib.request

payload = {
    "model": "qwen3:0.6b",
    "messages": [{"role": "user", "content": "讲讲递归"}],
    "stream": True,
    "think": False,
}
req = urllib.request.Request(
    "http://127.0.0.1:11434/api/chat",
    data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"},
)
with urllib.request.urlopen(req, timeout=300) as resp:
    for line in resp:
        if not line.strip():
            continue
        chunk = json.loads(line.decode("utf-8"))
        piece = chunk.get("message", {}).get("content", "")
        if piece:
            print(piece, end="", flush=True)
        if chunk.get("done"):
            break
```

OpenAI 兼容接口：

```python
stream = client.chat.completions.create(
    model="qwen3:0.6b",
    messages=[{"role": "user", "content": "讲讲递归"}],
    stream=True,
)
for chunk in stream:
    delta = chunk.choices[0].delta.content
    if delta:
        print(delta, end="", flush=True)
```

**关键实现细节**：原生接口的流式响应是 **NDJSON**（每行一个独立 JSON 对象），不是标准 SSE。所以解析时要**逐行读、逐行 `json.loads`**，不能把整个响应体当一个大 JSON 解析。OpenAI 兼容接口用的是标准 SSE（`data: {...}` + `[DONE]`），但 openai 库已经帮你处理了。

**注意 `flush=True`**：不加的话 Python 会缓冲输出，流式的视觉效果会被破坏。

### 3.2 结构化输出（Structured Output）

**原理**：模型生成的是自然语言，程序无法可靠解析。但很多任务真正需要的是**结构化数据**——比如"从这段文本里抽出人名、时间、金额"，你要的是 JSON，不是一句中文描述。

**做法**：ollama 支持 `format` 参数，传入 JSON Schema，服务端会**约束解码过程**，保证输出符合该结构（而不是生成完再检查）。

```python
payload = {
    "model": "qwen3:0.6b",
    "messages": [{"role": "user", "content": "从「张三明天下午三点来开会」抽取信息"}],
    "format": {
        "type": "object",
        "properties": {
            "name":   {"type": "string"},
            "time":   {"type": "string"},
            "action": {"type": "string"},
        },
        "required": ["name", "time", "action"],
    },
    "stream": False,
}
```

返回值放在 `message.content` 里，但它是一个**可以被 `json.loads` 直接解析的字符串**。

**为什么这比"让模型输出 JSON"更可靠**：纯提示词方式（"请用 JSON 格式回答"）只是给模型的建议，模型仍可能输出带 markdown 代码块包裹、或多说一句解释的内容。`format` 参数是在**解码层面**约束，从采样阶段就排除掉不符合语法的 token。

**这是把你的脚本从"聊天玩具"升级为"可用组件"的关键一步**——有了稳定结构，后续才能接入自动化流程。

### 3.3 视觉多模态

**原理**：多模态模型在输入侧增加了一个视觉编码器（通常是一个 ViT 类结构）。图片被切成固定数量的 patch，每个 patch 编码成一个向量，然后**映射到与文本 token 相同的语义空间**，从而能和文本 token 一起送进同一个 Transformer。

**关键认知**：对模型而言，图片不是"看到的"，而是**被转译成了一串 token**。所以：
- 图片会**占用上下文长度**（一张图可能等价几百个 token）
- 分辨率越高，占用的 token 越多
- 上下文有限 → 一次能看的图片数量和分辨率都受限

**可用的 ollama 视觉模型**（体积为粗略量级，以 `ollama pull` 实际为准）：

| 模型 | 体积量级 | 适用 |
|---|---|---|
| `llava:7b` | ≈4.7 GB | 通用图像描述 |
| `qwen2.5vl:3b` | ≈3 GB | 中文场景较好 |
| `moondream` | ≈1.7 GB | 轻量，纯 CPU 可跑 |
| `minicpm-v` | ≈5.5 GB | 文档/表格 OCR 较强 |

调用方式（原生接口，把图片以 base64 放进 message）：

```python
import base64

with open("screenshot.png", "rb") as f:
    img_b64 = base64.b64encode(f.read()).decode()

payload = {
    "model": "qwen2.5vl:3b",
    "messages": [{
        "role": "user",
        "content": "这张图里有什么",
        "images": [img_b64],
    }],
    "stream": False,
}
```

**对你的成本提醒**：CPU 推理下，7B 级视觉模型的速度会明显慢于 0.6B（参数量约 12 倍）。若要走这条路，优先试 1.7–3B 量级。

**一个实用场景**：结合你已经在做的事——把截图交给本地视觉模型做 OCR 或内容提取，全程不出本地，这对处理含敏感信息的截图是有价值的。

### 3.4 工具调用（Function Calling / Tool Calling）

**原理**：模型本身不能执行任何操作，它只能输出文本。工具调用的本质是**约定一种输出格式**：

1. 请求时告诉模型"有这么几个函数可用，名字和参数如下"
2. 模型判断需要调用时，输出一段**结构化的调用意图**（函数名 + 参数 JSON）
3. **你的程序**在本地真正执行该函数
4. 把执行结果作为新消息回传，模型据此生成最终回答

**必须理解**：模型不执行任何东西，它只是"提议调用"。执行权和安全性完全在你的代码侧。

```python
tools = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "查询指定城市的天气",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string", "description": "城市名"}},
            "required": ["city"],
        },
    },
}]

resp = client.chat.completions.create(
    model="qwen3:0.6b",
    messages=[{"role": "user", "content": "北京天气怎么样"}],
    tools=tools,
)
if resp.choices[0].message.tool_calls:
    call = resp.choices[0].message.tool_calls[0]
    print(call.function.name, call.function.arguments)  # 模型提议的调用
    # 接下来由你的代码执行，再把结果回传
```

**现实评估**：`qwen3:0.6b` 参数量小，工具调用的**准确率和稳定性都不高**——可能出现该调不调、参数编造、格式错误。要用这个功能，建议换 7B 以上模型。这也是"算力 ↔ 能力"取舍的直接体现。

### 3.5 嵌入（Embeddings）—— 被低估的方向

**原理**：嵌入模型把文本映射成一个**定长向量**（比如 1024 维），使得**语义相近的文本向量距离也相近**。这不是生成模型，而是编码模型，因此：
- 模型很小（几百 MB）
- 速度快
- 不需要自回归解码，**可真正并行**，CPU 上也能接受

**与生成模型的本质区别**：生成模型逐 token 串行输出；嵌入模型一次前向传播出一个向量。所以嵌入任务在 CPU 上的性能远好于生成任务。

```python
resp = client.embeddings.create(
    model="nomic-embed-text",
    input=["本地部署的优势", "私有化部署的好处"],
)
# resp.data[0].embedding 是一个 float 列表
```

**为什么这个方向对你特别合适**：

| 场景 | 机制 |
|---|---|
| 语义搜索 | 把资料建成向量库，查询时按相似度召回 |
| 去重 | 高度相似的文本向量余弦相似度接近 1 |
| 聚类 | 给文档按语义分组 |

**这直接构成了 RAG 的基础**。而且 ollama 还支持参数 `"truncate": false` 来避免输入被静默截断——做嵌入时要注意长文本会怎样被切分。

### 3.6 RAG —— 把扩展串起来的关键组装

**RAG（检索增强生成）的动机**：模型的知识只到训练数据截止时间，且**无法知道你本地的私有资料**。微调成本高，而 RAG 的思路是：**不改模型，改输入**——在提问前，先从你的资料库里检索出相关片段，拼进提示词。

**流程**（每一步都对应上面讲过的能力）：

```
离线阶段（建库）
  资料 → 切块(chunking) → 嵌入模型编码 → 存入向量库

在线阶段（问答）
  用户提问 → 嵌入模型编码 → 向量库相似度检索 → 取出Top-K片段
         → 拼成提示词（"根据以下资料回答…"）→ 生成模型 → 回答
```

**为什么必须先做 3.5（嵌入）**：RAG 的检索环节依赖向量相似度，没有嵌入就没有检索。

**关键工程问题——切块（chunking）**：把一个长文档切成多大的片段，直接决定检索质量。

- 切太小 → 语义不完整，检索到的片段看不懂
- 切太大 → 混入无关内容，稀释了相关信息，且占用上下文

这是 RAG 实践中最需要反复调试的参数，没有通用最优值。

**诚实的评估**：RAG 真正的技术含量在**检索质量**（切块策略、检索算法、是否需要重排），而不是生成——生成环节 0.6B 模型也够用，因为答案就在检索到的资料里。**但对你的场景，RAG 有更轻量的替代方案**，见 3.7。

### 3.7 轻量替代：系统提示词 + 上下文缓存

对"让模型了解我的资料"这个需求，不一定要上完整 RAG。有个更直接的方案：

**做法**：把所需资料直接写进 `system` 消息。

**为什么这在本地部署下可行**——这是你环境里一个容易被忽略的机制：

从服务日志可以看到，ollama 启用了 **prompt cache**（提示词缓存，上限 8192 MiB）：

```
srv load_model: prompt cache is enabled, size limit: 8192 MiB
srv prompt_save: - saving prompt with length 59, total state size = 6.454 MiB
srv get_availabl: - selected slot by LCP similarity, f_sim_best = 1.000
```

**机制解释**：

1. 第一次请求时，系统把提示词在前向传播过程中算出的 KV 缓存（key-value cache）保存下来
2. 下次请求时，用 **LCP（最长公共前缀）相似度**比对：与缓存的提示词前缀越相似，越能复用
3. 命中的部分**不需要重新计算**，直接加载缓存的 KV 状态

日志里那次 `f_sim_best = 1.000`（相似度 100%）正是复用生效的证据。

**实践含义**：如果每次对话的 `system` 提示词部分固定不变（比如总是一份同样的资料或同一套规则），那么这部分**只在第一次真正计算**，后续每次都被缓存复用，几乎不额外耗时。

**这给了你一条低成本路线**：

```
方案 A（重）：RAG  → 向量库 + 嵌入 + 检索 + 拼接   适合资料量很大（数 MB 以上）
方案 B（轻）：固定 system 提示词 + 依赖 prompt cache  适合资料量较小（几 KB ~ 几十 KB）
```

**判断标准是资料量**：

| 资料规模 | 建议 |
|---|---|
| 几 KB 以内 | 直接写进 system 提示词 |
| 几十 KB | 写进 system，靠缓存复用，注意上下文长度上限 |
| 数百 KB 以上 | 必须上 RAG，否则超出上下文 |

**顺带一个关键约束**：你的默认上下文只有 4096 token（日志：`vram-based default context` → `default_num_ctx=4096`），而模型本身支持 40960。原因是 ollama 按可用显存推算默认值，你无独显，所以取了下限。需要通过 `OLLAMA_CONTEXT_LENGTH` 环境变量手动调大，但要注意 **KV 缓存占用会随之线性增长**——4096 token 时 KV 缓存已占 448 MiB。

## 4. 支撑扩展详解

### 4.1 网络穿透 —— 当前最必要的补全

**动机**：ollama 绑定 `0.0.0.0` 只解决"局域网内可达"。一旦笔记本换网络，手机就连不上。

**原理**：内网穿透反转了连接方向。

```
常规思路（不可行）：
  外部设备 --主动连接--> 你的电脑    ✗ 被 NAT 挡住，且无端口映射权限

穿透思路（可行）：
  你的电脑 --主动建立长连接--> 中转服务器 <--外部设备连接中转服务器
```

关键在**方向**：你的电脑主动**出站**连接中转服务器，这个方向的连接 NAT 是允许的（NAT 只为出站连接维护映射表）。连接建立后长期保持，外部的请求经中转服务器沿这条已建立的通道回推。

**这就是为什么穿透不需要公网 IP、不需要端口映射权限。**

**方案对比**：

| 方案 | 原理 | 需要域名 | 成本 | 备注 |
|---|---|---|---|---|
| **Cloudflare Tunnel** | 官方 `cloudflared` 客户端出站长连接 | 需要 | 免费 | 自动 HTTPS，配置最简单 |
| frp | 自建需公网 IP 的中转服务端 | 可选 | 需自备服务器 | 可控性最强 |
| ngrok | 商业中转 | 免费版随机域名 | 免费档有限制 | 上手最快 |
| Tailscale | 基于 WireGuard 的虚拟组网 | 否 | 免费档 | **并非穿透，而是把设备组进同一虚拟内网** |

**Tailscale 值得单说**：它给每台设备分配一个虚拟 IP，设备之间像在同一局域网。你的手机装上后，就能用虚拟 IP 访问笔记本，**不需要暴露任何公网端口**。这在安全性上远优于把 11434 暴露到互联网。

**安全警告（不可省略）**：ollama 无任何鉴权。穿透到公网而不加保护，等于把算力和磁盘交给所有人。**穿透必须与 4.2 的反向代理一起做，不能单独上。**

### 4.2 反向代理 + 鉴权

**动机**：11434 是已知被大规模扫描的端口。ollama 本身没有 API Key、没有用户体系、没有访问控制。

**架构**：

```
外部客户端 --HTTPS--> 反向代理（TLS终止 + API Key校验 + 限流 + 日志）
                          --HTTP--> ollama:11434（仅监听回环）
```

**关键设计点**：此时 `OLLAMA_HOST` 应**保持默认的 `127.0.0.1`**，不要设 `0.0.0.0`。让 ollama 只接受本机的反向代理连接，安全边界由反向代理守住。

反向代理承担四件事：

| 职责 | 作用 |
|---|---|
| TLS 终止 | 对外只暴露 HTTPS，避免明文传输（API Key 明文走网络等于没设） |
| API Key 校验 | 无 Key 的请求直接拒绝，不进 ollama |
| 限流 | 防止被当作免费算力池刷爆 |
| 日志 | 记录来源，便于发现滥用 |

**一个必须知道的坑**：很多反向代理有**响应缓冲（response buffering）**机制，会把后端返回的数据攒够一批再转发给客户端。这会**彻底破坏流式输出**——用户在浏览器里看到的仍是一次性出现全文。

配置时需要显式关闭缓冲（Nginx 对应 `proxy_buffering off`，并设置 `proxy_cache off`）。这个坑很隐蔽，因为非流式模式下一切正常，只有流式会体现。

### 4.3 可观测性

**动机**：不知道服务是否活着、模型是否在内存、谁在调用、慢在哪。

| 层次 | 手段 | 能得到什么 |
|---|---|---|
| 存活 | `/api/version`、`/api/tags` 探测 | 服务是否在 |
| 模型状态 | `/api/ps` | 哪些模型在内存、剩余驻留时间 |
| 请求日志 | ollama 服务端日志 | 每个请求的耗时、token 数、缓存命中 |
| 资源 | 系统监控 | CPU/内存占用，判断是否过载 |
| 用量 | 自建统计 | 调用次数、token 总量（本地无计量，需自己记） |

**从服务日志能读出的关键指标**（你日志里出现过的）：

```
prompt eval time =     62.09 ms /    13 tokens    ← 提示词处理耗时
eval time =          6299.55 ms /   272 tokens    ← 生成耗时
srv get_availabl: selected slot by LCP similarity ← 缓存是否命中
```

**判断性能瓶颈的方法**：
- `prompt eval` 高 → 输入长（提示词、资料、图片）导致，考虑缩减输入
- `eval` 高 → 输出长（比如开了思维链），考虑限制输出长度或关闭思考
- 两者都不高但整体慢 → 请求在排队，考虑提高 `OLLAMA_NUM_PARALLEL` 或加硬件

### 4.4 会话持久化与上下文管理

**动机**：脚本一关，对话历史全丢。而且上下文会持续增长，最终超出上限。

**核心矛盾**：上下文有限（你当前 4096 token），但对话是无限的。**必须做取舍**。

**几种策略及其代价**：

| 策略 | 做法 | 代价 |
|---|---|---|
| 滑动窗口 | 只保留最近 N 轮 | 丢掉早期信息 |
| 摘要压缩 | 让模型把旧对话概括成一段话 | 概括会引入失真；且要额外调用一次模型 |
| 关键信息提取 | 只保留事实性内容 | 实现复杂 |
| 全量保留 | 不处理 | 迟早爆上下文 |

**工程要点**：

- 存**纯数据**（`{"role":..., "content":...}` 的列表），不要存 SDK 返回对象——这一点在你上一轮脚本里已经暴露过问题（原代码把 `response.choices[0].message` 对象直接存进了列表）
- 上下文超限时 ollama 会**裁剪最前面的内容**（日志里有 `--context-shift` 参数），但这是静默丢弃，你的程序应当自己感知并处理
- 会话状态存本地文件或 SQLite，重启可恢复

### 4.5 模型生命周期管理

**动机**：模型常驻内存会占用 RAM；卸载后下次请求又要重新加载（你日志显示加载耗时约 1.77 秒）。

**相关机制与参数**：

| 参数 | 默认 | 作用 |
|---|---|---|
| `OLLAMA_KEEP_ALIVE` | `5m` | 无请求多久后卸载模型 |
| `OLLAMA_MAX_LOADED_MODELS` | `0`（自动） | 同时驻留模型数上限 |
| `OLLAMA_LOAD_TIMEOUT` | `5m` | 加载超时 |
| `OLLAMA_MODELS` | `~/.ollama/models` | 模型存储路径（避免占满系统盘） |

**判定逻辑**：如果访问频繁（间隔短于 keep-alive），模型常驻，代价是内存；如果访问稀疏，反复加载，代价是首响应延迟。

**你的硬件是 39.7 GiB 内存 + 无独显**，跑 0.6B 模型绰绰有余，可以考虑调大 `OLLAMA_KEEP_ALIVE` 换取更稳定的响应速度。

**补充**：Windows 上设置这些变量后**必须重启 ollama 进程**才生效——环境变量只对新启动的进程有效。这个坑你在上一轮已经踩过一次。

### 4.6 前端界面

**动机**：让非技术使用者也能用，不必写代码。

| 方案 | 特点 |
|---|---|
| Open WebUI | 功能最全：多用户、权限、知识库、对话历史，可对接 ollama |
| AnythingLLM | 侧重文档问答，内置 RAG |
| Lobe Chat | 界面现代，支持多模型 |
| 自建网页 | 最可控，但需自己处理流式、历史、鉴权 |

**部署提示**：这类前端通常跑在容器里。容器内的 `localhost` 指的是**容器自己**，不是宿主机。要连宿主机的 ollama，地址应写 `host.docker.internal`（Docker Desktop）或宿主机的局域网 IP，**不能写 `localhost`**。这是初次部署最常见的失败原因。

**接前文的坑**：如果前端是网页，从手机上访问时属于跨域请求，**需要把前端的访问地址加进 `OLLAMA_ORIGINS`**——默认白名单不含局域网 IP。

### 4.7 缓存、降级与摘要

| 机制 | 作用 | 实现要点 |
|---|---|---|
| 结果缓存 | 相同问题直接返回，省算力 | 对 query 做哈希做 key；注意语义相同但字面不同的问题命中不了 |
| 语义缓存 | 用嵌入判断"意思是否相同" | 依赖 3.5 的嵌入能力 |
| 请求队列 | 限制并发，避免过载 | 显式排队并给客户端反馈，优于直接拒绝 |
| 超时降级 | 慢请求给兜底回答 | 需要提前定义"什么情况算超时" |
| 分级模型 | 简单任务用小模型 | 需要先定义"简单/复杂"的判据 |

**这里最值得做的是结果缓存**，因为它直接缓解你的算力约束，且实现简单。

### 4.8 量化与模型选择

**原理**：模型权重默认是 FP16（16 位浮点，每参数 2 字节）。量化把权重压到更低比特：

| 精度 | 每参数字节 | 相对体积 | 质量损失 |
|---|---|---|---|
| FP16 | 2.0 | 基准 | 无 |
| Q8_0 | ≈1.0 | 约 50% | 几乎无损 |
| **Q4_K_M** | **≈0.55** | **约 27%** | **轻微，通常可接受** |
| Q3_K | ≈0.43 | 约 22% | 开始明显 |

**你的 `qwen3:0.6b` 正是 Q4_K_M**——日志确认：`file type = Q4_K - Medium`、`file size = 492.75 MiB (5.50 BPW)`。

**选型规律**：
- 同一模型，量化越低速度越快、质量越差
- **Q4_K_M 是实践中常用的平衡点**
- 无独显时，**小参数量 + 高精度** 往往优于 大参数量 + 低精度（后者可能慢到不可用）

**对你直接的结论**：当前硬件上，7B 的 Q4 模型理论可行（约 4–5 GB），但 CPU 推理速度会降到 0.6B 的十几分之一，交互体验会很差。**0.6B–3B 区间是你硬件的实际舒适区。**

## 5. 按 ROI 排序的建议路线

"ROI"＝在**小于 1 天工作量**内能得到的实际能力提升。不建议跨级做。

| 阶段 | 做什么 | 投入 | 直接收益 |
|---|---|---|---|
| **第 1 步** | 流式输出 | 改几行 | 体验质变，最划算 |
| **第 2 步** | 结构化输出（`format`） | 加一个参数 | 脚本升级为可用组件 |
| **第 3 步** | 反向代理 + API Key | 半天 | 有了对外暴露的安全前提 |
| **第 4 步** | 内网穿透（优先 Tailscale 类方案） | 半天 | 摆脱同一局域网限制 |
| **第 5 步** | 嵌入 + 语义搜索 | 1 天 | 打开检索类应用的大门 |
| 第 6 步 | 可观测性 + 结果缓存 | 半天 | 稳定性和省算力 |
| 第 7 步 | 会话持久化 | 半天 | 可用性提升 |
| 第 8 步 | 前端界面 | 1 天 | 给他人使用 |
| 第 9 步 | 工具调用 | 1 天 | **建议先换更大模型，否则效果差** |
| 第 10 步 | 视觉多模态 | 1 天 | 需下载较大模型，CPU 速度受限 |
| 第 11 步 | RAG | 数天 | **前提是资料量确实大到需要** |

**为什么这个顺序**：

1. 前三步是**基础能力与安全**，成本极低但收益大
2. 第 4 步解决你当前最实际的痛点（网络移动性）
3. 第 5 步是**后续所有检索类应用的地基**——嵌入是信息检索的基础能力
4. 第 6–8 步是运维与易用性，属于"有了更好"
5. 第 9–11 步受**硬件算力**约束，小模型上效果有限，应放到换硬件之后

**一句话判断标准**：凡是需要"模型理解得更准"的功能（工具调用、多模态、复杂推理），都受参数量约束；凡是"工程层面"的功能（流式、缓存、鉴权、持久化），不受参数量约束。**你的硬件下，优先做后者。**

## 6. 关键概念速查

| 概念 | 一句话解释 | 相关参数 / 接口 |
|---|---|---|
| 流式输出 | 逐 token 推送，降低感知延迟 | `stream: true` |
| NDJSON | 每行一个 JSON，原生接口的流式格式 | `/api/chat` |
| SSE | Server-Sent Events，`data:` 前缀 + `[DONE]` | `/v1/chat/completions` |
| 结构化输出 | 在解码层约束输出符合 Schema | `format` 参数 |
| 嵌入 | 文本 → 定长向量，语义相近则向量相近 | `/api/embed`、`/v1/embeddings` |
| RAG | 先检索资料再生成，不改模型改输入 | chunking + 向量库 |
| 工具调用 | 模型输出调用意图，由你的代码执行 | `tools` 参数 |
| prompt cache | 复用公共前缀的 KV 缓存，避免重算 | 自动开启，8192 MiB 上限 |
| KV 缓存 | 注意力机制的 key/value 状态，随上下文线性增长 | 4096 token 时约占 448 MiB |
| 内网穿透 | 靠出站长连接反转连接方向，绕过 NAT | cloudflared / frp / Tailscale |
| 反向代理 | 前置一层做 TLS + 鉴权 + 限流 | Nginx / Caddy |
| 响应缓冲 | 反向代理攒批转发，会破坏流式 | `proxy_buffering off` |
| 量化 | 降低权重精度以缩小体积 | Q4_K_M ≈ 0.55 字节/参数 |
