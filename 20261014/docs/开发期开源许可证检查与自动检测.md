# 开发期的开源许可证检查与许可证自动检测

> 课程背景：《开原创新思维》课程中提到，应把"检测所使用的开源代码的许可证情况"这一动作从发布前审查提前到开发阶段。本文讲解两个问题：
>
> 1. 为什么要在开发时检查 LICENSE，以及具体检查什么；
> 2. 许可证自动检测是怎么实现的、能自动到什么程度、边界在哪里。

---

## 一、为什么"提前"是关键动作

### 1.1 传统做法与它的成本结构

传统合规流程把许可证审查放在**发布前**，作为一种交付闸门（release gate）。这个安排的问题不在于审查本身，而在于**审查发现的时机**：

- 在发布前发现某个传递依赖是 AGPL-3.0，此时它已经进入了架构、已被其他模块依赖、可能已被写进技术文档与客户材料。替换它意味着改架构、重测、延期。
- 在引入该依赖的那一天发现同样的问题，成本只是换一个库。

这就构成一条非常陡的成本曲线：**引入成本恒定且低，移除成本随耦合深度与时间指数上升**。把检查左移（shift left）到开发阶段，本质上是让一个不可逆的决策重新变得可逆。

### 1.2 检查的实质不是"能不能用"

初学者容易把这件事理解成一个二元判断——这个库的许可证"能用"还是"不能用"。这个理解会导致误判，因为许可证的约束不是针对"使用"，而是针对**分发行为与由此产生的义务**：

- 你在公司内部跑一个 GPL 工具处理数据，没有对外分发，就没有触发 GPL 的分发义务。
- 你把同一个工具打包进产品交给客户，触发了分发义务，必须随之提供对应源码。
- 你把一个 AGPL 组件部署成对外提供服务的 Web 后端，即使不交付任何二进制，AGPL 的网络交互条款同样会触发源码提供义务。

所以真正要问的问题是：**这个依赖会给"我的项目打算以什么方式交付"带来哪些必须履行的义务，而这些义务我承担得起吗？** 这是一个"义务 vs 交付方式"的匹配问题，而不是"许可证好坏"的排序问题。

### 1.3 提前检查能防住的三类风险

| 风险类型 | 具体情形 | 发布前才发现的代价 |
|---|---|---|
| 义务不可承担 | 闭源产品里混入 GPL-3.0 静态链接库 | 拆库、重写调用层、重测 |
| 许可证互不兼容 | 同一依赖闭包里同时存在 GPL-2.0-only 与 Apache-2.0 | 必须替换其中之一，可能影响多个模块 |
| 隐性依赖 | 传递依赖、vendored 代码、复制粘贴的代码片段、字体/图标/模型权重 | 追溯成本极高，责任归属不清 |

第三类是实践中最容易失守的。项目的直接依赖清单是"看得见"的，但一个前端项目的完整依赖闭包动辄数百个包，其中任何一个换了许可证，义务都会传递到你身上。

## 二、检查的对象：LICENSE 的义务结构

要检查，先要知道 LICENSE 里到底写着哪些可检查的条款。所有开源许可证的义务都可以拆成下面几类，**不同的许可证就是这几类义务的不同组合与不同强度**。

### 2.1 六类基本义务

1. **保留声明（attribution）**——保留版权声明、作者署名、许可证文本。几乎所有开源许可证都有。
2. **提供许可证全文**——分发时随附 LICENSE 副本。宽松许可证的核心义务基本就到此为止。
3. **提供源码（source provision）**——分发二进制时必须提供对应源码。这是 copyleft 的核心。
4. **同许可证授权（same-license）**——衍生作品必须以相同许可证分发。这是"传染性"的来源。
5. **专利授权与报复性终止**——授予使用者专利许可；若你以该软件侵犯你的专利为由起诉，则授权自动终止。Apache-2.0 与 GPL-3.0 都有，GPL-2.0 没有。
6. **网络服务触发**——提供网络交互式服务即视为分发。AGPL-3.0 独有。

### 2.2 传染强度的谱系

按"对被组合代码的影响范围"排序，主流许可证大致落在下面这条谱系上：

| 位置 | 许可证 | 约束范围 | 主要义务 |
|---|---|---|---|
| 无约束 | CC0 / Unlicense / Public Domain | 无 | 无（但注意：CC0 对专利不作表态，CC 官方不建议用于软件；Unlicense 缺专利与免责条款） |
| 宽松 | MIT / BSD-2 / BSD-3 / ISC | 无传染 | 保留声明、附许可证文本 |
| 宽松 + 专利 | Apache-2.0 | 无传染 | 上述 + NOTICE 文件传递 + 专利报复条款 |
| 文件级 copyleft | MPL-2.0 / EPL-2.0 | 仅修改过的文件 | 被修改的文件须以同许可证发布；可与其他许可证文件组成 Larger Work |
| 库级 copyleft | LGPL-2.1 / LGPL-3.0 | 被链接的库本体 | 库本身及其修改须开源；通过动态链接可让自己的作品不受传染 |
| 作品级 copyleft | GPL-2.0-only / GPL-3.0 | 整个衍生作品 | 分发衍生作品须整体以 GPL 授权并提供源码 |
| 作品级 + 网络触发 | AGPL-3.0 | 同上 + SaaS 场景 | 提供网络服务即须提供源码 |
| 源可用但非开源 | SSPL / BUSL / Elastic License | 由条款自定 | 不属于 OSI 认证的开源许可证；"源码可读"不等于"开源" |
| 专有 / 无许可证 | 商业许可 / 无 LICENSE 文件 | 全部权利保留 | **无 LICENSE 文件 ≠ 公共领域**，默认不可用 |

最后一行是高频错误。一个仓库没有 LICENSE 文件，法律状态是"版权保留、未授予任何权利"，你既没有复制权也没有分发权。GitHub 上看到仓库有代码可以直接 clone，那是平台的可访问性，不是许可证授权。

### 2.3 触发条件：分发（distribution / conveying）

copyleft 的义务由**分发**触发，这是理解整个体系的分水岭：

- GPL-2.0 用的词是 *distribute*，GPL-3.0 用的词是 *convey*（明确排除了"制造副本自用"这类情形）。
- **内部使用不构成分发**。公司内部部署一套 GPL 系统自用、不对外提供，不触发源码义务。
- **SaaS 对 GPL 不触发，对 AGPL 触发**。这正是 AGPL 存在的理由——它被创造出来就是为了堵住"用 GPL 做云服务而永远不分发"这个口子。
- 交付二进制给客户、交付设备固件、提供下载链接，都构成分发。

这条规则决定了策略设计的空间：同样是 GPL-3.0 的组件，在桌面客户端项目里是硬阻塞，在纯服务端的内部工具里可能完全可用。**检查工具的职责是报告许可证，判断"是否分发"是你的架构决策。**

### 2.4 兼容性：方向性比"能不能混"更重要

两个许可证不兼容，意思是无法把两边的代码合成一个作品再对外分发。这里有三个必须掌握的细节：

**第一，兼容性是单向的。**
Apache-2.0 的代码可以被纳入 GPL-3.0 的作品，整个作品以 GPL-3.0 分发——这是允许的。反过来，GPL-3.0 的代码不能被纳入一个以 Apache-2.0 分发的作品，因为 GPL-3.0 要求衍生作品也用 GPL-3.0。方向搞反，结论就完全错。

**经典案例：Apache-2.0 与 GPL-2.0-only 不兼容。**
原因具体而单一：Apache-2.0 包含专利终止与赔偿条款，而 GPL-2.0 第 6 条禁止附加任何额外限制。FSF 据此判定二者不能合并。GPL-3.0 在制定时明确接纳了 Apache-2.0 的专利条款，因此 GPL-3.0 与 Apache-2.0 兼容。所以：

```
Apache-2.0  →  GPLv3   兼容
Apache-2.0  →  GPLv2   不兼容
GPLv3       →  Apache-2.0   不兼容（方向反了）
```

**这个冲突在 Linux 内核上尤其尖锐**：内核是 GPL-2.0-only（不是 or-later），所以 Apache-2.0 的驱动代码无法直接并入主线内核。

**第二，"only" 与 "or later" 的差别是实质性的。**
`GPL-2.0-only` 表示只能按 v2 使用；`GPL-2.0-or-later` 允许使用者选择更高版本。一个 or-later 的组件可以通过选择 v3 来获得与 Apache-2.0 的兼容性，only 的组件不行。差一个后缀，结论相反。

**第三，链接方式影响衍生作品的判定。**
静态链接把库的目标代码并入你的二进制；动态链接在运行期调用共享库；子进程调用只通过接口通信；插件架构由用户在运行期加载。这四种方式在"是否构成衍生作品"上的强度依次递减，但**递减不是免责**——GPL 的判定没有一条机械的"链接方式对照表"，最终以是否构成衍生作品为准，而这是个法律判断。工程上可依赖的经验是：LGPL 明确为动态链接设计了隔离通道；GPL 没有这样的通道。

### 2.5 容易被漏掉的检查对象

许可证义务附着在**作品**上，而作品不只是 `.js` / `.py` / `.java` 源文件。实际项目中至少还要覆盖：

- **传递依赖**：依赖的依赖。任何一个包管理器都会拉进来。
- **vendored / 内嵌代码**：直接复制进仓库的第三方源码（常见于 C 项目的 `third_party/`、前端项目里内嵌的 polyfill、WebAssembly 模块）。
- **从外部复制的代码片段**：从问答站点、博客、旧项目里粘贴的代码段，通常没有许可证信息。
- **资源文件**：字体（字体许可证自成体系，OFL / Apache-2.0 / 商用授权各不相同）、图标集、示例图片、音频。
- **数据集与模型权重**：机器学习项目里，权重文件的许可证可能与代码仓库的许可证不同，且可能带有额外的使用限制条款。
- **生成的代码**：代码生成器、协议编译器产出的文件，其许可证归属取决于生成器与输入 schema 的许可证。
- **构建产物中的第三方**：打包后的 jar 里可能还有嵌套的 jar；静态编译的 Go 二进制里内嵌了全部依赖的许可证文本。

## 三、检查动作应该插在哪些环节

一个可运行的流程在时间轴上分布为五个检查点，越靠前越省事：

```
选型引入  →  编码  →  提交/PR  →  构建  →  发布
  (人工)    (标注)   (门禁★)   (清单)   (履约)
```

### 3.1 选型期：引入前的快速判定

在决定引入一个新依赖之前，用两分钟确认四件事：

1. **SPDX 标识符是什么**——是标准标识（`MIT`、`Apache-2.0`、`GPL-3.0-only`）还是一个自造的许可证名？后者需要逐条读。
2. **是否 OSI 认证**——OSI 认证清单是"这是开源许可证"的权威判定。SSPL、BUSL 这类"源可用"许可证不在清单上。
3. **声明的许可证与仓库里的 LICENSE 文件是否一致**——包元数据里的 license 字段经常与仓库实际许可证不符，这是自动检测要交叉验证的核心内容。
4. **许可证版本**——这个项目的这个版本是什么许可证？同一库跨版本换许可证是常态化操作（不少商业公司在某个版本后从 MIT/Apache 切到 BUSL）。

常用的查询入口：SPDX 许可证清单（权威标识符与全文）、OSI 认证清单（开源资格判定）、`choosealicense.com`（面向选择者的通俗对比）、GitHub 仓库页的许可证标签（快速但不精细）、ClearlyDefined / deps.dev（聚合了组件的声明与扫描许可证，适合批量查询）。

### 3.2 编码期：让许可证信息跟随文件

在源码文件头部写入结构化标签，使"哪个文件受哪个许可证约束"这个信息不再依赖猜测。REUSE 规范（FSF Europe 提出）就是为此设计的，它使用 SPDX 的文件级标签：

```c
// SPDX-FileCopyrightText: 2026 Reishkur
//
// SPDX-License-Identifier: Apache-2.0
```

需要在每个文件重复版权信息时，也可用单独的 `.license` 伴随文件或在仓库根放 `LICENSES/` 目录存放许可证全文。`reuse lint` 可以检查全覆盖情况，直接接入 CI。这一步的价值在于：**当你自己的项目有多个许可证区段、或需要向他人证明合规状态时，文件级标注是唯一可靠的证据来源**。

### 3.3 提交期：门禁（核心环节）

这是把检查"提前"落实到工程上的关键位置。设计原则是**政策即代码**：把许可证策略写进仓库配置文件，由 CI 在每次有依赖变更的 PR 上强制执行。

策略分四级，每级的默认动作不同：

| 级别 | 典型许可证 | 默认动作 |
|---|---|---|
| 允许 | MIT、BSD-2/3、ISC、Apache-2.0 | 自动通过，仅登记义务（保留声明、NOTICE） |
| 有条件允许 | MPL-2.0、EPL-2.0、LGPL-2.1/3.0 | 通过，但附加架构约束（如 LGPL 必须动态链接）并触发复核 |
| 需人工审批 | GPL-3.0、AGPL-3.0、无许可证、双许可 | 阻断并转人工，记录决策与理由 |
| 禁止 | SSPL、BUSL、专有许可、与自身许可证不兼容者 | 直接阻断合并 |

要点在于**升级动作也必须过门禁**。依赖自动升级机器人（Dependabot、Renovate 等）拉起的 PR 同样会改变依赖闭包与许可证状态，如果门禁只挂在人工 PR 上，这条通道就是漏洞。

契约上要覆盖的三件事：① 是否检测传递依赖；② 是否能在策略违规时真正阻断合并；③ 双许可与无许可证的包如何处理。任何一项缺失，门禁都是形式上的。

### 3.4 构建期：生成 SBOM

SBOM（Software Bill of Materials，软件物料清单）是"这份软件里有哪些组件、什么版本、什么许可证"的机器可读清单。它不只是合规需求，也是安全事件的响应基础——2021 年 Log4Shell 之后，能在一小时内回答"我们哪些产品用了 log4j"的公司和回答不了的公司，差距就是 SBOM。美国行政令 14028 已要求联邦供应商提供 SBOM。

两个主流格式：

- **SPDX**（Linux Foundation，ISO/IEC 5962:2021）——偏重许可证合规，支持文件级细节。
- **CycloneDX**（OWASP）——偏重应用安全与供应链分析。

两者都提供 JSON / XML 机器可读输出。SBOM 里三个字段的区分值得记住，它正好对应"声明 vs 实际"这个问题：

- `PackageLicenseDeclared`——包作者**声明**的许可证；
- `PackageLicenseConcluded`——扫描者根据实际扫描**判定**的许可证；
- `PackageLicenseInfoFromFiles`——从各个文件检测到的许可证集合。

自动检测的价值，很大程度上就是让 Declared 与 Concluded 的差异可见。

### 3.5 发布期：履行义务

检查的目的最终是要履行义务。发布包中通常需要一个顶层的汇总文件（常见命名 `NOTICE`、`THIRD-PARTY-NOTICES`、`CREDITS`、`LEGAL`），内容包含：

- 每个第三方组件的名称、版本、许可证标识符；
- 各许可证的完整文本；
- Apache-2.0 组件若自带 NOTICE 文件，其相关部分须并入你的顶层 NOTICE（这是 Apache-2.0 区别于 MIT 的一项额外义务，容易被漏掉）；
- 若有 GPL/LGPL 组件，还需说明源码获取方式（随附、提供下载地址，或以有效的书面要约提供）。

## 四、自动检测是怎么实现的

自动检测不是一个功能，而是**两条技术路线**，它们的数据来源、精度特性和失效模式完全不同。理解这一点比记住工具名重要得多。

### 4.1 路线 A：依赖级检测（解析声明与元数据）

**工作原理**：解析包管理器的依赖清单与锁定文件，得到确定版本的组件列表，再查询元数据源获取每个组件的许可证字段。

关键设计点是**读锁定文件（lockfile）而不是读清单文件（manifest）**：

- `package.json` 里的 `"^4.17.21"` 是一个版本范围，实际解析出哪个版本不确定；
- `package-lock.json` 里是被钉死的精确版本。

许可证随之绑定在版本上，所以必须以锁定文件为真相来源。对应关系：npm → `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`；Python → `poetry.lock` / `requirements.txt`（钉版后）；Rust → `Cargo.lock`；Go → `go.sum` 与 `go.mod`；Java → `pom.xml` / Gradle 锁定；.NET → `packages.lock.json`。

拿到组件列表后，用 **PURL**（Package URL，形如 `pkg:npm/lodash@4.17.21`）作为跨生态的统一组件标识，再去元数据源查询许可证。这条路线天然覆盖传递依赖——锁定文件里本来就包含全部传递依赖的解析结果。

**特性**：
- 快，几秒到几十秒；
- 覆盖完整依赖闭包；
- 误报极低。

**失效模式**：**信任元数据**。如果包的 license 字段写错、留空、或与实际打包内容不符，依赖级检测就会跟着错。它回答的是"作者声称的许可证是什么"，而不是"代码里实际的许可证是什么"。

### 4.2 路线 B：文件级检测（扫描代码文本）

**工作原理**：不看元数据，直接读代码文件的内容，与一个许可证参考语料库做文本比对，判断这段文本是哪个许可证。

这是"自动检测"技术含量的所在。以 ScanCode Toolkit 的设计为参照，它的匹配管线是**渐进式的**——先用便宜的方法试，只在必要时才用昂贵的方法：

**第 1 层：分词与词到整数的映射。**
不做字符级比对，而是按"词"处理。所有许可证语料涉及约一万五千个不同的词，因此可以建立一张词表把每个词映射为唯一整数。映射时按词频分配 ID：**高频词给低 ID（低区分度），低频词给高 ID（高区分度，即特征词）**。并设定一个阈值，低于阈值的词由于过于常见，无法单独构成许可证文本或声明。这样做有三个收益：后续所有操作变成整数集合运算（比字符串操作快）、内存占用可压缩到 16 位无符号整数数组、可以用位图等紧凑结构表示集合。

**第 2 层：整段哈希匹配。**
把整个待检文本做哈希，与"哈希 → 许可证规则"映射表比对。命中即返回。这一层处理最常见的场景：文件里原封不动地放着一段标准许可证全文。

**第 3 层：精确多模式匹配。**
把整段文本送入 Aho-Corasick 自动机，一次扫描找出语料库中所有精确出现的许可证文本或声明。命中即返回。这一层能处理"一个文件里嵌着好几段许可证引用"的情况。

**第 4 层：近似集合匹配（bag of words）。**
走到这里说明文本被改动过（比如填了著作权人、删了段落、加了注释）。做法是把文本表示成"词的集合"，变成整数向量，与索引中的向量比对——概念上等价于信息检索里的倒排索引检索。用**相似度（resemblance）与包含度（containment）**对候选排序，取最优的几个。然后对这几个候选**再做一轮多重集匹配**：多重集不仅看词是否出现，还看每个词出现几次，精度比第一轮高。两轮结果合并排序，得到候选集。

**第 5 层：成对局部序列比对。**
只对上面筛出的少数候选做序列比对——本质上是优化过的 diff，作用在整数序列上。它利用"高频低区分度词不予参与"这一点显著降低计算量。这一层的作用是给出**精确的匹配位置**：哪一段匹配上了，哪一段是新增或删除的。

**第 6 层：合并、精炼、过滤、打分。**
把多层得到的匹配合并成一个或多个 license detection，合并时考虑相似度、包含度、重叠区间，以及若干次级因素；过滤时依据匹配的密度、长度、匹配上的特征词数量；最终每个匹配按"规则文本中被匹配上的比例"打分。

**为什么这套设计是必要的**——对比一下替代方案：

- **纯正则表达式**：需要预先掌握许可证文本之间的细微关系才能写对，维护成本极高；且对相似许可证（例如 BSD 各变体、GPL 各版本）必须再写一遍复杂消歧逻辑。语料一变，正则全部要重审。
- **朴素的两两比对**：1000 个文件 × 1000 个参考文本，意味着上亿次 diff，完全不可行。渐进式管线的作用正是让"绝大多数情况在前两层就返回，根本不需要做昂贵的比对"。

参考规模上，ScanCode 维护的许可证文本库约在两千条量级，声明与引用规则约数万条。作为对比，GitHub 的许可证标签使用的小型语料只有二十来条常见许可证，因此它只能给出粗略提示，不能作为合规依据。

### 4.3 为什么自动检测必然不完美

工具输出的是"文本相似度推断"，不是法律结论。它会在下面这些地方失效或犹豫：

| 失效原因 | 具体表现 |
|---|---|
| 许可证变体 | BSD-3-Clause 的著作权人字段、Apache-2.0 附录的填写内容、GPL 文件头的 "or later" 声明——这些是许可证模板中允许变化的部分，工具需要正确识别"哪些差异是正常的" |
| 短引用歧义 | "This software is GPL" 这类极短声明，上下文不足以确定是哪个 GPL 版本 |
| 声明与实际不一致 | 元数据写 MIT，实际打包了 GPL 的二进制；这种情况只有文件级扫描才能发现 |
| 无许可证文件 | 工具无法从"没有许可证文本"推出法律状态，需要单独规则处理 |
| 混杂文本 | 一个文件里多段不同许可证的引用 |
| 二进制内嵌 | 嵌套 jar、静态链接的 Go 二进制、WebAssembly，需要先解包才能扫描 |
| 改动过的文本 | 被翻译、被截断、被拼接的许可证段落 |
| 生成代码 | 代码生成产物、混淆压缩后的代码，文本特征被破坏 |

因此**实践中正确的做法是两条路线都跑，然后做一致性对账**：依赖级给出"声明值"，文件级给出"实际值"，两者不一致的地方就是最需要人工复核的地方。

### 4.4 工具选型

按用途分层，从轻到重：

| 层次 | 代表工具 | 适用场景 |
|---|---|---|
| 包管理器原生 / 轻量 CLI | `license-checker`（npm）、`pip-licenses`（Python）、`go-licenses`（Go）、`cargo-about` / `cargo-deny`（Rust）、`license_finder`（Ruby，多语言） | 个人项目、小团队，接入 CI 成本最低 |
| 平台内置 | GitHub Dependency Review（`dependency-review-action`，支持按 SPDX 标识符配置禁止清单） | 已用 GitHub 的项目，PR 层面直接生效 |
| 文件级扫描 | ScanCode Toolkit、FOSSology、`licensee`、REUSE Tool | 需要验证实际许可证文本、审计 vendored 代码、生成文件级清单 |
| SBOM 生成 | `syft`、`cdxgen`、ScanCode 的 SPDX/CycloneDX 输出 | 需要交付 SBOM 或建立合规证据链 |
| 完整合规平台 | ORT（OSS Review Toolkit）、FOSSA、Snyk、Black Duck、Checkmarx | 中大型团队，有专职合规流程，需要策略引擎、审批流与报表 |

选型判断标准是三个问题：**是否覆盖传递依赖、能否在 CI 中真正阻断合并、双许可与无许可证如何处理**。任何一项答不上来的工具，只能作为提示，不能作为门禁。

## 五、可照搬的最小可行方案

以一个 npm 项目接 GitHub 为例，三段式落地，复杂度递增，可任选起点。

**第一段：PR 门禁（十分钟接入）**

```yaml
name: license-gate
on:
  pull_request:
    paths:
      - "package.json"
      - "package-lock.json"

jobs:
  license:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - name: check declared licenses
        run: npx license-checker --summary --failOn "GPL-3.0;AGPL-3.0;SSPL-1.0"
```

`--failOn` 接受分号分隔的 SPDX 标识符列表；命中即返回非零退出码，PR 被阻断。这一步覆盖依赖级检测与策略执行，成本最低、收益最直接。

其余生态的等价命令：

```bash
pip-licenses --format=markdown --with-urls --fail-on "GPL-3.0;AGPL-3.0"
go-licenses check ./... --disallowed_types=forbidden,restricted
cargo deny check licenses      # 需先配置 deny.toml 的 allow 列表
reuse lint                     # 检查文件级许可证标注覆盖率
```

**第二段：补上文件级扫描（防元数据谎报）**

```bash
scancode --license --copyright --info --json-pp scan.json ./src ./third_party
```

把 `scan.json` 里的检测结果与第一段的声明结果做对账，不一致的组件进入人工复核清单。

**第三段：生成 SBOM 与履约文件**

```bash
syft . -o spdx-json=sbom.spdx.json
syft . -o cyclonedx-json=sbom.cdx.json
```

发布时从 SBOM 派生出顶层 `THIRD-PARTY-NOTICES`，并检查 Apache-2.0 组件的 NOTICE 是否已并入。

## 六、回到课程：这套做法的定位

课程提出"把检测提前到开发阶段"，工程上它对应三个明确的方法论迁移：

**其一，合规从审查动作变成工程能力。** 审查依赖人的记忆与自觉，门禁依赖配置与流水线。前者随人数增长而失效，后者不会。

**其二，把法律不确定性收敛在可管理的边界内。** 自动检测无法给出法律结论，但能把需要法律判断的范围从"全部依赖"缩小到"少数不一致项与高风险许可证"。工具的价值不在于替代判断，而在于把判断的输入准备齐全。

**其三，与供应链安全共用同一套基础设施。** SBOM 既服务许可证合规，也服务漏洞响应；依赖清单既用来做许可证策略，也用来做版本升级与安全检查。这也是为什么这件事应该尽早、以工程化的方式做——它不是一次性任务，而是一条需要长期维护的流水线。

> 最后一句必要提醒：许可证合规的最终判断权在法院，不在工程师，也不在扫描工具。工程惯例与最佳实践不能替代法律意见。对高风险场景（闭源商业化分发、嵌入式交付、涉及专利的领域），扫描结果只能作为咨询律师时的输入材料。
