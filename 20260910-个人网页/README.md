# git 自动发布代码更新的常用方式

## 一、先划清边界：git 不管部署

git 的职责只有三件事：

1. **对象存储** —— blob（文件内容）、tree（目录结构）、commit（一次快照 + 元信息）、tag（带注解的引用）四类对象，全部按内容哈希寻址。
2. **引用管理** —— branch 和 tag 本质是"某个名字指向某个 commit"的文件。
3. **传输协议** —— fetch / push 时协商并搬运对象，最小化传输量。

它没有"运行服务"这个概念。它不知道你的代码该怎么启动、产物该放哪个目录、需不需要重启进程。

因此，任何"自动发布"都是同一件事的两半：

- **挂载点**：在 git 的哪个动作完成后，把控制权交出去；
- **同步动作**：接手的程序做什么，把哪个 commit 的内容变成正在运行的服务。

挂载点这一半，git 给的选项固定且有限；同步动作那一半，才是各家方案差异的来源。

## 二、挂载点全貌

### 2.1 hook 与 webhook 的区别

这两个词常被混用，但它们是不同层次的东西。

| 维度 | hook | webhook |
|---|---|---|
| 归属 | git 原生机制 | 托管平台的增值服务 |
| 形式 | git 进程 exec 一个本地脚本 | 平台向指定 URL 发 HTTP POST |
| 同步性 | 同步阻塞；钩子不返回，push 不算结束 | 异步；平台不等待响应 |
| 输入 | git 内部状态（stdin 引用列表、仓库路径、参数） | 平台封装好的 JSON 事件摘要 |
| 部署位置 | `.git/hooks/`（服务端则是裸仓库的 hooks） | 平台配置页或仓库配置文件 |

由此推出一个实用结论：**hook 能拿到 git 的内部状态，webhook 只能拿到平台想给你的信息**。需要精确知道"哪几个引用被更新"时，只有 hook 直接给了你；webhook 给的是平台加工的 payload。

### 2.2 挂载点地图

按时间顺序，一共有三类挂载点：

**第一类 · 提交阶段（本地仓库）**

| 钩子 | 触发时机 | 输入 | 典型用途 |
|---|---|---|---|
| `pre-commit` | 提交动作之前 | 无参数 | lint、格式化、拦截大文件与密钥 |
| `commit-msg` | 提交信息确定后 | 提交信息临时文件路径 | 校验 Conventional Commits 格式 |
| `pre-push` | 推送动作之前 | remote 名、URL | 推送前跑测试 |
| `post-commit` | 提交完成后 | 无参数 | 本地通知、触发本地构建 |

**第二类 · 推送接收阶段（git 服务端）**

| 钩子 | 触发时机 | 粒度 | 中止能力 |
|---|---|---|---|
| `pre-receive` | 整个推送批次开始前 | 批次 | 退出码非 0 → 整批拒绝 |
| `update` | 每个引用各调一次 | 单个引用 | 退出码非 0 → 该引用被拒 |
| `post-receive` | 所有引用更新完成后 | 批次 | 钩子已无法影响结果 |

判断依据很明确：**要拦截就用 `pre-receive` / `update`，要发布就用 `post-receive`**。因为只有 `post-receive` 阶段对象和引用都已落盘，此时读到的状态才与推送方声称的一致。

**第三类 · 推送之后（托管平台）**

平台比对引用得出事件类型，然后：

- 发给 webhook 端点（你自己搭的服务）；
- 或按仓库内配置文件拉起 CI runner；
- 或由平台自身的构建系统处理（托管式部署）。

## 三、方式一：客户端钩子

### 3.1 基本机制

脚本放在 `.git/hooks/` 下。`git init` 会放一批带 `.sample` 后缀的示例，去掉后缀并赋予可执行权限才生效。文件名固定，无扩展名。

### 3.2 三个必须理解的前提

**前提一：`.git/hooks/` 不在版本控制里。**

这个目录不随 `clone` 分发，团队每个人都要手工安装。husky、lefthook、pre-commit 这些框架存在的唯一理由就是解决这一点：它们把真正的脚本放进仓库（如 `.husky/`、`.pre-commit-config.yaml`），再在安装依赖时往 `.git/hooks/xxx` 写入一段转发用的壳脚本。

**前提二：可以绕过。**

- `git commit --no-verify` 跳过 `pre-commit` 与 `commit-msg`；
- `git push --no-verify` 跳过 `pre-push`。

本地用户对自己的机器有完全控制权，任何客户端约束都可以被解除。

**前提三：以本机当前用户身份执行。**

钩子能读到你的一切：SSH 私钥、云平台凭据、全部文件。反过来，从外部引入的钩子脚本也具备同等权限——这是供应链风险的一个入口。

### 3.3 结论

客户端钩子只能作为**质量门禁的辅助**。发布是不可绕过的强约束，而它天然可绕，把发布责任放在这里等于没有约束。

它唯一成立的场景是：单人、可信机器，用它省掉一次手工操作。

## 四、方式二：服务端钩子 + 裸仓库

### 4.1 为什么是裸仓库

`git init --bare` 创建的仓库只有对象库与引用，没有工作区。托管端不需要有人在那儿编辑文件，工作区纯属浪费——而且有工作区反而会让"推送目标目录"和"运行目录"混淆。

### 4.2 完整链路

```
本地仓库  --git push-->  裸仓库 /srv/app.git  --引用更新完成-->  post-receive 钩子  --检出-->  运行目录
```

1. 服务器上建裸仓库：`git init --bare /srv/app.git`
2. 本地添加远端：`git remote add prod user@host:/srv/app.git`
3. 执行 `git push prod main`
4. 服务端依次触发 `pre-receive` → `update` → `post-receive`
5. `post-receive` 中把对应 commit 检出到运行目录

### 4.3 钩子脚本写法

```bash
#!/bin/bash
# 位置：/srv/app.git/hooks/post-receive
# 要求：chmod +x，无扩展名
TARGET=/var/www/app
while read -r oldrev newrev refname; do
  [ "$refname" = "refs/heads/main" ] || continue
  git --git-dir=/srv/app.git --work-tree="$TARGET" checkout -f main
done
```

**`stdin` 的格式**：每行一个 `oldrev newrev refname`，三者以空格分隔。

**必须处理的边界**：

| 情况 | 特征 | 不处理会怎样 |
|---|---|---|
| 新建分支 | `oldrev` 为 40 个 0 | 一般无害，但日志会误导 |
| 删除分支 | `newrev` 为 40 个 0 | 会试图检出一个不存在的 commit 而失败 |

**为什么必须指定 `--git-dir` 与 `--work-tree`**：裸仓库没有工作区，`git checkout` 默认把文件写进仓库目录。二者必须同时给出。写成环境变量 `GIT_DIR` / `GIT_WORK_TREE` 与命令行参数语义等价。

**`-f` 的作用**：强制覆盖目标目录中的本地改动。部署目录本就不该有人工修改，覆盖是预期行为。

**更干净的替代方案**：

```bash
git --git-dir=/srv/app.git archive main | tar -x -C "$TARGET"
```

`git archive` 直接从对象库导出快照，不写索引、不在目标目录产生 `.git`。配合 `rsync --delete` 可同时清理已删除的文件。

### 4.4 两个真实缺陷

**缺陷一：非原子。** 目标目录是活目录，检出到一半时线上文件是新旧混杂的。改进方式：

- 部署到带时间戳的新目录，最后用 `ln -sfn` 原子切换符号链接（`ln -sfn` 本身是原子的）；
- 或保留上一版本目录，切换失败立即回切。

**缺陷二：无并发控制。** 两次推送间隔极短时，两个钩子进程会同时执行。加 `flock`：

```bash
exec 9>/var/lock/deploy.lock
flock -n 9 || { echo "另一个部署正在进行"; exit 1; }
```

### 4.5 权限设计

钩子以运行 git 进程的用户身份执行。不要用 root，专门建一个部署用户，配合 SSH 的 `command=` 限制该密钥只能执行 git 命令：

```
command="git-shell -c \"$SSH_ORIGINAL_COMMAND\"",no-port-forwarding,no-agent-forwarding ssh-ed25519 AAAA... deploy@ci
```

## 五、方式三：托管平台 webhook → CI/CD

### 5.1 链路

1. push 到达托管平台；
2. 平台比对前后引用，判定事件类型（push / pull_request / tag）；
3. 命中仓库内流水线配置的触发条件，分配 runner；
4. runner 在**全新的一次性环境**中 checkout 对应 commit；
5. 执行声明式步骤：装依赖 → 构建 → 测试 → 部署；
6. 部署动作通常是 rsync/scp 上传、构建镜像推 registry、调云平台 API、或更新 Deployment。

### 5.2 配置文件位置

| 平台 | 配置文件 | 触发写法 |
|---|---|---|
| GitHub Actions | `.github/workflows/*.yml` | `on: push: branches: [main]` |
| GitLab CI | `.gitlab-ci.yml` | `stages` + job 的 `rules` |
| Jenkins | `Jenkinsfile` | 声明式流水线 + 插件触发 |

### 5.3 相对方式二的实质优势

**构建环境是一次性的、声明式的。** runner 每次从干净镜像启动，同一 commit 必然得到同样结果，不会积累"这台机器以前装过什么"的隐形状态。方式二做不到：那台服务器的环境是历史沉积的产物，不可复现。

这个差别在实践中意味着：方式二的问题往往"只在服务器上复现"，方式三的问题能稳定复现。

### 5.4 两条安全底线

**底线一：密钥只能通过平台注入。** GitHub Secrets、GitLab CI/CD Variables、Jenkins Credentials。绝不写进仓库——哪怕后来删掉，历史里仍然存在，任何能 clone 的人都能读到。

**底线二：来自 fork 的 PR 默认拿不到密钥。** 一旦允许执行不可信 PR 的代码并同时注入密钥，等于给陌生人一个"执行任意代码 + 读走凭据"的窗口。GitHub 上 `pull_request` 与 `pull_request_target` 的区别正是围绕这一点设计的：后者在基础分支的上下文里运行且能拿到 secrets，因此绝不能 checkout PR 的代码再执行。

## 六、方式四：平台原生 Git 集成

### 6.1 静态站点

Vercel / Netlify / Cloudflare Pages / GitHub Pages：授权仓库后平台自动注册 webhook，推送即构建并发布到 CDN。

两个关键特性：

- **产物不可变**：每次构建的产物单独留存。回滚只是把指向切回旧产物，不需要"反向执行一次部署"。这比方式二的"就地 checkout"强得多——后者回滚要重新检出旧 commit，且同样非原子。
- **分支即环境**：主分支对应生产域名，其它分支和每个 PR 各自得到独立预览域名。

### 6.2 应用托管

Heroku / Railway / Render / Fly.io：

- `git push heroku main` 表面像方式二，实际是服务端 `pre-receive` 钩子触发 buildpack 构建；
- 构建发生在平台侧，产出 slug / 镜像（不可变）；
- 发布阶段切换产物 + 重启进程。

这一类本质是把方式二、方式三产品化，你只提供仓库授权与构建命令。

## 七、方式五：轮询式

### 7.1 唯一适用理由

目标机器收不到入站连接：无公网 IP、位于内网、防火墙封闭。webhook 送不进去，只能由目标主动拉。

### 7.2 实现

```bash
# crontab
* * * * * /usr/local/bin/deploy.sh
```

```bash
#!/bin/bash
# /usr/local/bin/deploy.sh
cd /var/www/app || exit 1
git fetch origin main -q
LOCAL=$(git rev-parse HEAD)
REMOTE=$(git rev-parse origin/main)
[ "$LOCAL" = "$REMOTE" ] && exit 0
flock -n /tmp/deploy.lock git reset --hard "$REMOTE"
```

要点：

- 先比对 hash，不同才动，避免每分钟产生无意义的索引写入与日志；
- 更省的方式：`git ls-remote origin main` 只取远端引用（不下载对象），比对后再决定是否 fetch；
- `git reset --hard` 丢弃目标目录的本地改动，与"部署目录不接受人工编辑"一致；
- `flock -n` 防止上一次部署未结束又启动一次。

### 7.3 权衡

| 优点 | 缺点 |
|---|---|
| 无需入站端口，NAT / 内网后也能用 | 发布延迟等于轮询间隔 |
| 实现极简 | 推送方拿不到部署结果反馈 |
| 无外部依赖 | 无法做到原子切换 |

## 八、五种方式的横向对比

| 维度 | 客户端钩子 | 服务端钩子 | webhook + CI | 平台原生 | 轮询 |
|---|---|---|---|---|---|
| 触发点 | 提交 / 推送前 | 推送接收时 | 推送之后 | 推送之后 | 定时 |
| 执行位置 | 本机 | git 服务器 | CI runner | 托管平台 | 目标机器 |
| 可绕过 | 是 | 否 | 否 | 否 | 否 |
| 环境可复现 | — | 否 | 是 | 是 | 否 |
| 产物可回滚 | — | 需自建 | 视实现 | 原生支持 | 需自建 |
| 部署延迟 | 即时 | 即时 | 分钟级 | 分钟级 | 轮询间隔 |
| 外部依赖 | 无 | 无 | 平台 | 平台 | 无 |

## 九、触发语义：推送不等于应该发布

这一层与选哪种方式无关，是所有方案的公共部分。

| 触发事件 | 目标环境 |
|---|---|
| push → main 分支 | 生产环境 |
| push → develop 分支 | 预发 / 测试环境 |
| 开 PR / MR | 一次性的预览环境 |
| 打 tag `v1.2.3` | 版本化的正式发布 |

常见收紧手段：

- 用 tag 触发正式发布，生产版本与 commit 一一对应且可追溯；
- 要求 PR 合并而非直推主分支；
- 要求 CI 全绿才允许进入部署阶段（在流水线里用 `needs:` 表达依赖）。

## 十、与方案无关的六个工程问题

**1. 原子性。** 就地覆盖活目录，过程中线上新旧混杂。要么新目录 + 符号链接原子切换，要么不可变产物 + 切换指向。

**2. 并发。** 短时间内的两次触发会重叠执行。加锁。

**3. 幂等。** 同一 commit 重复部署不应产生不同结果。避免在部署脚本里做"追加"类操作。

**4. 密钥管理。** 由平台或环境注入，绝不进仓库。历史提交无法真正删除。

**5. 产物与源码的区别。** 静态站点只需发布构建产物；后端服务要重启进程；容器要重新构建镜像并推 registry。"部署"在这三种情况下是三个不同动作，选型前必须先确定自己属于哪种。

**6. 执行身份。** 服务端钩子以运行 git 的用户身份执行，该用户不应有 root 权限。用专门部署用户 + SSH `command=` 限制。

## 十一、选型判断链

三个问题，按顺序问：

1. **目标机器能收到入站连接吗？**
   不能 → 只能轮询（方式五）。

2. **需要构建与测试门禁吗？**
   需要 → CI/CD（方式三）；如果托管平台自带构建能力 → 平台原生（方式四）更省事。

3. **没有托管平台，就是一台自建服务器？**
   → 服务端钩子（方式二），零依赖。

客户端钩子（方式一）不参与这个判断：它做质量门禁，不做发布。

## 十二、常见组合

成熟用法是分层叠加，三者职责不同、互不冲突：

- **本地钩子**：快速反馈，几秒内告诉开发者提交信息格式、代码风格、测试是否通过；
- **CI 流水线**：不可绕过的门禁与构建，产出可复现的产物；
- **部署环节**：由平台或脚本执行，只接受 CI 产出的、已验证的 commit。

这样分层的意义在于：把"反馈速度"和"约束强度"这两件互相冲突的事分给不同的层。本地钩子快但可绕，CI 慢但绕不过——两者各司其职，而不是试图用一个机制同时满足两个目标。
